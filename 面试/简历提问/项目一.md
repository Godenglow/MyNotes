## A. 项目定位、架构与选型（12 问）

> [!warning] 本组最容易被打穿的点
> 第 1、9、11 问都是「数据量级与真实度」，答虚了后面全崩——直接承认是本地演示规模。

### 1. 这个系统的业务目标是什么？"瞬时流量远大于库存"具体是什么量级（并发数、QPS、参与人数、库存量），你是如何估算的？

业务目标是通用的「限库存争抢」问题：库存很少（个位数到几十），而同一时刻有远多于库存的人来抢，谁先到谁得。

**当前是本地演示规模**：库存 10 件、并发 30、单机运行、没有真实用户。如果按真实业务估算，口径是「参与人数 × 峰值集中度 ÷ 时间窗」：假设 5 万人参与、8 成集中在开抢后 3 秒内，峰值就是每秒一万多请求——这个量级下单机 MySQL 每秒只能承受千级写入，所以必须靠 Redis 前面挡、MQ 后面削。

### 2. 为什么选择 Spring Boot + MyBatis + Redis + RabbitMQ 这套组合？其中每一件技术分别解决了什么核心矛盾？

逐件对应矛盾：Spring Boot 解决「快速搭起可运行的服务」（内嵌 Tomcat、自动装配，省掉 war 部署）；MyBatis 解决「SQL 可控」（秒杀的核心是一条带条件的原子 UPDATE，ORM 自动生成的 SQL 反而不好控制）；Redis 解决「数据库连接是稀缺资源」——用一次内存原子操作把绝大多数请求挡在数据库之外；RabbitMQ 解决「请求线程不该等数据库写完」——投递即返回，把写操作串行化到消费端。

### 3. 为什么用 RabbitMQ 而不是 Kafka 或 RocketMQ？在你的业务场景下三者优劣如何对比？

本项目消息量很小（每秒几十到几千条），选型看的是**功能匹配**而不是吞吐：RabbitMQ 单条消息可控、支持 per-message ack、原生有死信/延迟队列（TTL+DLX），异步下单这类「短消息、要可靠投递、可能要做延迟任务」的场景很合适；Kafka 是为高吞吐日志流设计的，topic 分区模型更重，延迟队列要靠自研时间轮；RocketMQ 在事务消息、大规模堆积上更强，但部署更重。

**结论**：量级小的时候 RabbitMQ 最省事；如果消息量到十万级每秒、需要顺序写日志，我会换 Kafka。

### 4. 三级拦截之间是逐级过滤还是每层都执行？请求穿过每一层的命中率与耗时分别是多少？

逐级短路，任一层拒绝即返回，后面不再执行。顺序与耗时：

① JVM 本地售罄标记——无网络调用，纳秒级；

② Redis DECR 预减——一次 RTT，本机同网段约 0.1~0.3ms；

③ 数据库原子 UPDATE——行锁 + 一次写盘，毫秒级。实测 30 个并发请求中，10 个穿过全部三层最终入队，20 个在第二级被判售罄（其中一部分在被第一级短路，因为 DECR 变负后本地标记被置位，后续请求不再访问 Redis）。

### 5. 能否从浏览器点击开始，完整讲一遍到订单落库的请求链路？其中同步与异步的切换点在哪里？

① 打开详情页 → `GET /goods/detail/{id}` 拿状态；

② 点「立即秒杀」→ `GET /seckill/verifyCode` 拿算术验证码图片（答案存 Redis，TTL 300 秒）；

③ 输入答案 → `GET /seckill/path` 校验验证码（校验通过即删除，一次性），生成 `MD5(uuid + 固定盐)` 作为个人秒杀路径存 Redis（TTL 60 秒）；

④ `POST /seckill/{path}/seckill` 提交，服务端依次校验 path、本地售罄标记、是否已抢过、Redis 预减库存，然后**把消息投进 `seckill.queue` 并立即返回 `data=0`**；

⑤ 消费端异步取出消息，再查一次数据库库存与重复订单，在事务里执行「原子减库存 + 写 order_info + 写 seckill_order + 回写 Redis 订单缓存」；

⑥ 前端轮询 `GET /seckill/result` 拿最终结果。**同步/异步的切换点就是第 ④ 步投递消息之后**——返回的是"已排队"，不是"已下单"。

### 6. 商品、库存、订单三张表的结构和索引是怎么设计的？订单表除了唯一索引还建了哪些索引，依据是什么？

四张业务表：`goods`（商品基础信息）、`seckill_goods`（秒杀活动：秒杀价、`stock_count`、时间窗）、`order_info`（订单详情）、`seckill_order`（秒杀资格记录：`user_id, goods_id, order_id`）。索引：`seckill_order` 上 **`UNIQUE KEY uk_user_goods (user_id, goods_id)`** 是防重最后防线；`order_info` 上建了 `idx_user_id` 和 `idx_goods_id`——依据是两条实际查询：按用户查订单列表、按商品统计成单量。`seckill_goods` 上建了 `idx_goods_id`，因为减库存那条 UPDATE 是按 `goods_id` 定位的。

### 7. 库存是放在商品表里还是单独建表？两种方案各有什么优缺点，你如何取舍？

本项目用**单独表** `seckill_goods` 存秒杀库存，`goods` 表存的是常规库存 `goods_stock`。好处：一次秒杀活动的库存、价格、时间窗是**活动维度的属性**，同一商品可以有多场活动、可以设置不同的秒杀价，独立表更自然；而且减库存只更新这一张窄表，行锁只锁一行、不碰商品主表，减少与商品信息读取的锁冲突。缺点是多一次关联查询（`left join`）。如果业务只有一个价格、一场长期活动，放商品表里少一次 join 更简单——取舍点是「活动是否需要独立生命周期」。

### 8. 系统做过限流、降级、熔断吗？为什么没有引入 Sentinel 之类的组件？

**限流做了**：自定义 `@AccessLimit(seconds, maxCount, needLogin)` 注解 + `AccessInterceptor` 拦截器，按「用户 + URI」维度在 Redis 计数。**降级和熔断没做，也没引入 Sentinel**——诚实说，单机演示场景没有服务依赖链（就是本机的 MySQL/Redis/MQ），Sentinel 的价值主要在多服务、多依赖的熔断与规则动态推送，这里用不上，引进来只是增加复杂度。如果这个系统要上生产，我会按「依赖谁就给谁加熔断」的原则做：Redis 不可用时的降级（直接拒绝并提示）、MQ 不可用时的降级开关、数据库连接池打满时的快速失败。

### 9. 项目是单机还是多机部署？如果单机运行，"高并发"结论是否还成立？多机部署后你的哪些设计会失效？

**单机部署**（本地 `java -jar`，依赖本机 MySQL、VM 上的 Redis、本机 RabbitMQ）。单机运行下，「高并发」这个说法要限定为**正确性结论**而不是吞吐结论：我验证的是「30 并发抢 10 件库存不超卖、不重复」，这是并发安全性的证明；吞吐能力我没有压到 QPS 级。多机部署后会失效/需要改的有三处：

① **JVM 本地售罄标记会各实例不一致**——A 实例判售罄不影响 B 实例，这个标记只能作为"提前短路"的优化，不能作为正确性依据（正确性始终在数据库那条 UPDATE 上，所以不会超卖，但可能出现"本地说过早售罄、其实还有货"的漏单）；

② `@AccessLimit` 的计数在 Redis 里是共享的，多实例下依然正确；

③ 消费端如果有多个实例，`prefetch` 与并发数的组合需要重新评估。

### 10. 两个月的周期里团队有几个人？你独立负责哪些模块？项目的代码量大概多少？

【按实际填】参考口径：代码量是**59 个 Java 源文件**（实测）、**5 张表**（`seckill_user` / `goods` / `seckill_goods` / `order_info` / `seckill_order`）、**12 个映射接口**（5 个 `@Controller`：`/login` 2 个、`/goods` 3 个、`/seckill` 5 个、`/order` 1 个、`/ai` 1 个 —— 其中 2 个返回 HTML 页面、1 个返回验证码图片、1 个是 SSE 流，严格说不是全是 REST 接口）。如果被问"你负责哪部分"，建议按真实情况答，例如"独立完成全部后端开发与部署调试"；如果确实参考了公开实现范例，**如实说"架构参考了公开的开源实现范例，缺陷修复、配置外置、AI 模块与并发验证是我自己做的"**——这个说法经得起追问，而且比含糊其辞安全得多。

### 11. 项目的实际运行形态是什么（本地演示/服务器部署/对外可用）？有没有真实用户访问？

**本地演示**：应用跑在本机 8088 端口，MySQL 本机、Redis 跑在一台 Linux 虚拟机、RabbitMQ 本机，没有对外发布、没有真实用户。诚实说明这一点，然后把重点转到「我用什么方式证明它是正确的」——端到端 + 并发验证脚本（27 项断言）与数据库侧的守恒校验。

### 12. 你认为这个项目最难的三个技术点是什么？其中哪一个方案完全由你独立设计？

① **判重与预减的先后顺序**——先扣 Redis 再判重会白扣库存（数据库里没有对应订单），这个顺序错了不会报错、只会少卖，很难发现；

② **重复下单的可靠防护**——只靠 Redis 判重是不可靠的（缓存丢失/重启即失效），必须用数据库唯一索引兜底，这是"缓存做加速、数据库做正确性"的分工认识；

③ **AI 模块与业务数据的安全接合**——让模型能查到实时库存/订单，同时不能让它越权查别人的数据。其中**完全由我独立设计并实现的是 ③**（工具函数不使用 userId 参数、身份由服务端注入），以及 ①②里判断依据的确立与验证方式。

## B. JVM 内存售罄标记（7 问）

> [!warning] 本组最容易被打穿的点
> 第 15 问（多实例一致性）与第 18 问（实测收益）——后者项目里没做过前后对比，别编数字。

### 13. JVM 内存售罄标记是用什么数据结构实现的，放在哪一层？它为什么比查询 Redis 更快？

`SeckillController` 里一个 `private Map<Long, Boolean> localOverMap = new ConcurrentHashMap<>()`，key 是 goodsId，value 表示"该商品是否已判定售罄"。放在 Controller 这一层（应用层，进程内）。比查 Redis 快是因为**不需要任何网络往返**：一次 `ConcurrentHashMap.get` 是纳秒级的内存读取，而一次 Redis 调用要走 TCP、序列化、服务端处理，即使同机也要几十到几百微秒——差三个数量级。

### 14. 这个标记在什么时机被置位、什么时机被清除？补货或库存回补后如何处理？

**置位**：Redis `DECR` 返回值小于 0 时（说明库存已被扣穿），立即 `put(goodsId, true)`。

**清除**：只在这两个地方置回 false——应用启动预热时，以及调用 `/seckill/reset` 重置数据时。

**补货/库存回补【未实现】**：项目里没有补货接口，也没有库存回补逻辑；如果要做，标记必须在回补成功的同一处清掉，否则会出现"Redis 里明明有货，请求却被本地标记拦掉"的漏单。

### 15. 多实例部署时本地标记会不一致，A 实例售罄而 B 实例仍有库存的情况会发生吗？该怎么处理？

**会发生**，这是本地标记的固有代价。但影响是单向的、可接受的：这个标记只在"确认售罄"时置 true，所以 A 实例判售罄后只会让它自己少卖，**不会让它多卖**（正确性始终由数据库那条 `stock_count > 0` 的 UPDATE 保证）。如果要求多实例下售罄状态一致，三种做法：

① 把标记挪到 Redis（退回一次网络调用，优化意义消失）；

② 用 Redis 的 pub/sub 或消息广播让各实例同步置位；

③ 干脆去掉这一层，因为 Redis DECR 本身已经足够快。生产上我会选 ③ + 把 Redis 做成集群，把这一层留给"单个热点商品极端 QPS"的场景。

### 16. 标记变量用的是 volatile、AtomicBoolean 还是普通变量？在这里可见性与原子性哪个更关键，为什么？

用的是 **`ConcurrentHashMap`**（而不是 volatile 或 AtomicBoolean），因为标记是"按商品 ID 分组"的集合，不是单个布尔量。这个场景里**可见性和原子性都需要**：多线程并发 `put`/`get`，普通 `HashMap` 在并发写入时会有扩容竞态（可能丢数据甚至死循环）；而 `ConcurrentHashMap` 用 CAS + synchronized 桶保证了复合操作的安全与可见性。**这里我最初用的就是 `HashMap`，是本次修复的一个点。** 另外取值时要用 `Boolean.TRUE.equals(map.get(id))` 而不是直接赋给 `boolean`——`get` 返回 null 时自动拆箱会抛 NPE。

### 17. 本地标记与 Redis 库存不一致时，最终兜底在哪一层？会不会把本可成交的请求错误拦掉？

**兜底在数据库那一层**：`update seckill_goods set stock_count = stock_count - 1 where goods_id = ? and stock_count > 0`，只要这条件成立就一定不会超卖。**存在误拦的可能性**，分两种情况：

① 商品从未预热过 → `get` 返回 null，用 `Boolean.TRUE.equals` 判断后视为"未售罄"，不会误拦（这也是我把它从直接拆箱改成 `equals` 的原因之一）；

② 标记被错误置 true 之后库存又有回补 → 会误拦，目前只能靠 `/seckill/reset` 清除。

**取舍**：宁可少卖不可超卖，这个方向是对的，但要在文档里写清"回补必须清标记"。

### 18. 这个优化带来的实测收益是多少？有没有 QPS、响应时间或 Redis 请求量的前后对比数据？

**【未实现：没有做过前后对比。】** 诚实回答：我知道理论上它能省掉售罄后的 Redis 往返，但没有用压测量化过。

**能给的数字是**：本次并发验证中 30 个请求里有 20 个被判售罄，其中一部分是在第一级被短路的（由 `DECR` 变负置位标记后，后续请求不再访问 Redis）。**如果要补这个数据**，做法是把标记临时关掉，用同一份压测脚本跑两轮，对比 Redis 的 `INFO commandstats` 里 `decr` 的调用次数与 P99 响应时间——这是我可以补做的实验。

### 19. 如果要把"售罄标记"扩展成热点商品多级缓存（如 Caffeine/Guava），你会怎么设计？如何保证一致性？

设计思路：热点商品数据（商品详情、库存、活动状态）加一层 Caffeine 本地缓存，读路径变成"本地 → Redis → DB"，写路径在库存变更后**先更数据库、再删缓存**（Cache-Aside + 失效，不做更新缓存，避免并发写覆盖）。一致性用三层保证：

① 本地缓存设短 TTL（例如 1~3 秒）作为最终兜底；

② 库存扣减成功后在 Redis 上发一条失效通知（pub/sub），各实例收到后清掉自己的本地副本；

③ **正确性不依赖缓存**——扣减仍以数据库那条条件 UPDATE 为准，缓存不一致最多导致短暂的展示数字偏差，不会造成超卖。另外要做热点探测（按 goodsId 统计访问频次）只缓存真正的热点，避免全量缓存带来的一致性负担。

## C. Redis 预减库存（17 问）

> [!warning] 本组最容易被打穿的点
> 第 23、24、28、35 问分别是「对账、回补、持久化、故障注入」——这四件项目里都没做，先承认再讲方案。

### 20. Redis 预减库存用的是 DECR 还是 Lua 脚本？DECR 返回负数代表什么，你怎么处理？

用的是 **`DECR`**（`RedisService.decr`，底层 `jedis.decr`），不是 Lua。返回值小于 0 表示"库存已被扣穿"（注意：**不是等于 0**，因为并发下多个请求会同时扣到负数）——此时把本地售罄标记置位并返回 `500500 秒杀已结束`。这里有个重要认知：**这个负数没有意义，它不是"剩余库存"**。被拒绝的请求也已经执行过扣减了，所以并发结束后这个值会比 0 更小（实测见过 -3、-13、-18、-20）。它只是闸门，真实库存以数据库为准。

### 21. 库存 key 的名称、value 类型、过期时间是怎么设计的？为什么这样设计？

key 是 `GoodsKey:gs<goodsId>`（前缀由 `BasePrefix` 拼成 `类名:业务前缀`，所以完整形态是 `GoodsKey:gs1`）；value 是整数字符串，用 Redis 的 `DECR` 直接当计数器；**过期时间是 0，即永不过期**（`new GoodsKey(0, "gs")`）。不过期是刻意的：秒钟级的 TTL 一旦到期，计数器会被重置成"键不存在"，`DECR` 会从 -1 开始，导致本该有货的商品被判售罄；库存是业务状态而不是缓存，生命周期应该跟随活动，由 `/seckill/reset` 或活动结束后的清理来管。

### 22. Redis 中的库存什么时候写入（启动预热、定时刷新还是首次请求懒加载）？冷启动期间的请求会怎样？

**启动预热**：`SeckillController` 实现 `InitializingBean`，在 `afterPropertiesSet` 里把 `seckill_goods.stock_count` 逐个写进 Redis，同时把本地标记初始化成 false。**没有定时刷新，也没有懒加载兜底**。所以冷启动期间的问题很具体：

① 如果 Redis 里没有这个 key 而应用已经开始接流量，`DECR` 会把不存在的键当 0 处理、返回 -1 → 直接判售罄 → **这个商品会被错误地拒绝**；

② 应用启动时 Redis 不可达则整个服务起不来（`afterPropertiesSet` 抛异常会导致 Spring 上下文初始化失败）——这是实测过的行为。

**改进方向**：加"首次请求发现 key 不存在就从数据库加载"的懒加载兜底，并把预热失败降级为告警而不是启动失败。

### 23. Redis 库存与数据库库存的最终一致性如何保证？有没有对账或校准任务？

**【未实现：没有对账任务，也没有校准。】** 目前的一致性只靠两点性质维持：

① 数据库是权威（`stock_count` 是唯一的真实库存）；

② Redis 只是闸门——它被扣成负数也不影响正确性，因为最终判定的还是数据库那条带 `stock_count > 0` 的 UPDATE。

**但确实存在会偏离的场景**：消息投递失败或消费失败时，Redis 已经扣了、数据库没扣，两边就会不一致（表现为"少卖"）。

**该补的是**：一个定时对账任务，比对 `seckill_goods.stock_count` 与 `Redis 计数`，偏差超过阈值就告警并重建 Redis 计数（以数据库为准），而不是反向修数据库。

### 24. 预减成功但后续失败（消息投递失败、消费失败）时如何回补库存？回补会不会造成超卖？

**【未实现：没有回补机制。】** 这是当前设计的一个真实缺口：预减在 Redis 上成功了，但如果 MQ 投递失败（broker 挂了）或消费端处理失败，这份库存就"凭空消失"了——数据库没减，用户也没抢到，表现为少卖。

**为什么不回补**：因为回补本身有超卖风险——如果消费其实成功了、只是 ack 丢了，此时回补就会把已成交的库存再放出去。**正确的做法**是让回补幂等、并且只在确认失败的条件下执行：

① 消费端处理用"条件 UPDATE 的影响行数"判断是否真的减过库存；

② 补偿动作带上唯一键（订单号/消息 ID）做幂等；

③ 实在拿不准就走对账，由对账任务按数据库的权威值重建 Redis 计数，而不是做精确的 `INCR` 回补。

### 25. 判重与预减是两条独立命令，为什么不用 Lua 合并成原子操作？不合并会引发什么具体 bug？

**没合并是两个考虑**：

① 判重读的是 Redis 里的订单缓存（`OrderKey:soug<uid>_<goodsId>`），而订单的权威在数据库唯一索引上，所以"用 Lua 把判重和预减绑成原子"并不能真正消灭竞态——真正的防线不在这里；

② 改动最小化。

**不合并引发过的具体 bug 就是我修的那个顺序问题**：原来先 `DECR` 再判重，导致重复提交的用户**白扣掉一份 Redis 库存**（数据库里没有他的订单），结果是少卖加上提前售罄。**修复方式是把判重移到预减之前**——这能挡住绝大多数重复提交，但严格来说仍是两条命令、仍有极小窗口（同一用户的两次请求并发穿过判重）。**要做到严格原子**，应该用一段 Lua 同时判断"用户是否已抢过"和"库存是否足够"，两个 key 一起操作（同一个 Redis 实例上天然同 slot）。

### 26. 为什么不用分布式锁或 Redisson 信号量来管理库存？与 DECR 方案相比优劣如何？

**DECR 更轻且足够**：Redis 单命令本身是原子的，计数场景不需要"加锁-校验-释放"三步，少了两轮网络往返，也没有锁超时、锁误删、看门狗续期这一堆坑。分布式锁的优势是能做**复杂的临界区**（比如"校验 A 再校验 B 再写 C"要多步），而这里只有一个整数的加减。Redisson 的 `RSemaphore` 语义上更贴近"信号量=许可数"，能支持 `tryAcquire` 超时和公平性，但代价是引入 Redisson 依赖、许可数还要与数据库库存同步（又多了一个一致性面）。

**结论**：单一计数用 `DECR`；如果将来要支持"每人限购 N 件 + 库存 + 黑名单"这种多条件联合校验，我会用 Lua 而不是锁。

### 27. Redis 与 MySQL 之间的库存更新顺序是什么？你了解"先删缓存还是先更数据库"的经典争论吗，怎么选？

本项目的顺序是：**请求线程只减 Redis（预减）→ 消费线程减数据库**，两件事在不同线程、不同时间发生，不存在"同一次请求里先更谁"的问题——这是异步削峰设计带来的天然解耦。关于经典争论：那是**缓存与数据库双写一致性**的问题（缓存里存的是数据库某行的副本），主流结论是 **Cache-Aside + 先更数据库、再删缓存**（不是更新缓存），因为"先删缓存后更库"在并发下会出现"删了缓存、另一个请求读旧值回填"的窗口；而本项目的 Redis 存的不是数据库的副本、而是一个**独立的计数器/闸门**，属于"Redis 做流量前置判定、数据库做权威扣减"的分工模式，不能用双写一致性的套路去套。

### 28. Redis 的持久化配置是什么（RDB/AOF/everysec）？宕机丢数据会对库存造成什么影响，如何兜底？

**【未实现：没有做过持久化配置】**，用的是 Redis 默认（RDB 快照，未开启 AOF）。**宕机丢数据的影响**取决于丢多少：RDB 会丢最后一次快照之后的所有写入，也就是预减记录全部丢失、计数器回到快照时的旧值（比真实可用库存大）。后果是**可能放更多请求进入队列**（多卖的风险前移到 MQ 层），但**最终不会超卖**——因为数据库那条 `stock_count > 0` 的条件 UPDATE 仍然会把多余的请求挡掉，它们会在消费端 `reduceStock` 返回 0 时被判失败。

**如果要做更稳的设计**：Redis 开 AOF `everysec`（最多丢 1 秒）用于降低偏差；更重要的是**加对账**——Redis 只是闸门，允许它不准，但不能允许它长期偏离而没人知道。

### 29. 项目里的 Redis 是单机、主从哨兵还是集群？如果是单机，这个方案在真实高并发场景下的风险在哪？

**单机**（跑在一台 CentOS 7 虚拟机上，`bind 0.0.0.0`、`protected-mode` 开着但绑定地址是通配、16 个库、未配主从）。单机在真实高并发下的风险：

① **单点故障**——Redis 挂了整个秒杀入口不可用（本项目里应用启动都依赖它）；

② **单线程吞吐上限**——命令处理是单线程的，虽然能到十万级 QPS，但热点 key 全打在一个实例上时网络与 CPU 会成为瓶颈；

③ **数据无副本**——宕机丢数据（见第 28 问）；

④ **内存无上限**——实测该实例 `maxmemory 0`、`maxmemory-policy noeviction`，内存写满会直接报错而不是淘汰。

**改造方向**：先做主从 + 哨兵（解决单点），热点商品用本地缓存 + hash tag 分散。

### 30. 热点商品 key 在 Redis 集群下会集中打到一个节点，你了解热点 key 的解法吗？本项目怎么处理？

**了解，但本项目是单机、不存在分片问题**。热点 key 的解法：

① **本地缓存前置**（本项目已有本地售罄标记，属于这一类的最简形态）；

② **key 打散**——把 `stock` 拆成 N 个分片 key（`stock:1:1` … `stock:1:N`），请求按 userId 取模分散到不同分片，总库存 = 各分片之和（代价是可能某分片先空、需要借用逻辑）；

③ **读写分离**——写走主、读走从；

④ 热 key 探测（客户端统计 + 上报）后动态加本地缓存。

**取舍**：打散方案会牺牲"精确的剩余库存展示"，所以更适合"只要不超卖、不需要精确数字"的场景。

### 31. Redis 事务、Pipeline、Lua 分别适合什么场景？你在项目中分别用到了哪些？

**本项目三个都没用到**，只用了单命令（`GET/SET/SETEX/DECR/INCR/EXISTS` 和 SCAN 批量删除）。适用场景分别是：**事务（MULTI/EXEC）**——需要一组命令连续执行、中间不插入其他客户端命令，但它不是原子回滚语义（命令语法错误才整体不执行，运行期错误无法回滚），本项目不适合；**Pipeline**——批量命令减少 RTT，适合"一次请求要发很多条不相关命令"，本项目单次请求只有 1~2 条命令，用不上；**Lua**——需要"读-判断-写"原子化时才是正解，本项目第 25 问提到的"判重 + 预减"合并、以及第 74 问提到的"限流计数 INCR+EXPIRE 原子化"就该用它，**这两处是我明确知道该改但还没改的地方**。

### 32. 有没有实现"每人限购 N 件"？如有，如何在 Redis 中原子地校验并扣减？

**【未实现】**：当前是"一人一单"，靠 `seckill_order` 上的 `(user_id, goods_id)` 唯一索引保证。如果要做每人限购 N 件，Redis 侧的正确做法是用 Lua 把三件事绑成一次原子操作：`GET 用户已购数 → 判断 < N → INCR 用户已购数 → DECR 库存 → 判断库存 >= 0`，任一条件不满足就整段回滚语义（Lua 里通过返回不同状态码让调用方区分"库存不足/超出限购"）。数据库侧对应地把唯一索引改成 `(user_id, goods_id, seq)` 这种带序号的形式，用 `seq` 支持多件。

### 33. 缓存穿透、击穿、雪崩分别对应本项目中的什么场景？你做了哪些防护？

**穿透**（查不存在的数据）——本项目对应"查一个不存在的 goodsId"，会造成每次请求都落到数据库；**现状：没有专门防护**，接口对不存在的商品会返回"商品不存在"（`AiToolKit` 里显式判空），但商品详情接口没有空值缓存。**击穿**（热点 key 过期瞬间）——本项目**恰好规避了**这个问题，因为库存 key 刻意永不过期，不会出现"过期瞬间大量请求打到数据库"。**雪崩**（大量 key 同时过期）——本项目 Redis 里只有库存计数和少量缓存键，页面缓存 TTL 统一 60 秒但没有集中失效压力；**现状防护有限**，主要靠"数据库那条条件 UPDATE 是权威"这一点保证即使缓存全失效也不会超卖（只会慢）。

**该补的**：空值缓存 + 合理随机化 TTL。

### 34. 有没有遇到过库存 key 未设置 TTL 或数据残留的问题？如何避免预减数据与真实库存长期偏离？

**库存 key 是刻意不带 TTL 的**（见第 21 问），所以"未设置 TTL"是设计而不是 bug。

**数据残留的风险确实存在**：`/seckill/reset` 会重置数据库库存并把 Redis 计数写回 10，但如果只清了数据库、没清 Redis，Redis 就会长期提供一个偏大的闸门值。

**当前避免偏离的手段**：

① 应用启动预热会按数据库值覆盖 Redis；

② `/seckill/reset` 同时更新两边；

③ 数据库是权威，Redis 偏大也不会超卖（多余请求会在消费端被判失败）。

**该补的**：对账任务 + 对账偏差告警（同第 23 问）。

### 35. 你如何验证 Redis 层逻辑的正确性？有没有做过故障注入（如手动删除库存 key、模拟 Redis 超时）？

**做过的是**：

① 端到端验证里直接读 Redis 校验 key 的存在与取值（比如断言 `GoodsKey:gs1` 存在且是整数、`SeckillKey:verifyCode...` 的验证码答案与图片一致、`AiChatKey:session...` 的会话条数与 TTL）；

② 并发测试后核对 Redis 计数与数据库库存的偏差，确认"Redis 可为负、数据库不为负"这个设计特征。**【未实现：故障注入没做过】**——没有删除库存 key、没有模拟 Redis 超时或重启。

**该补的**：

① 手动 DEL 库存 key 后发请求，验证"冷启动被判售罄"这个缺陷；

② `redis-cli DEBUG SLEEP` 或防火墙丢包模拟超时，验证应用的失败行为（目前是抛异常 → 用户看到 500）；

③ Redis 重启后重建计数的演练。

### 36. Redis 客户端用的是 Lettuce 还是 Jedis？连接池参数怎么配？压测时出现过连接耗尽或超时吗？

用的是 **Jedis**（裸用，不是 spring-data-redis），版本随 Spring Boot 1.5.10 带来（2.9.x），通过 `RedisPoolFactory` 手工构造 `JedisPool`。连接池参数本地配置为 `poolMaxTotal=100`、`poolMaxIdle=50`、`maxWait=3秒`、超时 10 秒。**30 并发下没有出现连接耗尽或超时**（池子 100 条远超需求）。

**需要说明的两点**：

① 原来提交进仓库的配置是 `maxTotal=1000`（那台公网服务器上的值），本地化时改小了；

② `maxWait` 原来配的是 500（而这个值在 `RedisPoolFactory` 里会被乘 1000 当作毫秒，也就是最长阻塞 **500 秒**），本地改成了 3 秒——这类"单位被乘了但值没改"的坑值得记住。

## D. 数据库原子 UPDATE 兜底（10 问）

> [!warning] 本组最容易被打穿的点
> 第 40 问（行锁竞争有多激烈）与第 43 问（隔离级别）——项目里默认 RR、没做过锁等待观测，别编数字。

### 37. `UPDATE ... SET stock_count = stock_count - 1 WHERE id = ? AND stock_count > 0` 为什么能防止超卖？它依赖数据库的什么机制？

依赖 **InnoDB 的行级排他锁 + 条件更新的原子性**。执行这条 UPDATE 时，InnoDB 会对匹配到的行加 X 锁，且"读取当前值 → 判断条件 → 更新"这一系列动作在锁保护下完成，其他事务必须等锁释放。所以即使 100 个事务同时来，也会被串行化：前面的事务把 `stock_count` 减到 0 之后，后面事务再拿到锁时 `stock_count > 0` 不再成立，UPDATE 影响行数为 0，直接失败。**关键点是"条件写在 UPDATE 的 WHERE 里"**，而不是"先 SELECT 再判断再 UPDATE"——后者在两次操作之间有窗口，一定超卖。

### 38. 既然数据库兜底是正确的，前面两层是否多余？如果去掉 Redis 只留数据库，性能上会发生什么？

**不多余**，它们解决的不是"正确性"而是"承载能力"：数据库兜底保证了不出错，但**每个请求都要去抢那一行的锁**。去掉 Redis 只留数据库会发生什么：

① 所有请求（包括注定失败的）都占用一条数据库连接，连接池（本地配 20）会瞬间打满，后续请求连不上数据库直接报错；

② 那一行的 X 锁被反复争抢，事务排队等待，`innodb_row_lock_waits` 飙升、响应时间从毫秒涨到秒级；

③ 大量 UPDATE 产生 binlog 与 redo 写入，磁盘 IO 成为瓶颈。

**一句话**：数据库能保证不超卖，但它的吞吐是每秒千级，而秒杀入口的流量是每秒万级——Redis 和 MQ 的作用就是把这两个数量级之间的落差吃掉。

### 39. UPDATE 影响行数为 0 时业务如何响应？用户看到的提示是什么？如何区分"售罄"与"重复下单"？

`GoodsService.reduceStock` 返回 `ret > 0` 的布尔值，为 false 时 `SeckillService.seckill` 调用 `setGoodsOver(goodsId)`（在 Redis 写 `SeckillKey:go<goodsId>`）并返回 null，也就是**这次秒杀失败**。用户侧：前端在轮询 `GET /seckill/result`，`getSeckillResult` 查到 `isGoodsOver` 存在就返回 **-1**，前端提示"对不起，秒杀失败"。

**区分售罄与重复下单**：重复下单在**入口就被拒绝**（判重读 Redis 订单缓存命中，返回 `500501 不能重复秒杀！`），根本不会走到消费端，所以用户看到的是明确的"不能重复秒杀"；而 -1 是"没抢到"。两者在 API 层用不同 code 区分。

### 40. 高并发下这条 UPDATE 的行锁竞争有多激烈？有没有出现锁等待、超时或死锁？如何优化？

**在本次验证规模（30 并发）下没有观测到锁等待、超时或死锁**——最终的失败都是"条件不满足、影响行数 0"，不是等锁超时。原因有两层：

① Redis 预减已经把并发压到很低（30 个请求里只有 10 个真正到数据库），② 这些请求经 MQ 异步串行化后，实际并发写数据库的只有 `prefetch=1` 下的少数消费者。**【未实现：没有做锁竞争的量化观测】**（没查 `innodb_row_lock_waits`、没看 `SHOW ENGINE INNODB STATUS`）。

**要观测的话**：`SHOW STATUS LIKE 'Innodb_row_lock%'` 看等待次数与平均等待时间，或者开 `performance_schema` 看锁等待直方图。

**优化方向**：消费端并发数不要盲目调大（本项目 `prefetch=1`，把写数据库的并发压到最低，用吞吐换稳定性）；真要提吞吐，正确方向是"分段库存"（把一行的竞争拆成 N 行）而不是加锁。

### 41. 减库存与插入订单是否在同一个事务中？事务边界放在服务方法里还是 MQ 消费端？

**在同一个事务里**。`SeckillService.seckill` 标了 `@Transactional`，它内部先调 `goodsService.reduceStock`（减库存），成功后再调 `orderService.createOrder`（写 `order_info` + 写 `seckill_order` + 回写 Redis 缓存），两个操作在同一个事务中——这是必须的：如果减了库存但订单没写成功又不回滚，就变成了"库存少了、单子没生成"的少卖。**事务边界在 service 层**（`SeckillService`），MQ 消费端（`MQReceiver`）只是事务的**发起方**：它做前置校验（库存、重复订单），校验通过才调用 service 那个事务方法。

**边界为什么这么划**：消费端的前置查询是只读判断，不需要进事务（甚至应该避免长事务）；真正需要原子性的只有"减库存 + 写订单"这一对写操作。

### 42. 减库存成功而订单插入失败时怎么回滚？回滚是否会释放已被合理占用的库存，从而影响其他用户？

靠 Spring 的声明式事务回滚：`createOrder` 抛异常（比如唯一索引冲突）会让整个 `@Transactional` 方法回滚，**减库存那一步也一起撤销**。会不会影响其他用户：**不会造成问题，只会让这次请求失败**。因为 InnoDB 的行锁一直持有到事务结束，其他事务在锁释放前后拿到的都是自洽的值；回滚把 `stock_count` 恢复原值，等于这份库存重新可售，下一个请求可以正常抢到——**这不是"超卖"，而是"这份库存刚才没卖出去、现在继续卖"**。要注意的是**回滚会拉长锁持有时间**，所以事务里不应该有任何慢操作（远程调用、发消息、写日志），这也是本项目把 MQ 投递放在事务外（请求线程里做）的原因。

### 43. 数据库隔离级别用的是哪一级？在并发消费场景下有没有遇到不可重复读、幻读或锁冲突？

用的是 **MySQL 默认的 RR（可重复读）**，项目里没有显式修改。**没有遇到不可重复读、幻读或锁冲突**，原因很具体：

① 本项目在事务里只做"按主键/唯一键定位一行然后更新"，读的是**唯一索引的等值条件**，InnoDB 在这种条件下加的是记录锁（record lock）而不是间隙锁，天然不会产生幻读问题；

② 没有"先查一批、再写一批"的范围操作。

**需要澄清的一个常见追问**：RR 下的快照读（普通 SELECT）与当前读（`UPDATE`/`SELECT ... FOR UPDATE`）行为不同——本项目的 UPDATE 是当前读，读的是最新已提交版本，这正是它作为"兜底正确性"的基础。

### 44. 唯一索引 (user_id, goods_id) 意味着"一人一单"，如果业务变成"每人限购 3 件"或"退款后可重新购买"，索引与逻辑应如何调整？

**每人限购 3 件**：唯一键要能容纳多行，改成 `(user_id, goods_id, seq)`，`seq` 取 1/2/3——插入时按当前已购数计算 seq，靠唯一索引保证并发下不会插入两条相同 seq；或者更简单：保留一人一行、加一个 `buy_count` 列，改成"条件 UPDATE 累加 + 判断 < 3"（配合 Redis 的原子计数更好）。

**退款后可重新购买**：矛盾在于"要保留历史记录"和"允许再次购买"不能用同一个唯一键表达。两种做法：

① 唯一键带上状态或"有效标记"（例如 `(user_id, goods_id, is_valid)`，退款后把旧记录的 `is_valid` 置 0），代价是同一用户有效期内只能有一条；

② 干脆去掉这个唯一索引，改用**幂等表**（记录 `(request_id)` 或 `(user_id, goods_id, 批次)`）来控制"同一个批次只能买一次"，把"是否允许再买"交给业务状态机判断。

**取舍点**：唯一索引是"物理约束、最可靠但最死板"，业务规则一复杂就该往幂等表 + 状态机迁移。

### 45. "库存与订单数守恒"你是怎么验证的？有没有写对账 SQL、定时校准或异常告警？

**验证方式**：并发测试结束后用 SQL 直接查三件事并做断言——① `seckill_goods.stock_count` 的值；

② `seckill_order` 里该商品的行数；

③ `order_info` 里该商品的行数。断言是 `stock_count + 订单数 = 初始库存`，以及两张订单表行数一致。实测 30 并发抢 10 件的结果是 `stock_count=0`、两张表各 10 行、`0 + 10 = 10` 守恒。**【未实现：没有定时对账、没有告警】**——对账 SQL 只存在于验证脚本里、只在压测后跑一次。要做成生产级的：把这条 SQL 变成定时任务（比如每分钟跑一次，只扫当天活动商品），偏差超过阈值就告警；同时加"订单数 > 初始库存"这种绝对错误的硬告警。

### 46. 除唯一索引外，数据库层面还有没有其他约束（非负检查、状态约束）？MySQL 8.0 的 CHECK 约束你了解吗？

**项目里没有用 CHECK 约束**，字段上只有 `DEFAULT` 和 `NOT NULL`。了解 MySQL 8.0.16 起**真正支持了 CHECK 约束**（8.0.16 之前会解析但忽略），所以现在可以写 `CHECK (stock_count >= 0)` 来把"库存不能为负"变成数据库层的硬约束——这对本项目是有价值的补充，因为它能把"某个 bug 导致库存被减成负数"这类问题在写入时就拦下来（当前只能靠条件 UPDATE 的逻辑正确性）。另外值得加的还有：`status` 字段的取值约束（`CHECK (status IN (0,1,2,3,4,5))`）、金额字段的 `CHECK (goods_price >= 0)`。

**但要注意**：CHECK 只在写的时候校验，不能替代业务层的并发控制——它防的是"逻辑写错"，防不了"并发超卖"（超卖要靠条件 UPDATE）。

**为什么本项目没加**：表结构是从项目初始化就定下的，加约束需要评估存量数据是否满足条件（比如历史订单里有没有不合法的 status）。

## E. 重复下单防护与缺陷修复（12 问）

> [!warning] 本组提示
> 本组是简历亮点区，也是最容易被深挖的地方（第 50 题会直接问到你修的那个 bug）。原则：讲清"不报错但结果错"这个特征 + 讲清你怎么让它暴露。

### 47. Redis 判重的 key 如何命名？带不带商品维度？过期时间设置多久，依据是什么？

key 是 `OrderKey:soug<userId>_<goodsId>`（前缀 `OrderKey:soug` 由 `BasePrefix` 拼出，业务键是 `userId + "_" + goodsId`）。**带商品维度**，因为语义是"这个用户对这个商品是否已经抢到过"——一个用户完全可以抢不同商品。

**过期时间为 0，永不过期**：这份记录是"订单存在"的伴随状态，订单在它就该在；如果设了 TTL，一旦过期就会放行重复下单，而数据库层虽然能兜住（唯一索引），但会把错误延迟到更深的层次暴露。

**代价**：需要显式的清理时机（`/seckill/reset` 会清），否则测试数据会残留。

### 48. 判重使用什么命令？返回值如何判定为"重复请求"？会不会误杀正常请求？

用的是 **`GET`**（不是 `SETNX`）：`redisService.get(OrderKey.getSeckillOrderByUidGid, userId + "_" + goodsId, SeckillOrder.class)`，反序列化后非 null 即判定为"已经抢到过"，返回 `500501 不能重复秒杀！`。

**为什么用 GET 不用 SETNX**：这条记录是"订单已创建"的**结果缓存**，它的写入时机是订单创建成功后（在 `createOrder` 里回写），所以读操作应该是被动的查询；用 SETNX 去"占位"反而会在订单创建失败时留下错误的占位记录。

**会不会误杀**：不会——同一个用户对同一个商品本来就是只允许一单，命中即拒绝是正确行为。

### 49. 请完整讲一遍"Redis 判重 + 数据库唯一索引"的双重防护链路，并说明各自在什么情况下会失效。

**链路**：请求进入 → 查 Redis `OrderKey:soug<uid>_<gid>`（命中即拒）→ 通过则预减库存、投递 MQ → 消费端**再查一次**（`MQReceiver` 里同样调 `getSeckillOrderByUserIdGoodsId`，防的是"两次请求都穿过了入口判重"的并发窗口）→ 事务里减库存 + 写 `order_info` + 写 `seckill_order`（**这一步受唯一索引约束**）→ 写完后回写 Redis 缓存。

**Redis 判重的失效场景**：

① Redis 被清空、重启或数据丢失；

② key 未设置成功（比如写入时 Redis 抖动）；

③ 两个请求并发穿过判重（先查后写之间没有原子性）。

**唯一索引的失效场景**：几乎没有——它是物理约束，任何插入路径都绕不过去；唯一"失效"的情况是这个约束没建（**这正是项目原来的状态，是我加上去的**）。

**核心认识**：Redis 是"加速判断"，唯一索引是"正确性保证"；把正确性寄托在缓存上是最常见的错误。

### 50. 你提到在压测中修复了一处"让去重机制静默失效"的缺陷，它的技术根因是什么（并发时序、异常吞没、key 写错还是 Lua 逻辑错误）？请复述定位过程。

**根因既不是并发时序也不是异常吞没，而是"写错了数据"**：`OrderService.createOrder` 里创建秒杀资格记录时，把用户 ID 写成了硬编码的字面量 `1L`：

```java
SeckillOrder seckillOrder = new SeckillOrder();
seckillOrder.setOrderId(orderInfo.getId());
seckillOrder.setUserId(1L);        // ← 应该是 seckillUser.getId()
seckillOrder.setGoodsId(goods.getId());
orderDao.insertSeckillOrder(seckillOrder);
```

**为什么"静默"**：

① 不报错——`1L` 是合法值，插入成功；

② 现有代码路径下**看不出问题**——`OrderService.getSeckillOrderByUserIdGoodsId` 实际上只读 Redis 缓存，而缓存那一行用的是**正确的** `seckillUser.getId()`（`redisService.set(..., "" + seckillUser.getId() + "_" + goods.getId(), seckillOrder)`），所以正常流程判重是好的；

③ 但它让**数据库层的二次判重彻底失效**——`MQReceiver` 里那句"再查一次重复订单"以及按 `(user_id, goods_id)` 的查询，对除 1 号用户之外的所有人都永远查不到记录。

**具体触发条件**：一旦 Redis 缓存丢失（重启、被清空、或走 `/seckill/reset`），去重就只剩这一层已失效的数据库判断，用户可以重复秒杀同一商品。

**定位过程**：并压测后我没有只看接口返回，而是直接查数据库核对——`select user_id from seckill_order` 发现所有记录的 `user_id` 都是 `1`，而参与压测的用户 ID 是 `13000000010` 之类的，两者对不上，顺藤摸到 `createOrder`。

**修复**：改成 `seckillUser.getId()`，并在 `seckill_order` 上补了 `UNIQUE KEY uk_user_goods (user_id, goods_id)` 作为数据库层的硬兜底。

### 51. "静默失效"意味着不报错但结果错误，你是如何让它暴露出来的？用了哪些工具或手段？

**靠的是"不信任接口返回、直接校验数据源"**。具体手段：

① 压测后**直接查数据库**（mysql 客户端跑 SQL），核对 `seckill_order.user_id` 与参与压测的用户 ID 是否一致——这一步是发现问题的关键，如果只看 HTTP 响应码和订单数，一切"正常"；

② **守恒校验**：断言 `stock_count + 订单行数 = 初始库存`，以及两张订单表的行数是否相等；

③ **唯一性校验**：`select user_id from seckill_order group by user_id having count(*) > 1` 查有没有重复用户。

**方法论**：静默失效的 bug 只能靠"对数据本身做断言"来发现，不能靠"看有没有异常"——所以我把这些断言写成了可重复执行的验证脚本，而不是靠手工点页面。

### 52. 修复后你如何证明去重确实生效？有没有留下可重复执行的复现用例或回归测试？

**有，是一份可重复执行的验证脚本**（27 项断言，覆盖端到端链路 + 并发场景），其中和去重直接相关的有三条：

① 单用户重复秒杀被拒绝——同一用户连续两次提交，第二次必须返回 `500501`；

② `seckill_order.user_id` 记录的是真实用户——直接查库断言 `user_id = 13000000000`；

③ 并发后无重复下单——30 个并发用户抢完，`group by user_id having count(*) > 1` 的结果必须为 0。

**关于"唯一索引兜底是否真的生效"**：它的验证思路是"即使应用层判断失效，插入也会冲突"——我验证的是唯一索引确实存在（`show index from seckill_order` 有 `uk_user_goods`）以及并发后无重复数据。**【未实现：没有写成 JUnit 单元测试】**，脚本是仓库外的 PowerShell 文件（`verify-seckill.ps1`），需要手动执行——这是我列在待补清单里的事。

### 53. 判重 key 在请求失败后是否需要删除？如果不删除，用户要被锁死多久？这个体验问题怎么权衡？

**不需要删除，也不会锁死用户**——关键在于这个 key 的语义：它**不是"请求占位"，而是"订单已存在的标记"**，只在订单创建成功后才写入。所以写失败/秒杀失败的路径根本不会写它，也就没有"失败要清理"的问题。

**对比一下另一种常见设计**：如果用 `SETNX` 在请求入口就占位（比如 `order_lock:uid_gid`），那失败时就**必须**清理或设短 TTL，否则用户被锁死；而本项目的顺序是"先在数据库把订单真正建出来，再回写缓存标记"，天然规避了这个坑。

**体验上的唯一代价**：用户抢成功后就被永久拒绝再次购买（这是业务规则，不是缺陷）；如果将来支持退款后重购，就需要在退款成功后**主动删除这个 key**——这是新业务带来的清理义务。

### 54. 同一用户多设备并发提交、同一 IP 多用户提交时，各自会表现如何？你的防护维度是什么？

**同一用户多设备并发**：判重维度是 `userId`（来自 token），与设备无关，所以两台设备同时提交时——Redis 判重可能被同时穿过（先查后写非原子），但消费端的二次判重和数据库唯一索引会兜住，结果是**只有一单成功，另一单在 `reduceStock`/插入处失败**。用户看到的是"一单成功 + 一单失败"。

**同一 IP 多用户提交**：**本项目没有 IP 维度的防护**——限流的维度是"用户 + URI"（`@AccessLimit` 的 key 是 `requestURI + "_" + userId`），锁定的是登录用户。所以同一个 IP 上的多个账号可以各自正常参与（这在业务上是合理的）。**如果要做 IP 维度**（防同一台机器开一堆小号），要注意 NAT 会让大量正常用户共用一个出口 IP、`X-Forwarded-For` 可伪造——所以 **IP 只能作为风控的弱特征**，通常配合设备指纹、账号年龄、行为序列一起打分，而不是直接按 IP 限流。

### 55. RabbitMQ 是至少一次投递语义，消费端如何保证重复投递不会生成重复订单？幂等键选的是什么？

**幂等键是 `(user_id, goods_id)`**，靠三层保证：

① 消费端入口先查 Redis 订单缓存，命中直接 return；

② 减库存用条件 UPDATE（`stock_count > 0`），库存为 0 时影响行数 0、直接结束；

③ **最关键的一层**——写 `seckill_order` 时受唯一索引 `uk_user_goods` 约束，重复投递会在插入时抛 `DuplicateKeyException`，事务整体回滚，不会产生第二条订单。

**为什么选 `(user_id, goods_id)` 而不是消息 ID**：因为业务语义本身就是"一人一商品一单"，用业务唯一键做幂等比用消息 ID 更贴合（消息 ID 只能防"同一条消息重复消费"，防不住"用户重新发起了请求"这种跨消息的重复）。

**要补充的一点**：当前消费端是**自动 ack**（没有手动 ack），所以"消费成功但 ack 丢失"会触发重投，正好由上面的唯一索引兜住——这正是幂等设计的价值。

### 56. "重复提交被稳定拒绝"——拒绝发生在哪一层？返回的提示信息会不会泄露系统内部状态？

**拒绝发生在应用入口层**（`SeckillController.seckill` 里的判重查询），返回 `{"code":500501,"msg":"不能重复秒杀！"}`——**HTTP 状态码仍是 200**，靠响应体里的 `code` 区分。

**不泄露内部状态**：所有对外错误都走 `CodeMsg` 里的固定文案（`500501`、`500500`、`500102 请求非法！`、`500103 请求过于频繁`），异常统一被 `GlobalExceptionHandler` 兜住并转成 `{"code":500100,"msg":"服务端异常！"}`，**原始异常堆栈只打到服务端日志、不返回给客户端**——这一点很重要，否则 SQL 报错信息会暴露表结构。

### 57. 极端时序：判重通过 → 预减成功 → 用户取消或超时未支付，这段状态如何回收？有没有遗漏的窗口？

**【未实现：没有做未支付超时关单，也没有库存回补。】** 这是当前设计里明确的缺口，窗口是真实存在的：预减在 Redis 上扣掉了一份库存、消息也入队了、订单也建出来了，但用户一直不支付——订单会永久停留在 `status=0`（新建未支付），那份库存也不会回到池子里。

**要做的话分两件事**：

① **关单**——用 RabbitMQ 的 TTL + 死信队列（下单时投一条延迟 15 分钟的消息，到期消费时检查订单状态，仍是未支付就关单）。这里要注意**不能用定时扫全表**，必须按"订单过期时间 + 状态"建索引；

② **回补**——关单成功后把库存加回数据库，并且**同一次操作里把 Redis 计数也加回去、清掉对应商品的本地的售罄标记**（否则会出现"数据库有货但被本地标记拦掉"的漏单）。

**为什么本项目没做**：它属于完整的交易闭环（支付、超时、退款），超出了"库存扣减"这个核心问题；但面试时应该主动说明这个窗口存在，附上方案——**能说清"缺什么、为什么缺、怎么补"比假装完整更安全**。

### 58. 如果重新设计去重方案，你会如何组合 Redis+Lua、唯一索引、状态机或幂等表？

重新设计会分四层，各管一件事：

① **入口层（Redis + Lua）**——用一段 Lua 原子完成"判断用户是否已抢过 + 判断库存是否足够 + 扣减 + 记录用户占位"，把第 25 问说的那个极小并发窗口彻底消掉，同时用一个短 TTL 的占位 key 表达"处理中"状态；

② **可靠性层（MQ + 幂等表）**——消息投递带唯一的 `request_id`，消费端先往幂等表插入 `request_id`（唯一约束），插入成功才继续处理，这是"消息级幂等"，与本项目的"业务级幂等"互补；

③ **正确性层（数据库唯一索引）**——保留 `(user_id, goods_id)`（或扩展成带 seq 的形式）作为不可绕过的物理约束；

④ **状态层（订单状态机）**——显式定义 `待支付 → 已支付 / 已取消` 的合法流转，用"条件 UPDATE + 原状态条件"保证状态流转的幂等（`update ... set status=已取消 where id=? and status=待支付`，影响行数 0 说明已被别人改过）。

**分层原则**：不指望任何单点绝对可靠，而是让每一层各自负责一个失效场景——Lua 防并发窗口、幂等表防重复消费、唯一索引防逻辑写错、状态机防非法流转。

## F. RabbitMQ 异步削峰（13 问）

> [!warning] 本组最容易被打穿的点
> 第 63–70 问涉及 ack 模式、publisher confirm、堆积监控、重试策略——这些项目里配得很粗（自动 ack、无死信、无限重试），要主动讲出风险。

### 59. 交换机类型、队列数量、路由键命名是怎么设计的？为什么这样划分？

**只有一个队列 `seckill.queue`（durable），没有自定义交换机**——用的是 RabbitMQ 默认的 direct exchange，routing key 就是队列名，所以本质是"点对点"的最简模型。命名上按"业务域.用途"：`seckill.queue`。

**为什么这么简单**：秒杀下单是一条单一的处理链，没有"按商品/按区域分流"的需求，也没有多消费者组各自关注的场景（topic/fanout 的用武之地），所以一个队列足够。

**补充说明**：项目里原来还声明了 direct/topic/fanout/headers 四套演示用的交换机和队列（`queue`、`topic.queue1/2`、`header.queue`、`topicExchage` 等），但没有任何生产者或消费者在用，我在整理阶段把它们删掉了，只保留真正使用的 `seckill.queue`，同时把 broker 上残留的 4 个空队列和 3 个交换机也清理了。

### 60. 消息体包含哪些字段？为什么不做大消息？消息体里有没有敏感信息或可以精简的内容？

消息体是 `SeckillMessage { SeckillUser seckillUser; long goodsId; }`，用 fastjson 序列化成 JSON 字符串投递。**消息很小**（几百字节），只带完成异步下单必需的上下文——大消息会占用 broker 内存、增加网络传输，而消费端真正需要的商品信息可以在消费时按 `goodsId` 查库（避免消息里的数据过期）。

**⚠️ 这里有一个我明确知道的问题**：消息体里塞的是**整个 `SeckillUser` 对象，它包含 `password`（密码摘要）和 `salt` 字段**——而 `MQSender`/`MQReceiver` 原来会把整条消息打进日志（`log.info("receive message:" + message)`），等于每次秒杀都把用户的密码摘要和盐写进日志。**我已经修复了日志泄漏**（改成只打 `goodsId` 和 `userId`），但**消息体本身仍然冗余**——更好的做法是消息里只传 `userId`（消费端需要用户信息时再查，或者只查昵称等非敏感字段），这样既减小了消息体积，也从根上消除了敏感字段的流转。这是我可以主动说的改进点。

### 61. "校验通过即投递并返回排队中"——这里的校验包含哪些步骤？校验、预减、投递三步的先后顺序为什么这样排？

校验共三步：

① **秒杀路径校验**（`checkPath`，拿请求里的 path 与 Redis 里存的该用户该商品的 path 比对）；

② **本地售罄标记**（`Boolean.TRUE.equals(localOverMap.get(goodsId))`）；

③ **重复下单校验**（查 Redis 订单缓存）。然后才预减库存，最后投递。

**顺序的关键点在于"判重必须在预减之前"**：原来的实现是先预减再判重，导致重复提交的用户**白扣掉一份 Redis 库存**（数据库里没有他的订单），结果是少卖加提前售罄——这是本次修复的一个真实缺陷。

**路径校验为什么放最前**：它最便宜（一次 Redis 读）且能挡住"不知道地址盲目压接口"的脚本，让后面的逻辑不被打扰。

**投递放最后**：只有前面都通过、且库存确实预减成功，才值得占用 MQ 的资源。

### 62. 客户端轮询结果接口是怎么设计的（查 Redis 还是查库）？轮询频率与超时策略是什么？为什么不用 WebSocket/SSE/长轮询？

`GET /seckill/result` **只查 Redis，不查库**（`getSeckillResult`：先查订单缓存，命中返回 orderId；否则查 `SeckillKey:go<goodsId>` 是否售罄，是则返回 -1；否则返回 0 表示还在排队）。

**这个设计很关键**：轮询是高频接口（客户端会反复调用），必须做到零数据库压力。**前端轮询间隔是 50ms**（`setTimeout(..., 50)`）——**⚠️ 这里有一个真实的冲突**：该接口上有 `@AccessLimit(seconds=5, maxCount=5)`，也就是 5 秒内最多 5 次，而 50ms 的间隔在 5 秒内会发出 100 次，**注定会触发限流**；更糟的是前端回调只处理 `data.code == 0`，收到限流错误码时什么都不做，轮询会静默中断、用户永久卡在 loading 遮罩上。**我在写验证脚本时正是因为这个限制把间隔改成了 1.5 秒才能取到结果**——这是实测发现的，不是推测。

**为什么不用 WebSocket/SSE**：秒杀结果是一次性的（成功/失败/还在排队），不需要服务端主动推；轮询实现最简单、无连接维持成本。如果要优化，**SSE 是更合适的替代**（比 WebSocket 轻、天然支持服务端推送），我这次在 AI 助手模块里就是用 SSE 实现的流式推送。

### 63. 消费端的并发消费者数、prefetch、手动/自动 ack 分别如何配置？依据是什么？

配置是 `concurrency=10`、`max-concurrency=10`、`prefetch=1`、**自动 ack**（没配手动 ack），另外 `default-requeue-rejected=true`。

**依据**：10 个并发消费者是为了让"减库存 + 写订单"这个写操作有一定并行度；`prefetch=1` 是刻意压到最低——它意味着**每个消费者手上同时只有 1 条未 ack 的消息**，单消费者内不会积压，配合多个消费者反而能更均衡地分摊（RabbitMQ 会把消息轮询给空闲消费者）；更深一层的原因是**降低数据库行锁的并发度**（第 40 问）。

**⚠️ 自动 ack 的风险要说清**：`acknowledge-mode` 默认是 auto，Spring AMQP 在"监听方法没有抛异常"时提交 ack——也就是**消费成功但 ack 丢失（网络抖动）会导致消息重投**（这由唯一索引幂等兜住）；反过来，如果监听方法里捕获了异常没往外抛，消息会被认为处理成功而丢失。生产上更稳的是手动 ack + 明确的异常处理策略。

### 64. 生产端、Broker、消费端三个环节的消息丢失你分别怎么防？用了 publisher confirm 还是事务？

**诚实说：三端都防得不完整。** 生产端：只配了**发送重试**（`spring.rabbitmq.template.retry` 开启、初始间隔 1 秒、最多 3 次、最大间隔 10 秒），**没有开 publisher confirm、没有用事务**——所以"消息发出去但 broker 没收到"这种情况会静默丢消息（表现为用户预减了库存却永远等不到订单）。Broker 端：队列声明为 `durable`（持久化队列），但**消息本身没有设置 delivery mode=2（持久化消息）**，broker 重启可能丢消息。消费端：自动 ack，见第 63 问。

**该补的**：

① 生产端开 `publisher-confirms`（异步回调模式，性能损耗小）并记录未确认消息；

② 消息设为 persistent；

③ 消费端手动 ack + 死信队列兜住处理失败。

**为什么原来没配**：这套参数沿用了参考实现的默认值，我在本地化时只改了连接信息——这是我的疏漏，不是有意取舍。

### 65. 路由失败（return 回调）有没有处理？什么配置下会出现消息无法路由？

**【未实现：没有处理 return 回调。】** 什么情况下会出现无法路由：

① 发送时指定了 exchange，但该 exchange 上没有任何 binding 匹配这个 routing key；

② 队列被删除或绑定被删。

**关键点**：只有在 `mandatory=true`（或 `spring.rabbitmq.template.mandatory=true`）时，无法路由的消息才会通过 `basic.return` 回调返回给生产者，**否则消息会被 broker 直接丢弃且生产者毫无感知**。

**本项目的情况比较特殊**：`MQSender` 用的是 `amqpTemplate.convertAndSend(MQConfig.SECKILL_QUEUE, msg)` 这个重载——**只传了"队列名"，实际走的是默认 direct exchange + routing key 等于队列名**，只要队列还在就一定能路由到，所以路由失败的概率很低（队列由应用启动时声明，也是 durable）。**但如果队列被误删**，消息就静默丢失了——这也是应该加 mandatory + return 回调的原因。

### 66. 队列堆积如何监控与告警？堆积到什么程度算异常？扩容消费者的触发条件是什么？

**【未实现：没有做堆积监控与告警。】** 能拿到这些数据的途径是 RabbitMQ 的 management HTTP API（`/api/queues` 里有 `messages`、`messages_ready`、`messages_unacknowledged`、`consumers`，以及 `message_stats.publish/deliver` 速率）或 `rabbitmqctl list_queues`。

**判异常的阈值**：不能只看绝对值，要看两件事——① **ready 消息是否持续增长**（说明消费速率跟不上生产速率，这是真堆积）；

② **unacked 是否长期高位**（说明消费者卡住或处理超时）。**扩容触发条件**应该是"消费速率 < 生产速率且 ready 持续 N 分钟增长"，而不是"消息数超过某个绝对值"（秒杀场景天然会有瞬时堆积，几秒内消化掉是正常的）。

**本项目的"监控"只有一个替代品**：验证脚本里查过一次 `/api/queues` 确认 `seckill.queue` 已声明、consumer 数为 10——这只能算抽查，不是监控。

### 67. 消费失败的重试策略（次数、间隔、是否入死信）是什么？无限重试会造成什么后果？

**配置是 `default-requeue-rejected=true`，也就是消费方法抛异常时消息会被重新入队——而且没有次数上限、没有间隔控制、也没有死信队列。** 这等于**无限重试**。后果很严重：

① **毒消息（poison message）会打转**——如果某条消息因为数据问题必然处理失败（比如商品被删了、消息体格式坏了），它会被反复投递、反复失败，占满消费者、把真实业务消息堵在后面；

② 日志被同一个异常刷屏；

③ CPU 空转。

**正确做法**：

① 配 `spring.rabbitmq.listener.simple.retry`（最大重试次数 + 退避间隔），或者 `default-requeue-rejected=false` 让消息在重试耗尽后被丢弃/进死信；

② 给队列绑定死信交换机（DLX），失败消息落到死信队列后人工介入或定时补偿；

③ 明确区分"可重试异常"（网络抖动、锁冲突）和"不可重试异常"（数据非法），只有前者才重试。**这是本项目在 MQ 使用上最需要补的一处。**

### 68. 死信队列、延迟队列用到了吗？"下单后 15 分钟未支付自动关单"你会怎么实现？

**都没用到。** 15 分钟关单的实现方案，两种都可行，取舍不同：

① **TTL + 死信队列**——下单时往一个"延迟队列"投消息并设 `x-message-ttl=900000`，该队列不设消费者、只配置 `x-dead-letter-exchange` 指向真正处理关单的队列，消息 TTL 到期后自动被投到死信队列，消费者在那里检查订单状态（若仍未支付就关单并回补库存）。**优点**是不引入插件；**坑**是 TTL 是队列级的、且**只有当消息到达队头时才会被判定过期**（前面有未过期消息会挡住后面的），所以需要按时间分桶或用单条消息 TTL；

② **延迟插件（rabbitmq_delayed_message_exchange）**——直接给消息设 `x-delay` 头，精度好、无队头阻塞，代价是要在 broker 上启用插件。若消息量到百万级，两者都不太合适，**该上时间轮（Netty HashedWheelTimer）或专门的定时任务框架（XXL-Job）**，用"订单过期时间 + 状态"的联合索引分批扫描。

**关键设计点**：关单这个动作必须**幂等**（`update order set status=已取消 where id=? and status=未支付`，靠影响行数判断是否真的改成功），因为延迟投递可能重复触发。

### 69. 消费端的幂等如何实现？先写订单再减库存、与先减库存再写订单，各自的失败场景有什么不同？

**本项目的幂等实现**（第 55 问详述）：查 Redis → 条件 UPDATE 减库存 → 插入受唯一索引约束的 `seckill_order`，三层都能在重复消费时安全返回。

**两种顺序的失败场景差异**：**先减库存再写订单**（本项目）——如果写订单失败会回滚减库存（同一事务），不会产生"库存少了但订单没生成"；风险点是**扣减成功但事务提交前进程崩溃**，不过事务未提交就会被数据库回滚，仍然是安全的。**先写订单再减库存**——问题更大：订单已经落库（**而订单是业务上的"承诺"，通常不能回滚**），此时如果减库存失败，要么订单变成"超卖订单"（有单没货），要么需要额外的补偿流程去关单；换句话说，**你把"必须先占住资源再承诺"这个顺序搞反了**。所以正确顺序永远是"先占资源（减库存，可回滚）→ 再产生结果（写订单）"，并且两者在同一个事务里。

### 70. 削峰只是把压力后移，如果消费能力不足，数据库最终仍会被打满——你如何评估消费端吞吐？是否做了消费限速？

**这个判断是对的，而本项目没有做消费端的容量评估，也没有主动限速。** 本项目的"限速"是**被动的**：`prefetch=1` + 10 个消费者意味着最多 10 条消息同时在处理，天然把写数据库的并发压在 10 以下。**要评估消费端吞吐**，正确的做法是：

① 测单条消息的处理耗时（本项目里是"一次 UPDATE + 两次 INSERT + 一次 Redis 写"，估计毫秒级），算出单消费者 TPS；

② 乘以消费者数得到理论上限；

③ 用生产速率（预减通过的速率）对比，确认 `消费 TPS > 生产 TPS`，否则队列必然无限堆积。**如果生产速率超过消费能力**，可用的手段是：

① 提高消费者并发（但要受数据库行锁与连接池限制）；

② **在入口侧主动限速**（例如对"预减通过并投递"这个动作按商品做令牌桶限流，让入队速率不超过消费能力）——这比让队列堆到爆更可控；

③ 极端情况下**降级**：直接返回"活动太火爆，请稍后重试"，把流量挡在系统之外。

### 71. 如果 RabbitMQ 整体不可用，秒杀接口如何降级？有没有设计开关、旁路或同步降级方案？

**【未实现：没有降级开关、没有旁路。】** 当前行为是：`MQSender.sendSeckillMessage` 内部 `amqpTemplate.convertAndSend` 抛异常 → 异常向上冒泡 → `GlobalExceptionHandler` 兜住返回 `500100 服务端异常！`。也就是**用户看到"服务端异常"，但 Redis 库存已经被这个请求预减掉了一份**（预减在投递之前）——又是一次少卖。**该设计的降级方案**（三选一，按业务容忍度排序）：

① **同步降级**——检测到 MQ 不可用时，直接在请求线程里执行"减库存 + 写订单"（即把消费端的逻辑内联），牺牲吞吐保可用性，用配置开关 `seckill.mq.enabled=false` 控制；

② **快速失败**——入口前置健康检查（例如缓存一个"MQ 可用"标记，不可用时直接返回"当前活动太火爆"），并且**把预减放到投递之后或做成可回补**，避免"扣了库存又没下单"；

③ **降级到队列缓冲**——本地内存队列 + 定时重投（只能扛短暂抖动，进程崩溃会丢消息，风险高）。

**生产上我会选 ① + ② 组合**：开关切同步处理保证功能可用，同时入口限流把同步处理的压力控住。

**另外要强调**：不管选哪种，都要解决"预减成功但没投递成功"的库存归还问题——这正是第 24 问那个回补缺口的延伸。

## G. 接口防刷与秒杀地址隐藏（11 问）

> [!warning] 本组最容易被打穿的点
> 第 74 问（INCR 与 EXPIRE 非原子）与第 80 问（MD5 地址能否重放）——这两处项目里的实现都有真实弱点，要主动承认并给出改进方案。

### 72. @AccessLimit 注解包含哪些属性（时间窗口、次数、是否登录）？拦截器如何解析这些参数？

注解定义三个属性：`int seconds()`（时间窗口秒数）、`int maxCount()`（窗口内最大次数）、`boolean needLogin() default true`（是否要求登录）。

**实际用法**：秒杀接口是 `@AccessLimit(seconds = 5, maxCount = 5)`，也就是 5 秒内最多 5 次。**拦截器解析流程**（`AccessInterceptor.preHandle`）：

① 判断 handler 是不是 `HandlerMethod`（静态资源不是，直接放行）；

② 先解析当前用户（从 cookie 或 `token` 请求参数取 token → 查 Redis → 放进 `UserContext`）；

③ `method.getMethodAnnotation(AccessLimit.class)` 拿注解，为 null 直接放行；

④ 拼限流 key：`request.getRequestURI()`，若 `needLogin=true` 则先判空（未登录直接返回 `500100`），并把 key 拼成 `URI + "_" + userId`；

⑤ 用 `AccessKey.withExpire(seconds)` 作为缓存前缀（这样 key 的 TTL 就等于注解里的窗口秒数），先 `get` 再 `incr`，超过 `maxCount` 就 `render` 一个 JSON 响应并返回 false（中断请求）。

### 73. 为什么用拦截器而不是 AOP 或 Filter 实现限流？三者在 Spring MVC 中的执行顺序与差异是什么？

**选拦截器的核心理由：它能拿到 `HandlerMethod`，也就是能拿到方法上的注解**。三者的差异：**Filter** 在 Servlet 容器层，作用于所有请求（包括静态资源），拿不到 Spring MVC 的 handler 与注解，要做注解驱动就得自己解析 URL 映射；**Interceptor** 在 DispatcherServlet 内、HandlerMapping 之后，能拿到 `HandlerMethod`，也能修改响应、能在 preHandle/postHandle/afterCompletion 三个时机介入——注解限流天然适合它；**AOP** 作用在 Bean 方法调用上，虽然也能拿到注解，但它是"方法级"的，对"每个 HTTP 请求"这个语义不如拦截器贴切，而且 AOP 代理会带来额外开销、对静态资源无效。**执行顺序**是 `Filter → Interceptor.preHandle → AOP → Controller → AOP → Interceptor.postHandle → Filter`。

**本项目用拦截器的额外好处**：它顺带承担了"解析当前用户并放入 ThreadLocal"的职责（`UserContext`），Controller 通过参数解析器直接拿到 `SeckillUser`，业务代码零侵入。

### 74. 限流计数用什么 Redis 命令？INCR 与 EXPIRE 两步非原子，你怎么解决？有没有改用 Lua？

用的是 **`GET` + `INCR` 两条命令**（`redisService.get` 判 null 则 `set(key, 1)`，否则 `incr`），**不是 INCR + EXPIRE 组合**——这里用了个取巧的做法：**把 TTL 放在 key 前缀的属性里**，也就是 `AccessKey.withExpire(seconds)`，`RedisService.set` 在 `expireSeconds > 0` 时会用 `SETEX` 一次性设置值和过期时间，所以"设置计数"和"设置过期"是原子的、不存在先 INCR 后 EXPIRE 中间断掉导致键永不过期的问题。

**但确实还有一个非原子问题（且是真实缺陷）**：`GET` 和 `INCR` 是两次独立调用，**并发下会超发**——比如窗口内已经有 4 次、同时来了 5 个请求，它们可能都读到 4、都判断通过，最终放行远超 5 次。**【未实现：没有改用 Lua】**，这是我知道但没改的地方。**正确做法**是一段 Lua：`local c = redis.call('INCR', key); if c == 1 then redis.call('EXPIRE', key, seconds) end; return c`——把"自增"和"首次设置过期"绑成原子操作，调用方只比较返回值与 maxCount。这样既消除了并发超发，也彻底避免"键永不过期"（第 128 问会追问的点）。

### 75. 固定窗口限流的临界突变问题是什么？滑动窗口、令牌桶、漏桶各自的实现与取舍？你为什么没换用？

**临界突变**：固定窗口在"窗口交界处"允许的请求量会突增到接近 2 倍——比如限 5 次/5 秒，用户在 4.9 秒时用掉 5 次、到 5.0 秒窗口刷新后又用 5 次，实际在 1 秒内放行了 10 次。

**三种替代方案**：

① **滑动窗口**（用 ZSET 存请求时间戳，或用多个小窗口近似）——精度高，代价是每个请求要写一条 ZSET 记录、内存开销与请求量成正比；

② **令牌桶**（按速率往桶里放令牌、请求取令牌）——允许突发但有上限，实现需要"上次补充时间 + 当前时间"计算，通常也用 Lua 保证原子；

③ **漏桶**（请求入队、按固定速率流出）——严格平滑，但会引入排队延迟，对秒杀这种"要么立刻放行要么拒绝"的场景不合适。

**本项目没换的原因很实际**：`maxCount=5/5秒` 这个力度下，临界突变造成的 2 倍偏差对秒杀场景几乎没有影响（真正的防线是库存判定，限流只是降低无效流量），而换 Lua 令牌桶会引入额外复杂度与每次请求的脚本执行开销。

**如果被问到"该不该换"**：我的判断标准是"限流是保护系统还是业务规则"——保护系统用固定窗口够用，业务规则（比如"每用户每天限领 2 张券"）就必须用精确窗口。

### 76. 限流维度是"用户 + URI"，未登录用户如何识别？按 IP 限流会遇到 NAT、代理、伪造 X-Forwarded-For 等问题吗？

**未登录用户不会被识别为独立维度**——因为注解默认 `needLogin=true`，拦截器发现 `seckillUser == null` 时**直接返回 `500100` 拒绝请求**，根本不会进到计数环节。所以本项目的限流**只对已登录用户生效**，key 是 `requestURI + "_" + userId`。

**这个设计有个副作用要承认**：被注解标了 `needLogin=true` 的接口，实际上把"认证"也一起做了——认证被搭在了限流注解上（项目里那个本来负责认证的 `LoginInterceptor` 从未被注册，`@NeedLogin` 是死代码）。

**按 IP 限流会遇到的问题**：

① **NAT/出口 IP 复用**——一栋宿舍、一个公司共用一个公网 IP，按 IP 限流会误伤大量正常用户；

② **代理与伪造**——`X-Forwarded-For` 是客户端可伪造的请求头，只有在你信任的代理（如 Nginx）**重写**过它时才可信，否则攻击者伪造一个随机 IP 就能绕过；

③ **IPv6 与移动网络**——地址空间与切换频率让 IP 维度的意义下降。

**结论**：IP 只能作为**风控的弱特征**参与打分，不能作为硬性限流维度；要防"同一台机器开一堆小号"，该用设备指纹 + 账号行为序列。

### 77. 触发限流后返回什么状态码与响应体？前端如何提示？有没有统一异常处理？

**HTTP 状态码是 200**，响应体是统一的 Result 信封：`{"code":500103,"msg":"请求过于频繁","data":null}`（`CodeMsg.ACCESS_LIMIT_REACHED`）。

**实现方式**：拦截器不抛异常，而是自己往响应里写 JSON（`render(response, codeMsg)`：设 `Content-Type: application/json;charset=UTF-8`，用 fastjson 序列化 `Result.error(codeMsg)` 写进 outputStream，然后 `return false` 中断请求）——**所以它绕过了 `@ControllerAdvice`**，这也是为什么状态码只能是 200（响应已经开始写了）。

**前端提示**：js 里统一判断 `data.code != 0` 就 `layer.msg(data.msg)` 弹提示。

**统一异常处理**：业务异常（`GlobalException`）和参数校验异常（`BindException`）走 `GlobalExceptionHandler`（`@ControllerAdvice`），其他异常统一转成 `500100 服务端异常！`——但**限流和未登录这两条路径是拦截器直接写的响应，不走统一处理器**，这是设计上的一处不一致（改进方向：把拦截器改成抛自定义异常，让 `@ControllerAdvice` 统一处理，同时用 `ResponseStatus` 返回 429 语义更清晰）。

### 78. "对业务代码零侵入"具体是怎么实现的？注解解析带来的反射开销如何优化？

**实现方式**：把"限流"这个横切关注点从业务方法里彻底挪出去——业务代码上只留一个 `@AccessLimit(seconds=5, maxCount=5)` 注解，限流的判空、计数、拒绝全部由 `AccessInterceptor` 在方法执行前完成。Controller 方法体里看不到任何限流相关代码，加/改限流规则只改注解。

**顺带做到零侵入的还有两件事**：

① 用户解析——`AccessInterceptor` 把当前用户放进 `ThreadLocal`（`UserContext`），`UserArgumentResolver` 让 Controller 直接声明 `SeckillUser` 参数就能拿到，不需要每个方法都 `request.getParameter("token")`；

② 异常处理——`@ControllerAdvice` 统一兜住。

**反射开销**：每次请求调一次 `method.getMethodAnnotation(AccessLimit.class)`，这是 Spring 已经缓存过注解元数据的查询，开销在纳秒级，相对一次 Redis 往返（几十到几百微秒）可以忽略。

**如果真要优化**：

① 把注解信息按 `HandlerMethod` 缓存在 `ConcurrentHashMap` 里（一次性解析）；

② 更彻底的是在启动时遍历所有 handler，把"需要限流的接口 + 参数"预编译成路由表，运行时只查表——但这是十万级 QPS 才值得做的事，本项目不需要。

### 79. 秒杀地址用 MD5 生成，输入包含哪些因子？为什么要 60 秒过期？地址在什么时候下发给前端？

**生成方式**：`SeckillService.createSeckillPath` 里 `MD5Util.md5(UUIDUtil.uuid() + "123456")`——即"**随机 UUID + 一个固定盐**"做 MD5，存进 Redis（key 是 `SeckillKey:sp<userId>_<goodsId>`，TTL 60 秒）。

**注意因子里的关键设计**：**Redis 的 key 里带了 `userId`**，也就是说地址本身虽然是个随机串，但它在服务端是**与用户绑定**存储的——校验时用当前登录用户的 id 去查，别的用户拿到这个地址也用不了。

**为什么 60 秒**：要覆盖"用户打开验证码 → 看清答案 → 输入 → 提交"这个正常操作流程（一般 10~30 秒），同时又要短到让脚本难以"囤积一批地址慢慢用"。

**下发时机**：用户先请求 `GET /seckill/verifyCode` 拿到验证码图片，输入答案后请求 `GET /seckill/path?goodsId=N&verifyCode=A`，校验通过才生成并返回地址；前端拿到地址后拼进下单 URL `POST /seckill/{path}/seckill`。

### 80. 用 MD5 生成的地址是否足够不可预测？攻击者拿到真实地址后能否重放？地址与用户如何绑定？

**不可预测性**：足够。输入是 `UUID.randomUUID()`（122 位随机性，基于 `SecureRandom`），加盐做 MD5 只是把它固定成 32 位十六进制串；**MD5 在这里不是安全哈希的用途**（不是为了抗碰撞或抗爆破），只是"把随机数转成短字符串"——所以"MD5 不安全"这个质疑在这里不成立，真正的随机性来自 UUID。

**能否重放**：**在 60 秒 TTL 内、使用同一个用户身份，可以重放**——地址是一次性下发的、但不是一次性的。这是一个真实的取舍：如果要做成严格一次性，应该在 `checkPath` 校验通过后**立即删除**这个 key（`GETDEL` 语义或用 Lua 原子取出即删）。**本项目的防重不依赖地址的一次性**，而是靠后面的"判重 + 唯一索引"——也就是地址只负责"挡住不知道地址的盲目脚本"，防重由别的层承担。

**地址与用户的绑定**：靠 Redis key 里的 `userId`（`SeckillKey:sp<userId>_<goodsId>`），校验时用当前请求的用户 id 查——所以即使地址泄露给别人，对方也用不了（除非他拿着你的 token）。

### 81. 地址过期时用户还停留在页面上，体验问题怎么处理（自动刷新、提示重进、宽限期）？

**【未实现：没有专门处理。】** 当前行为：地址 60 秒后 Redis 里的 key 过期，用户此时点"立即秒杀"会走 `checkPath` 失败 → 返回 `500102 请求非法！` → 前端弹出这个提示。**问题是提示语不够友好**（"请求非法"会让用户困惑），而且用户需要重新走一遍验证码流程。

**该做的三件事**：

① **提示语分层**——把"地址过期"与"地址错误"区分开（比如过期的 key 可以在 Redis 里留一个更短 TTL 的"已过期"标记，或者直接在前端按时间判断），提示"秒杀地址已过期，请重新获取"；

② **前端自动重取**——在倒计时结束时或收到该错误码时，自动重新请求验证码 + 地址，用户无感；

③ **宽限期**——把 TTL 设成 90~120 秒（覆盖用户可能的犹豫），或者校验时容忍"过期不超过 N 秒"的地址（记录下发时间）。

**为什么会出现这个缺口**：当时的设计假设是"用户拿到地址就会立刻点"，没有考虑停留场景；属于典型的"没被测试覆盖到的体验路径"。

### 82. 除了限流与地址隐藏，你还了解哪些防刷手段（验证码、设备指纹、风控规则、黑名单）？本项目为什么没上验证码？

**先纠正一个前提**：本项目**是有验证码的**——算术验证码（`GET /seckill/verifyCode` 返回一张 AWT 渲染的算式图片，答案存 Redis、TTL 300 秒、校验一次即删），它的定位是"**分散请求、拉平峰值**"（让用户花几秒看图算题，把瞬时并发摊开），而不是安全屏障。**我在前面给过的一个建议是"可以删掉它"**，理由是：算术题可以被 OCR 毫秒级破解，它挡不住脚本，只对真人有效；如果目的是挡脚本，应该换成更有用的东西。

**其他防刷手段及适用性**：

① **设备指纹**——采集浏览器/设备特征做唯一标识，能识别"同一台机器开多个小号"，但涉及隐私合规、且可被伪造；

② **风控规则引擎**——按"账号年龄 + 历史行为 + 请求频率 + 设备聚集度"打分，超过阈值要求二次验证（短信/滑块），这是**生产上最有效的一层**，因为它是多维的、持续对抗的；

③ **黑名单/灰名单**——对已确认的异常账号/IP 做拒绝或降级（比如始终返回"已售罄"但不影响真实用户）；

④ **请求签名与重放防护**——客户端用密钥对"时间戳 + nonce + 参数"签名，服务端校验时效与 nonce 唯一性，这能替代验证码做"机器识别"（成本高但有效）。

**本项目没做这些的原因**：都属于"风控体系"，需要真实的攻击样本、日志与数据支撑才能调参，demo 规模下引入只是摆设；**能说清"为什么不做"比硬塞一个摆设更有说服力**。

## H. Function Calling 大模型客服助手（9 问）

> [!warning] 本组提示
> 本组是简历亮点区。第 83 问的关键：**不要声称用了 Spring AI**（项目是 Spring Boot 1.5.10 / Java 8，用不了），如实说手写 HTTP + SSE——这个回答本身是加分项。

### 83. Function Calling 用的是哪个模型与框架（Spring AI / LangChain4j / 原生 API）？完整链路请描述一遍。

**模型是 DeepSeek（`deepseek-chat`，走它的 OpenAI 兼容接口），框架没用——是手写的 HTTP 客户端。** 这里有个明确的约束需要讲清楚：**Spring AI 要求 Spring Boot 3.4+ / Java 17，而本项目是 Spring Boot 1.5.10 / Java 8，用不了**；所以我自己写了 `DeepSeekClient`：用 `HttpURLConnection` 发 POST，请求体用项目已有的 fastjson 拼（`model` / `messages` / `tools` / `stream`），流式响应按 SSE 逐行读（只处理 `data:` 开头、跳过 `[DONE]`），解析 `choices[0].delta.content` 后回调出去——**没有引入任何新依赖**。

**完整链路**：用户提问 → `AiChatController`（`GET /ai/chat`，带 `@AccessLimit` 限流）→ 从 Redis 读出该会话的历史消息 → **第一轮非流式调用**（带 `tools`）判断要不要查数据 → 如果模型返回 `tool_calls`，逐个执行 `AiToolKit` 里的 Java 方法并把结果作为 `role=tool` 消息追加 → **第二轮流式调用**生成最终回答、逐块推给前端 SSE → 回答结束后把"用户问题 + 助手回答"存回 Redis。

### 84. 注册了哪些函数？每个函数的名称、参数 schema 与描述是怎么写的？模型如何选择调用哪一个？

注册了**三个只读工具**，都用标准的 JSON Schema `{name, description, parameters}` 声明：

| 函数 | 参数 | 数据来源 | 用途 |
|---|---|---|---|
| `getGoodsStock` | `goodsId` (integer，必填) | `seckill_goods.stock_count` | "还剩多少件" |
| `getSeckillActivity` | `goodsId` (integer，必填) | `seckill_goods` 的 `start_time`/`end_time` | "什么时候开始/结束" |
| `getMyOrders` | **无参数** | `order_info`（按当前用户） | "我抢到了吗" |

**description 的写法**是刻意带上了"什么时候该调用"的自然语言提示，例如 `getGoodsStock` 的描述是"查询某件秒杀商品当前的库存数量和秒杀价。**用户问"还剩多少件""还有货吗"时调用**"——这是引导模型正确路由的最有效手段。

**模型如何选择**：靠 `description` 的语义匹配 + 请求里带 `tools` 数组（没有强制指定 `tool_choice`，即 `auto` 让模型自主决定）；实测三种问法分别命中了对应的工具，且"还剩多少件、什么时候开始"这类复合问题模型会在**一条响应里同时返回两个 `tool_calls`**（这也是我只做一轮工具解析就够用的原因）。

### 85. 用户用自然语言查询订单时，如何防止越权查询他人数据？鉴权放在模型调用之前、函数内部还是结果返回之后？

**靠"结构性防御"：`getMyOrders()` 不接受任何参数。** 用户身份不是模型传进来的，而是服务端从已登录会话里拿到的——`AiChatController` 通过项目的参数解析器（`UserArgumentResolver` + `UserContext`）拿到当前 `SeckillUser`，再把它传给 `AiToolKit.execute(name, args, user)`，工具内部直接用 `user.getId()` 查库。**所以模型在结构上就没有"指定别人的 userId"这个能力**，无论 prompt 怎么诱导都做不到——这比"在 prompt 里叮嘱模型不要查别人数据"可靠得多。

**鉴权的位置**：

① **模型调用之前**——`/ai/chat` 上有 `@AccessLimit(needLogin = true)`，未登录直接拒绝，工具根本不会被触发；

② **函数内部**——即使模型幻觉出一个 userId 参数，工具签名里也没有这个参数可以接；

③ 结果返回之后不做额外过滤（因为查询条件本身已经被限定死了）。

**这种设计思路值得强调**：**能用结构约束解决的问题，不要交给 prompt**。

### 86. 如何防止 prompt 注入（诱导调用越权函数、套取系统提示词或他人信息）？

**本项目靠的是"缩小攻击面"，而不是做过滤**，因为工具集本身就极窄：

① **只读**——三个工具全是查询，没有任何写操作，所以最坏情况是"泄露数据"，不存在"改数据/下单"这类破坏；

② **无越权参数**——`getMyOrders` 不接受参数，模型无法指定查询对象（第 85 问）；

③ **数据范围天然受限**——能查到的就是"当前用户自己的订单 + 公开的商品库存与活动时间"，这些数据对用户本来就是可见的。**因此剩下的风险主要是"套取系统提示词"，而系统提示里没有任何敏感信息**（就是一句角色设定 + "不许编造数字"的约束），泄露也无害。**如果要做更严格的防护**（本项目没做）：

① **输入侧**——对用户输入做检测（"忽略以上指令"这类注入特征），但这本质上是一场猫鼠游戏，不该作为主要防线；

② **输出侧**——拦截回答里是否出现"系统提示""工具返回原文"之类的痕迹；

③ **函数白名单 + 参数校验**——只允许调用注册过的函数、对参数做强类型与范围校验（本项目有基础版：`AiToolKit.execute` 里对未知函数名返回 error）；

④ **权限收窄**——把工具按用户角色分级（比如只有运营能调统计类工具）。

**一句话总结**：prompt 注入的根治办法是"让模型即使被完全控制也做不了坏事"，也就是最小权限的工具设计。

### 87. 模型传错参数或"幻觉"出不存在的数据时如何兜底？函数执行失败如何反馈给模型与用户？

**参数层兜底**：`AiToolKit.execute` 里先 `JSONObject.parseObject(arguments)` 解析参数（参数为空时给空对象），按函数名分发；`goodsId` 不存在时返回 `{"error":"商品不存在: goodsId=x"}` 而不是抛异常——**把错误当成一种正常的工具结果回传**。

**执行层兜底**：整个 `execute` 套了 try-catch，任何异常都转成 `{"error":"工具执行失败: ..."}` 的 JSON 返回给模型。

**为什么要把错误回传给模型**：这样模型能基于错误信息给用户一个合理的解释（比如"这个商品不存在，请确认 ID"），而不是前端看到一个空白回答。

**幻觉不出数据**：这是本设计最关键的一点——**系统提示里明确写了"凡是涉及库存数量、时间、订单的问题，必须先调用工具获取真实数据，严禁凭印象编造任何数字"**，而且即使模型不调工具直接回答，也没有数据可编（它的训练数据里不可能有我们这个商品的实时库存）。

**验证方式**：我在验证脚本里专门断言了"回答里的库存数字必须等于数据库里的值"（实测答出"还剩 10 件"且数据库确实是 10）。

### 88. 大模型响应慢、成本高，你做了哪些工程处理（超时、缓存、限流、异步、流式输出）？

做了四件事：

① **流式输出（SSE）**——回答通过 `GET /ai/chat` 以 `text/event-stream` 增量下发，前端 `EventSource` 边收边渲染，用户不需要等整段生成完（实测首字延迟 1993ms、整段 2139ms）；

② **两阶段调用**——第一轮非流式只用来判断"要不要查数据"，第二轮流式生成用户可见的回答，避免"非流式先答一遍、流式再答一遍"的**重复计费**；

③ **限流**——复用项目既有的 `@AccessLimit(seconds=60, maxCount=10)`，每用户每分钟最多 10 次对话，因为**每次对话都真实消耗 token**（这一层是成本保护，不只是防刷）；

④ **异步推送**——SSE 的发送放在独立线程池里（`Executors.newFixedThreadPool(4)`，守护线程），不占用 Tomcat 请求线程。

**超时**：`HttpURLConnection` 设了连接 10 秒、读取 30 秒。**【未实现：没有做结果缓存】**——相同问题会重复调用模型（可以考虑按问题语义缓存，但要小心"库存类问题不能缓存"）；也没有做重试与降级文案（目前失败统一返回 `AI 服务暂时不可用，请稍后再试`）。

### 89. 这个模块怎么做测试与回归？模型输出不稳定时如何保证质量？

**测试方式**：写了一份可重复执行的验证脚本（`verify-ai.ps1`，**真实调用 DeepSeek**，10 项断言），覆盖四类：

① **工具是否真的被触发**——断言 SSE 事件流里出现了 `tool:getGoodsStock` 这类事件（前端也把这个事件渲染成"⏳ 正在调用业务接口：xxx()"，既是进度提示也是"真的查了库"的可见证据）；

② **数字是否与数据库一致**——先重置数据让库存确定（10 件），再断言回答里包含 10；

③ **流式是否生效**——记录首个 `delta` 事件的到达时间与整段完成时间，断言"首字早于整体完成"；

④ **会话是否持久化**——直接查 Redis 确认会话 key 的条数与 TTL。

**模型输出不稳定怎么保证质量**：核心思路是**不比对文本、只比对事实**——不断言"回答等于某句话"（那是不可能的），而是断言"回答里包含正确的数字""触发的是预期的工具""数字与库一致"。**这套断言是稳定的**，因为它校验的是"事实正确性"而不是"措辞"。**【未实现：没有 JUnit 测试】**，脚本在仓库外、需要手动执行。

### 90. 为什么要在秒杀系统中集成大模型客服？它对主链路有没有性能或安全上的影响？

**动机是真实的**：秒杀活动期间咨询量会暴增，而且问题高度集中——"什么时候开始""还剩多少件""我抢到了吗""为什么我没抢到"。这些问题的答案全都在业务系统里，但大模型并不知道，所以如果只做一个通用聊天框，它只能编造。

**这个模块的价值就在于"把实时业务数据接给模型"**：通过 Function Calling 让它查真实库存、活动时间和用户订单，回答里的数字全部来自数据库。

**对主链路的影响**：

① **性能上无影响**——独立端点（`/ai/chat`）、独立线程池（4 个守护线程，与秒杀和 MQ 消费的线程池完全隔离），且 AI 接口本身被限流到每用户 10 次/分钟；唯一的共享资源是 Redis（会话存储）和数据库连接（工具查询），属于只读、量级远小于秒杀主链路。

② **安全上有影响，需要设计**——最需要注意的是"不能让它成为越权的查询入口"，这靠第 85 问的"工具不接受身份参数"从结构上解决；另外**成本也是一个安全边界**（未限流的话一个脚本就能刷爆 token 账单），所以必须限流。

**⚠️ 一个必须说明的点**：这个模块是我在原有秒杀系统**之后**新增的，主链路（秒杀下单）不依赖它——AI 服务不可用或配额用尽时，秒杀功能完全不受影响（`ai.enabled=false` 时该接口返回明确提示，其他功能正常）。

### 91. 如果调用量很大，这一层的架构你会怎么设计（独立服务、网关限流、结果缓存、降级文案）？

按优先级四步演进：

① **独立成单独服务**——把 AI 模块从秒杀应用里摘出去（它现在的线程池、限流、依赖都与主业务无关），单独部署、单独扩缩容，好处是模型调用慢不会影响任何交易链路，也便于单独给 AI 服务配更大的线程池与更长的超时；

② **网关层按用户/租户限流**——把限流从应用内注解提到网关（比如 Spring Cloud Gateway + Redis 令牌桶），可以按"用户、来源、模型"多维配额，还能做配额分级（普通用户 10 次/分钟、付费用户 60 次/分钟）；

③ **结果缓存**——对"低时效性"的问题做缓存（比如"秒杀规则是什么"可以缓存答案），但**必须按问题类型分流**：涉及库存/订单/时间的问题绝不能缓存（或者只能缓存极短 TTL），这个判断可以让模型先做一次分类；更高级的是**语义缓存**（用向量相似度命中"意思相同"的问题，避免措辞不同就穿透）；

④ **降级与兜底**——准备静态文案（"当前咨询量较大，请稍后再试"）、模型降级（主模型超时/失败时切到更小更快的模型）、以及**功能降级**（模型全挂时直接返回"该问题请查看订单页"这类引导）。**另外要补的一层是"可观测性"**——记录每次调用的 token 消耗、首字延迟、工具调用成功率，这是控制成本与质量的前提。

## I. 测试、压测与工程化（7 问）

> [!warning] 本组最容易被打穿的点
> 第 92 问会直接质疑"30 并发能不能叫高并发"——**主动承认它验证的是正确性、不是吞吐**，然后给出补做的方案，比硬撑强得多。

### 92. "30 并发抢 10 件库存"这种测试规模能否支撑"高并发"的结论？为什么没有做 QPS 上千的压测？

**不能，这个规模支撑不了"高并发"的吞吐结论——它验证的是并发正确性。** 我要把这两个概念分清楚：**"高并发"作为吞吐指标**需要 QPS/延迟/资源消耗的数据（我没测）；**"并发正确性"**验证的是"多个请求同时抢同一份资源时，业务结果是否仍然正确"（这个测了）。

**30 并发抢 10 件的价值在于它给出了确定的断言基础**：入队 10、售罄 20、数据库库存 0、两张订单表各 10 行、零重复、`0 + 10 = 10` 守恒——这些断言在小规模下**可以逐条核对数据库**，错误无处可藏；而如果直接上 1000 并发，出问题时很难判断是"超卖"还是"压测工具自身的问题"。**为什么没做上千 QPS 的压测**，三个真实原因：

① 本项目是本地单机演示环境（应用、数据库、MQ 都在同一台机器上），压测机器同时是服务机器，测出来的数字没有意义；

② 压测工具（我当时用 PowerShell + .NET HttpClient 模拟多用户）本身会成为瓶颈——**这一点我实际踩到了**：30 个 HttpClient 没释放，连续跑几次后本地端口耗尽、请求拿不到响应；

③ 没有可观测性支撑（没有 Actuator/Prometheus），压出来的数字无法下钻分析。**如果补做**，我的方案是：用 JMeter 或 wrk（独立机器或至少独立进程）打"读接口"（商品详情、库存查询）测吞吐上限，用 JMeter 的 CSV 数据集模拟多用户打"写链路"测预减通过率与消费端 TPS，同时开 Redis `slowlog`、看 MySQL 的 `Innodb_row_lock_waits` 与连接池活跃数，才能得出有意义的结论。

### 93. 压测脚本怎么写的（JMeter/wrk/自研线程池 + CountDownLatch）？如何避免压测工具自身成为瓶颈？

**本次用的是自研脚本（PowerShell + .NET HttpClient）**，思路是完整复现真实用户链路而不是只打一个接口：

① 先用 SQL 批量创建 30 个测试用户；

② 逐个登录拿各自的 token（放在各自的 `CookieContainer` 里，模拟不同用户）；

③ 每个用户各自走"取验证码 → 取秒杀路径"准备阶段；

④ **并发阶段**——为每个用户构造 `HttpClient.PostAsync` 请求并**先只把 Task 收集起来不 await**，三十个请求几乎同时发出（相当于用 .NET 的任务并发替代 `CountDownLatch` 的"齐射"效果），然后统一 `WaitAll` 收集结果；

⑤ 随后直接查数据库做守恒断言。

**压测工具自身的瓶颈——我踩过两个**：

① **连接耗尽**：每次运行创建 30 个 `HttpClient` 且从不 `Dispose`，连续跑几次后累积的连接耗尽本地端口，表现为后续请求拿不到响应（修复：跑完显式 `Dispose`）；

② **结果处理不适配**：收集响应时直接对 Task 取 `.Result`，一旦某个任务异常整个脚本就崩在 `InvokeMethodOnNull` 上，反而看不出"到底多少请求真的有响应"（修复：加容错，把无响应的计入"其它"并打印出来）。

**避免工具成为瓶颈的通用原则**：

① 复用连接（一个连接池/一个 `HttpClient` 多用户，或者至少显式释放）；

② 压测脚本与目标服务**不在同一台机器**（或至少不要争同一份 CPU）；

③ 只记录必要的指标（时间戳 + 状态码），别在压测线程里做重计算或写日志；

④ 压测本身的资源（线程数、文件句柄、端口）要提前算账。

### 94. 压测中观察到哪些瓶颈（CPU、Redis 延迟、数据库锁等待、GC）？你是如何定位的？

**【未实现：没有做系统性的瓶颈观测。】** 我做的是**正确性验证**（断言数据结果），不是性能剖析——所以诚实说，我没有测量 CPU、Redis 延迟、锁等待、GC 这些指标。

**能间接说出的观察有三个**：

① 消费端没有出现"消息处理不过来"的现象（30 条消息很快消化完，因为只有 10 条真正到库）；

② 数据库没有出现锁超时或死锁（失败都是"影响行数 0"而不是等锁超时）；

③ Redis 侧没有连接耗尽（连接池 100 条，30 并发远未触及）。**如果要做瓶颈定位**，我的排查顺序是：

① **先看资源水位**（`top`/`vmstat` 看 CPU 与上下文切换、`iostat` 看磁盘 IO）判断是计算、IO 还是等待；

② **再看 JVM**（`jstat -gcutil` 看 GC 频率与停顿、必要时 `jstack` 抓线程栈看有多少线程阻塞在哪一行、用 `-XX:+PrintGCApplicationStoppedTime` 确认 STW 影响）；

③ **数据库侧**（`SHOW STATUS LIKE 'Innodb_row_lock%'` 看行锁等待、`SHOW PROCESSLIST` 看慢查询、开 `slow_query_log` 抓耗时 SQL）；

④ **Redis 侧**（`SLOWLOG GET` 看慢命令、`INFO commandstats` 看各命令调用量、`redis-cli --latency` 看延迟分布）；

⑤ **链路侧**（看接口 P99 与错误率，用 Arthas 的 `trace`/`watch` 定位到具体方法）。

**优先级原则**：先看"等待"再看"计算"——秒杀场景绝大多数瓶颈最终会落在数据库行锁或连接池等待上，而不是 CPU。

### 95. 单测与集成测试覆盖到什么程度？库存、判重、MQ 消费这些关键路径有自动化测试吗？

**【未实现：项目里没有 `src/test` 目录，零单元测试。】** `pom.xml` 里有 `spring-boot-starter-test` 依赖但没有任何测试类，`mvn test` 不执行任何用例。**我有的是一条仓库外的端到端 + 并发验证脚本**（PowerShell，27 项断言），它确实覆盖了你问的这三条关键路径：

① **库存路径**——断言 `stock_count` 与订单数守恒、库存不为负；

② **判重路径**——单用户重复秒杀必须被拒（`500501`）、并发后 `group by user_id having count(*)>1` 必须为 0、`seckill_order.user_id` 必须是真实用户；

③ **MQ 消费路径**——提交后轮询必须能拿到 `orderId`（说明消息被正确消费并落库）、`order_info` 与 `seckill_order` 行数必须一致。

**但要老实区分这两者的差别**：这份脚本是**黑盒的端到端测试**，能证明"整条链路的结果正确"，但**不能定位**（哪一层坏了）、**不隔离**（依赖真实 MySQL/Redis/MQ 全部可用）、**不会在 CI 里自动跑**。

**该补的顺序**：

① 库存扣减的并发单测（用真实数据库，多线程同时调 `seckill` 断言不超卖）——这是最有价值的一个；

② 判重逻辑的单测（mock `RedisService`，验证"缓存命中即拒绝"）；

③ MQ 消费的集成测试（`@SpringBootTest` + 真实 broker 或 Testcontainers）。**这也是我列在"两周重构"里的第一件事。**

### 96. 日志规范、traceId、监控告警（Actuator/Prometheus/Grafana）你做了哪些？

**【未实现：这些基本都没做。】** 现状是：

① **日志**——只有 4 个类用了 `@Slf4j`（`LoginController`、`UserController`、`MQSender`、`MQReceiver`），其余用 `System.out.println` 或 `e.printStackTrace()`，**没有 logback/log4j 配置文件**（完全依赖 Spring Boot 默认：INFO 级别、只输出到控制台、无文件滚动）；

② **traceId**——没有，跨线程（请求线程 → MQ 消费线程）完全无法关联，排查问题只能靠时间戳猜；

③ **监控**——没有引入 Actuator，更没有 Prometheus/Grafana，所以队列长度、库存计数、限流拒绝数这些关键指标**没有任何观测手段**（这也直接导致第 66、94 问"没有数据"）。

**本次改造中我修掉的日志问题是"敏感信息泄漏"**：`MQSender`/`MQReceiver` 原来会把整条消息打进日志，而消息体里带着用户的密码摘要和盐；`LoginController` 原来 `log.info("【用户登录】" + loginVO.toString())` 也会打印密码字段——这两处都改成只记录标识（`userId`、`goodsId`、`mobile`）。

**该补的优先级**：

① 加 logback 配置（控制台 + 按天滚动文件、保留 7 天）；

② 加一个 `traceId`（用 MDC，`Filter` 里生成并在 MQ 消息里透传，消费端从消息头恢复 MDC）；

③ 引 Actuator + Micrometer 暴露关键计数（秒杀入队数、售罄拒绝数、限流拒绝数、消费失败数、库存余量），这是"削峰是否生效"唯一能拿数据说话的途径。

### 97. 部署方式是 Docker Compose 还是裸机？配置与密钥如何管理？启动脚本、健康检查有吗？

**部署方式是裸机**：`java -jar target/seckill-1.0.0.jar`，没有 Dockerfile、没有 Compose、没有 K8s。

**依赖也是裸的**：本机 MySQL（Windows 服务）、Redis（跑在一台 CentOS 虚拟机上）、RabbitMQ（本机 Windows 服务）。

**配置与密钥管理（这块是我本次改造的重点之一）**：

① 原来所有连接信息**硬编码在 `application.properties` 里提交进了仓库**（包含远程 MySQL 的 root 密码、Redis 密码），这是严重问题；

② 现在拆成两份——`application.properties` 只放不含凭据的公共配置（并声明 `spring.profiles.active=local`），**真实的连接串与密码放在 `application-local.properties`，该文件已加入 `.gitignore`**，同时提供 `.example` 模板供他人照填；

③ 数据库驱动从 5.1.x 升到 8.0.33（MySQL 8 的 `caching_sha2_password` 认证要求）；

④ AI 的 API key 同样只放在被忽略的本地文件里（我用 `git grep` 验证过所有被跟踪文件里都没有它）。

**启动脚本与健康检查**：**没有**——没有启动脚本、没有健康检查端点、没有重启策略，所以"应用是否活着"只能靠 `netstat` 看端口或访问接口。

**该补的**：

① Dockerfile（多阶段构建：Maven 构建 + 只带 JRE 的运行镜像）+ Compose 把 MySQL/Redis/RabbitMQ 一起编排起来，这样"一条命令起全套"；

② Actuator 的 `/actuator/health` 作为健康检查（K8s 的 liveness/readiness 探针）；

③ 启动脚本里带"等待依赖就绪"的逻辑（本项目启动时若 Redis 不可达会直接启动失败，见第 22 问）。

### 98. 项目目前已知的缺陷与遗留问题有哪些？如果给你两周重构，你会先改哪里？

**已知缺陷（分成"会影响正确性/安全"和"影响工程质量"两类）**：

*影响正确性或安全的（优先修）*：

① **`@AccessLimit` 的 `GET`+`INCR` 非原子**，并发下限流会超发 → 改 Lua；

② **MQ 消费端自动 ack + 无限重试 + 无死信队列**（`default-requeue-rejected=true`），毒消息会打转 → 加死信 + 重试上限；

③ **没有未支付超时关单与库存回补**，预减成功但用户不支付那份库存永远不回池 → 加延迟队列 + 幂等关单；

④ **预减成功但消息投递失败时不归还库存**（少卖）→ 加对账与补偿；

⑤ **登录拦截器从未注册**（`WebConfig` 里那行被注释掉了），认证实际上搭在限流注解上，导致没有 `@AccessLimit` 的接口（如 `/goods/to_list`）其实不需要登录，而 `@NeedLogin` 是死代码；

⑥ **商品列表页缓存会串用户**——缓存键是全局的，而页面 HTML 里含当前登录用户信息，第一个访问者的页面会被返回给所有人；

⑦ **`RedisService.scanKeys` 用 `*key*` 子串匹配而非前缀匹配**（`sp.match("*" + key + "*")`），靠命名巧合才没误删；

⑧ **fastjson 1.2.38** 有已知反序列化漏洞，且被用于 Redis 值的反序列化。

*影响工程质量的*：

⑨ **零测试、零 CI、零 Docker**；

⑩ **前端 50ms 轮询与接口的 5 次/5 秒限流冲突**（且回调不处理错误码，用户会永久卡住）；

⑪ **`Result.error(null)` 返回 `code=0`**——`Result` 的构造器在 `codeMsg == null` 时直接 return，`code` 保持默认值 0 而 0 代表**成功**，这是个高危埋雷；

⑫ **`.idea/` 被提交进仓库且 JDK 配成 21**（与 `java.version=1.8` 冲突）；

⑬ **MQ 消息体携带整个 `SeckillUser`（含密码摘要与 salt）**，应精简为只传 `userId`；

⑭ Redis 库存计数被扣成负数这一特性没有文档化，容易被误当成"剩余库存"展示。

**两周重构的优先级**：**第 1 天**——补并发单元测试（把"不超卖、不重复下单"固化成回归测试，这是所有后续改动的安全网）+ 修 ⑪ 这类一行的高危问题；**第 2–4 天**——修限流原子性（Lua）与 MQ 可靠性（手动 ack + 死信 + 重试上限），这两处是"会真的出事"的；**第 5–7 天**——补登录拦截器（让认证与限流职责分离）+ 修页面缓存串用户 + 消息体精简；**第 8–10 天**——实现未支付超时关单与库存回补（延迟队列 + 幂等关单 + 对账任务），把交易闭环补完整；**第 11–14 天**——工程化：Dockerfile + Compose 一键起全套、Actuator + 关键指标、logback + traceId、升级 fastjson 与淘汰的依赖。

| 验证脚本规模 | 端到端 + 并发 **27 项断言**；AI 模块 **10 项断言** | `verify-seckill.ps1` / `verify-ai.ps1` |
| 运行环境 | JDK 8 (Corretto 8u452)、Maven 3.8.6、MySQL 8.3、Redis 7.2.5、RabbitMQ 4.3.5 | 实测版本输出 |

**两个"反常识"但值得主动讲的设计事实**：
1. **Redis 里的库存计数被扣成负数不是 bug**，而是"先减后判"的必然结果——它是流量闸门，真实库存以数据库 `stock_count` 为准。实测并发结束后它是 -3 ~ -20 之间，而数据库是 0。
2. **2016 年的 `amqp-client 4.0.2` 能连上 2025 年的 RabbitMQ 4.3.5**——我担心过协议不兼容，实测连接与队列声明都正常。

## 附录二：项目里没有做的事

> **别声称有。** 这些是面试官最可能顺着简历追问、但你答不上细节就当场暴露的地方。被问到就直接说"这部分没做/这是我们当时的取舍"，然后给出你会怎么做——**承认 + 方案**比含糊其辞安全得多。

| 类别 | 没做的事 |
|---|---|
| **组件选型** | Sentinel / Redisson / 分布式锁 / 延迟队列 / 死信队列 / Kafka / 微服务 |
| **Redis** | Lua 脚本、Pipeline、事务、主从哨兵集群、持久化配置（AOF）、对账任务、故障注入 |
| **可靠性** | 库存回补、publisher confirm、手动 ack、重试上限、堆积监控告警 |
| **交易闭环** | 未支付超时关单、退款后重购、每人限购 N 件、收货地址 |
| **测试** | `src/test` 单元测试、CI、JMeter/wrk 压测、QPS 与延迟数据、瓶颈剖析 |
| **可观测性** | Actuator / Prometheus / Grafana、traceId、logback 配置、慢查询监控 |
| **部署** | Docker / Compose / K8s、健康检查、启动脚本、CI/CD |
| **AI 模块** | Spring AI / LangChain4j（**框架用不了，是手写 HTTP + SSE**）、Lettuce、语义缓存、多模型降级 |

**三个最需要提前想好说辞的问题**：
1. **"为什么没用 Spring AI？"** → Spring AI 要求 Spring Boot 3.4+ / Java 17，本项目是 Boot 1.5.10 / Java 8，用不了；所以手写了兼容 OpenAI 协议的 HTTP 客户端 + SSE 解析。**这是版本约束问题，不是能力问题**，答出来是加分项。
2. **"30 并发也算高并发？"** → 承认它验证的是**并发正确性**（不超卖、不重复），不是吞吐；并说明为什么小规模更适合做正确性验证（每条断言都能核对数据库），以及补做吞吐压测的方案。
3. **"你修的那个 bug 是你自己写的吗？"** → **如实说是**——它是在既有实现里发现的（硬编码 `user_id = 1L`），我通过"不信接口返回、直接查库核对数据"的方式定位到，并补了唯一索引兜底。**这个回答体现的是"能发现静默失效的缺陷"，是能力而不是污点。**
