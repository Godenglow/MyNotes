## A. 微服务拆分与架构

### 1. 为什么拆成用户、房间、预约、统计、人脸识别五个微服务？拆分依据是业务边界还是技术边界？粒度是否过细？

**答：** 拆分依据是**业务边界**，不是技术边界：用户（身份与组织架构）、房间（空间与座位资源）、预约（核心交易）、统计（只读分析）、人脸（外部第三方能力），每一块的数据归属和变更节奏都不同。人脸识别拆出来是因为它依赖外部服务、失败模式和其他服务完全不同。

**粒度确实偏细**，这点我认：以这个业务量，用户 + 房间合成一个"基础数据服务"更合理。拆细的代价是多实例部署、跨服务查询变麻烦；收益是权限与资源模型独立演进。**如果重做，我会拆成三个：基础数据、预约、统计。**

### 2. 请画出服务调用关系：预约服务依赖谁？统计服务的数据从哪来？有没有循环依赖？

**答：** 需要澄清一个容易被误判的点：**这个项目的服务之间没有直接调用**。前端（或测试脚本）统一走网关，网关按路径把请求路由到对应服务；服务之间零依赖，因此**不存在循环依赖**。

**统计服务的数据是直接读同一个数据库的**——它自己带了一套 `ReservationMapper` / `UserMapper`，查的是 `library_db` 里那些表。所以严格说这不是"服务解耦"，而是"代码解耦、数据耦合"。

**这是我事后认为需要改的地方**：统计服务应该通过接口拿数据（Feign 或消息），而不是直接读写别的服务的表——否则表结构一改，统计服务就跟着坏。

### 3. 为什么选 Spring Cloud Alibaba，而不是原生 Spring Cloud 或 Dubbo？

**答：** 说实话，**这不是我做过的严肃选型**——项目起点就是 Spring Cloud Alibaba 这套，我沿用了它。我能讲的是它相对另外两个的实际差异：

选 SCA 的合理理由是**生态一致性**：Nacos 一个组件同时覆盖注册发现（和后续可扩展的配置中心）、和 Spring Cloud 的 Gateway / LoadBalancer 是原生配合的，学习与排错成本最低。

原生 Spring Cloud 的差别主要是注册中心换 Eureka/Consul；**Dubbo 是 RPC 框架，和 Spring Cloud 不是同一层的东西**——Dubbo 更适合内部高频调用、对性能和接口契约要求高的场景，而本项目服务间根本没有调用，所以 Dubbo 在这里没有用武之地。

**如果面试官追问"你评估过什么"**，诚实说"这是沿用项目的技术栈，我做过的是理解它们各自解决什么问题"，比硬编一个选型对比要安全。

### 4. Nacos 的注册发现原理（心跳、临时/持久实例、健康检查）是什么？Nacos 宕机后服务间调用会怎样？

**答：** 服务启动时向 Nacos 注册自己的 IP:端口和元数据，默认是**临时实例**——客户端每 5 秒发一次心跳，超过 15 秒标记不健康，超过 30 秒摘除；网关侧则订阅服务列表变更（Nacos 2.x 用 gRPC 长连接推送），本地维护一份实例缓存做负载均衡。

**Nacos 宕机后**：已注册的实例在客户端本地缓存里还在，所以**短时间内服务调用不受影响**；但新实例注册不上、实例下线感知不到会摘不掉，时间一长缓存过期就可能路由到已挂的节点。

**本项目是单机 standalone、单 Nacos、实例都是默认临时实例**，所以 Nacos 一挂，网关拿不到实例列表就无法路由——这也是常见环境的单点问题。要做高可用得部署 Nacos 集群。

### 5. 用了 Nacos 配置中心吗？配置热更新（@RefreshScope）的原理与坑有哪些？

**答：❌ 没用。** 项目只引入了 `nacos-discovery`，**没有引入 `nacos-config`**，也没有 `bootstrap.yml`，配置全部在各服务的 `application.yml` 里，敏感项走环境变量覆盖（`${DB_PASSWORD:默认值}` 这种写法）。

**为什么没上配置中心**：单机部署、配置项不多，环境变量加 profile 已经够用，引入配置中心反而多一个必须运维的组件。

**如果要做**：加 `spring-cloud-starter-alibaba-nacos-config`，配置放 Nacos，用 `@RefreshScope` 或 `@ConfigurationProperties` + `/actuator/refresh` 触发。**主要的坑**：`@RefreshScope` 是懒加载代理，Bean 会在刷新后重建，所以**不能持有状态、也不能在构造器里做重活**；另外 Spring Cloud 2020 之后 `bootstrap.yml` 默认不生效，要显式引入 `spring-cloud-starter-bootstrap` 或改用 `spring.config.import`——这个版本坑我记得很清楚。

### 6. Gateway 的路由、断言、过滤器怎么配置？为什么用 Gateway 而不是 Nginx 或 Spring MVC 拦截器做统一入口？

**答：** 项目里网关配了 13 条路由，规则很直白：`predicates` 用 `Path=` 匹配前缀，`filters` 用 `StripPrefix=1` 或 `2` 剥掉服务名，`uri` 用 `lb://服务名` 交给负载均衡器解析成实例。

有两处容易踩的细节我处理过：
1. **`StripPrefix` 的取值要和 controller 的 `@RequestMapping` 对齐**——有的服务路径自带模块前缀（如 `/room/**`）就不能剥，有的是统一前缀（如 `/api/identity/**`）就要剥两层。混用是常见的 404 来源。
2. **WebSocket 路由不能剥前缀**，否则 `/ws/**` 握手路径变了就断开；另外用 `DedupeResponseHeader` 去重 CORS 响应头，避免浏览器报重复的 `Access-Control-Allow-Origin`。

**为什么不用 Nginx**：Nginx 做入口也能做，但它不认识 Nacos 的服务列表，服务扩缩容要手工改配置或再引入 consul-template 那套；**Gateway 能直接 `lb://` 订阅注册中心，且能用 Java 写过滤器**。至于 Spring MVC 拦截器，它没法在进入业务应用前就决定"这个请求该去哪个服务"，做不到路由。

**什么时候反而该用 Nginx**：需要静态资源、TLS 终结、超大并发七层转发时，通常是 Nginx 在最前面、Gateway 在内部。

### 7. 网关聚合各服务接口文档是怎么实现的？服务上下线时文档如何刷新？踩过哪些版本兼容的坑？

**答：** 用 springdoc 的**网关聚合**能力：各业务服务自己暴露 `/v3/api-docs`，网关为每个服务配一条 `/服务名/v3/api-docs/**` 的路由 + `StripPrefix=1`，然后在网关的 `swagger-ui.urls` 里列出这几个地址，`disable-swagger-default-url: true` 防止 UI 自己改写地址。这样只开一个 `http://localhost:8080/swagger-ui.html` 就能在右上角切换 5 个服务的文档。

**服务上下线时文档会怎样**：**不做额外处理——拉不到就报错**。因为聚合是"点击哪个分组才去请求那个地址"，服务没起来那个分组就是空的或报错，不影响其他分组。

**踩过的坑**：网关是 **WebFlux 栈**，必须用 `springdoc-openapi-starter-webflux-ui`，而业务服务是 Servlet 栈用 `webmvc-ui`——两边用错 starter 会导致文档页 404 或启动报 Web 类型冲突。另外网关不能引入 `spring-boot-starter-web`（会与 Gateway 冲突），所以它依赖 `common-module` 时必须把 `spring-boot-starter-web` 和 `security` 排除掉。

### 8. OpenFeign 的工作原理是什么（动态代理、编解码、负载均衡）？它与 RestTemplate 如何取舍？

**答：❌ 项目里没有用 OpenFeign**，一个 pom 里都没有引入，也没有 `@EnableFeignClients`——因为**服务之间零调用**，用不上。

不过原理我可以讲清楚，因为这是常考点：Feign 的核心是**基于接口的动态代理**——你把 HTTP 调用声明成一个 Java 接口（`@FeignClient` + `@GetMapping`），启动时扫描这些接口生成代理对象，方法被调用时由 `Contract` 解析注解拼出请求模板，`Encoder` 把参数编码成请求体，交给 `Client`（默认用 JDK 或 OkHttp）真正发出去，`Decoder` 再把响应反序列化成返回类型；集成了 Spring Cloud LoadBalancer 后，`uri` 里写服务名会被解析成实例地址并做负载均衡。

**取舍**：Feign 的优势是**接口即契约**——调用方不用手写 URL 和参数拼接，可读性和可维护性好，适合服务多、调用频繁的场景；RestTemplate（或 WebClient）更灵活、少一层代理，适合零星调用或需要精细控制超时/重试/拦截器的场景。**本项目如果要加服务间调用，我会用 Feign**，因为那时调用会变多，声明式的收益才体现出来。

### 9. Feign 的超时与重试如何配置？重试会不会导致预约请求被重复执行？如何保证幂等？

**答：❌ 没有 Feign，所以项目里没有这套配置。**

这个问题本身很关键，我讲一下**如果引入会怎么做**：超时用 `spring.cloud.openfeign.client.config.<服务名>.connectTimeout/readTimeout`，重试默认是关的（Spring Cloud 的 `Retryer.NEVER_RETRY`），要开必须显式配 `Retryer`。

**重试和幂等的关系是这里的重点**：预约属于**写操作**，一旦重试就可能重复下单。所以我的做法会是——
1. **写接口默认不重试**，只在连接建立失败这类"请求肯定没到达"的情况重试；
2. 必须重试时，调用方带一个**幂等键**（请求号 / 业务唯一号），服务端用唯一索引或幂等表把它挡住；
3. 超时无法区分"没执行"和"执行了但响应丢了"，所以**超时后不能盲目重试**，要靠查询或幂等键确认。

本项目的预约接口正好有现成的幂等基础：`(seat_id, date, time_slot)` 上的唯一索引，重复请求会被唯一键挡住。

### 10. 有没有做熔断限流（Sentinel/Resilience4j）？某个服务不可用时系统会怎样表现，如何防止雪崩？

**答：❌ 没有，而且我是主动把 Sentinel 依赖删掉的。** 原项目在 6 个模块里都引入了 `spring-cloud-starter-alibaba-sentinel`，但**全仓库没有任何限流/熔断规则，也没有 `@SentinelResource`**，dashboard 地址还错指到了网关端口 8080。引了不用、只留个依赖名，属于"技术栈堆砌"，所以我把它移除了。

**某个服务不可用时会怎样**：如果那个服务挂了，Nacos 摘不掉实例前，网关转发过去会连接失败，**请求直接 5xx**；因为服务间没有调用，**不存在调用链级的雪崩**。

**如果要做**：我会按接口价值配三种规则——抢座这类核心写接口做**并发线程数限流**（保护数据库）、统计这类重查询做**慢调用熔断**、非核心接口（人脸识别）做**降级返回**。落地方式是 Sentinel 的 `FlowRuleManager` 编程式规则（不依赖 dashboard），或网关层的 `RequestRateLimiter`（基于 Redis 令牌桶）。**先限流还是先熔断的判断标准**是：保护自己用限流，防止被下游拖死用熔断。

### 11. 跨服务数据一致性：预约成功但统计或违约记录更新失败怎么办？最终一致性如何实现？

**答：** 需要先澄清：**本项目不存在跨服务写操作**。统计服务是只读的，而且直连同一个库；违约次数（`violation_count`、`ban_until`）是**预约服务自己写 user 表的**，跟预约在同一个事务里，所以这里的一致性由**单库本地事务**保证，不需要分布式事务。

**如果将来真的拆库了**，这个问题的答案是：统计不需要强一致（看板允许分钟级延迟），所以走**异步 + 最终一致**——预约成功后发消息，统计端消费并更新汇总；消息用**本地消息表 + 定时补偿**（业务表和消息表同事务写入，再异步投递，投递失败的靠扫描重发），而不是引入 Seata 那类强一致方案，因为看板数据不值得为它承担两阶段提交的代价。

**判断标准**：先问"这块数据不一致会有什么后果"。统计错了没人受伤，就异步；账目错了会出事，才需要强一致。

### 12. 鉴权架构是怎样的？JWT 在网关统一校验还是各服务各自校验？用户身份如何透传给下游？白名单如何管理？

**答：** 这是本项目需要如实说明的一处设计：**JWT 是在各业务服务里校验的，不是在网关统一校验。** 网关只保护了自己的 Swagger 文档页。

具体链路是：`common-module` 里的 `JwtAuthenticationFilter`（`OncePerRequestFilter`）在每个服务里生效——取 `Authorization: Bearer xxx`，先查 **Redis 白名单**（登出会删掉，所以已签发的 token 也能立刻失效），再用 `JwtTokenProvider` 验签解析，然后构造 `UserSession` 放进 `SecurityContextHolder`。**身份是从 token 的 claims 里取的**（`userId`/`roles`/`state`），不是通过请求头往下游透传——因为没有服务间调用，不存在透传问题。

**白名单**是过滤器里的一个 `AntPathMatcher` 数组：登录/注册/发送验证码/`v3/api-docs`/swagger 资源/`/ws/**` 放行，其余一律要求 token；缺失或无效直接返回 401。

**我要指出的问题**：理想形态是**网关统一鉴权 + 身份透传**，各服务只信网关传过来的身份头。当前这样做的代价是每个服务都得引一套鉴权依赖、且校验逻辑分散；好处是服务可独立对外。

### 13. 跨服务排查问题靠什么？有没有引入 traceId、Sleuth、SkyWalking 之类的链路追踪？

**答：❌ 没有引入任何链路追踪**（没有 Sleuth、Micrometer Tracing、SkyWalking，也没有自己塞 traceId）。

**当前靠什么排查**：各服务独立日志 + 关键路径打的节点日志（并发抢占被唯一索引拦截会记一条 info）。但**我得承认这不够**：一旦请求跨了网关和一个服务，日志之间没有关联标识，只能靠时间戳和 userId 人工拼。

**如果要做**，成本最低的是**自己塞一个 requestId**：网关生成 `X-Request-Id` 放进 MDC 和响应头，下游过滤器读出来继续放 MDC，日志格式里带上它——不引组件也能把一次请求的日志串起来。再往上才是 Sleuth/Micrometer Tracing + Zipkin，或 SkyWalking 这种带 APM 界面的。

### 14. 数据库是一个实例多库还是每服务独立库？为什么？跨服务的联表查询怎么处理？

**答：** 是**一个 MySQL 实例、一个库（`library_db`），6 个服务共用**。

**为什么**：这是我要如实说的一点——**这是原设计的取法，不是微服务该有的形态**。按微服务原则应该"每服务独立库"（Database per Service），否则：服务之间可以绕过接口直接读写别人的表（统计服务就是这样）、表结构变更无法独立演进、也没法按服务做独立的容量规划。

**跨服务联表查询怎么处理**：正因为共库，**项目里根本不需要跨服务联表**——统计服务直接在自己服务里 join 同一库的表就行。这是共库带来的"方便"，也是它的"代价"。

**如果改成每服务独立库**：跨服务查询要改成"接口聚合"（调用方拿 id 列表，逐个服务查回来在内存里拼）或"数据冗余"（把展示需要的字段冗余一份，用消息同步）。本项目里预约表已经做了一部分冗余——它存了 `room_name`、`seat_name`，就是为了列表展示时不用回查房间和座位。

## B. 高并发抢座与生成列唯一索引

### 15. "生成列 + 唯一索引"到底是什么？生成列语法怎么写？STORED 与 VIRTUAL 有何区别，你选了哪个？

**答：** 生成列（Generated Column）是**由其他列计算出来的列**，值不靠应用写入，而是由数据库按表达式算出来。语法：

```sql
active_seat_key VARCHAR(80) GENERATED ALWAYS AS (
    CASE WHEN status IN ('PENDING','CHECKED_IN')
         THEN CONCAT(seat_id, ':', `date`, ':', time_slot)
         ELSE NULL END
) STORED
```

**STORED 与 VIRTUAL 的区别**：`STORED` 把计算结果**实际存进表**（占存储、写时计算、可以直接建索引）；`VIRTUAL` 不存值，读的时候实时算（不占存储，但每次读都要算）。

**我选了 STORED**，原因有两点：一是它更适合"结果要被频繁用于约束和查询"的场景；二是 `STORED` 生成列在**唯一索引**和后续按它做查询时行为更直观，不需要推演 MySQL 在什么情况下会物化、什么情况下回表重算。代价是每行多占约几十字节，以及每次更新相关列都要重算并同步到索引里。

### 16. 你的生成列表达式具体长什么样？它是如何表达"同一座位 + 同一时段"的？

**答：** 表达式就是把"座位 + 日期 + 时段"拼成一把键，但在**非有效状态下返回 NULL**：

```sql
CASE WHEN status IN ('PENDING','CHECKED_IN')
     THEN CONCAT(seat_id, ':', `date`, ':', time_slot)
     ELSE NULL
END
```

**为什么这样能表达约束**：这把键唯一 → 一个座位在一个日期的一个时段上只能有一条有效预约。而 `CANCELLED`、`BREACH`、`RELEASED` 这些历史状态取 `NULL`，**MySQL 的唯一索引允许多个 NULL**，所以历史记录可以无限保留、互不冲突。

**这就是整个设计的核心技巧**：MySQL 没有"部分索引"（不能只对满足条件的行建唯一索引），所以用"生成列 + NULL 语义"**模拟出部分唯一索引**。

对应索引：`UNIQUE KEY uk_reservation_active_seat (active_seat_key)`。

### 17. 如果用户选择任意时间段（如 9:10–11:35），区间重叠能否用唯一索引表达？不能表达时你会怎么办？

**答：❌ 当前不支持任意时间段**，这个设计里时段是枚举的：`MORNING(08:00–12:00)`、`AFTERNOON(12:30–17:30)`、`EVENING(18:00–22:00)`。所以"区间重叠"这个问题在当前模型里**不存在**——同一时段的值本身就是固定的三个字符。

**如果真要做任意时间段，唯一索引就表达不了了**，因为"两条区间是否重叠"是区间代数问题（`a.start < b.end AND b.start < a.end`），不是值相等。可行的方案有三条：

1. **时间片离散化**：把时间切成固定粒度（比如 30 分钟）的槽位，一条预约对应多个槽位行，对 `(seat_id, date, slot_no)` 建唯一索引。代价是行数变多，但完全可以靠唯一索引解决。
2. **数据库层加排他约束**：PostgreSQL 有 `EXCLUDE USING gist (seat_id WITH =, tsrange WITH &&)` 能直接表达区间互斥，**MySQL 没有对应能力**。
3. **应用层加锁 + 串行化**：按 `(座位, 日期)` 加锁，锁内查重叠再插入。可靠性依赖锁，比数据库约束弱。

**我的选择会是第 1 种**——把"重叠"问题转化成"相等"问题，让数据库约束继续兜底，这跟当前设计是同一个思路。

### 18. 唯一索引如何区分"有效预约"与"已取消/历史预约"？取消后同一时段能否再次预约？状态列参与唯一键会带来什么问题？

**答：** 靠**生成列在非有效状态下返回 NULL** 来区分。`PENDING`/`CHECKED_IN` 是有效状态，取值；其余状态取 NULL。

**取消后能否再次预约：能，我实测验证过。** 流程是：把原记录改成 `CANCELLED` → 它的 `active_seat_key` 立刻变成 NULL → 唯一的约束位释放 → 新的预约可以插入同一把键。实测结果里两条记录并存，只有新的那条 `active_seat_key` 非空。

**如果直接把 status 放进唯一键会怎样**（这是个常见错误）：`UNIQUE(seat_id, date, time_slot, status)` 会导致两件坏事：
1. **不允许第二条 CANCELLED**——因为前三个列相同、`status` 也相同，用户取消两次同一个座位时段就会失败；
2. 不同状态的历史记录数量被限制（比如只能有一条 `BREACH`）。

**根本原因是"唯一性只能对所有行成立，而我要的是只对有效行成立"**——所以必须让无效行"不参与"唯一性，`NULL` 就是这个"不参与"的开关。

### 19. MySQL 版本对生成列建索引有什么限制？VIRTUAL 列能否建唯一索引？

**答：** 生成列从 **MySQL 5.7 开始支持**，本项目的 DDL 里也标注了依赖 5.7+。

**VIRTUAL 列可以建索引**（包括唯一索引），这是 5.7 就支持的特性——二级索引里存的是计算后的值，所以能基于它做唯一性约束。区别在于：
- **VIRTUAL**：值不存表，建索引时索引里存该值；不建索引时读该列要实时算。
- **STORED**：值存表，索引也存。

**几个实际限制要注意**：表达式必须**确定性**（不能用 `NOW()`、`RAND()`、子查询）；不能引用 `AUTO_INCREMENT` 列；生成列可以引用其他生成列，但不能循环引用；另外生成列的表达式**不能直接改**（要改得先删列再加）。

**我选 STORED** 的另一个理由是：这个键既要被唯一索引用、也可能被查询用，STORED 的行为最好预测。

### 20. 唯一索引冲突时抛出什么异常？如何转换成"该座位已被预约"的友好提示？在全局异常处理器还是业务层捕获？

**答：** 冲突时 MySQL 报 `ERROR 1062 Duplicate entry`，经 MyBatis-Spring 的异常翻译后，在 Spring 里表现为 **`org.springframework.dao.DuplicateKeyException`**。

**在哪里捕获：在业务层，而且必须在这个 Service 方法的"事务边界之外"。** 具体写法是：

```java
String lockToken = redisLock.tryLock(lockKey, USER_LOCK_TTL);
try {
    return transactionTemplate.execute(status -> doCreateReservation(...));
} catch (DuplicateKeyException e) {      // ← 在事务外捕获
    log.info("并发抢座被唯一索引拦截: seatId={}, date={}, timeSlot={}", ...);
    throw new IllegalStateException("该座位该时段刚刚被预约，请选择其他座位");
} finally {
    redisLock.unlock(lockKey, lockToken);
}
```

**为什么不在全局异常处理器统一处理**：一是**这里需要把异常翻译成业务语义**（"座位被抢了"而不是"数据重复"），二是我要**打一条带业务字段的日志**便于排查并发的真实发生频率，三是不同接口对同一异常的处理可能不同。全局处理器留着兜底未预期的异常，业务异常在业务层转。

### 21. 有没有对比过"先查询再插入"与"直接插入靠唯一索引兜底"？两者的并发正确性与性能差异如何？

**答：都有，而且是配合使用的**，这也是本项目最值得讲的一个点。

- **先查询**（`count` 座位占用）存在的意义是**给用户友好提示**：绝大多数冲突是"已经有人约了"这种稳态冲突，查一次就能直接告诉用户"该座位该时段已有预约"，不用让数据库抛异常。
- **唯一索引**是**并发正确性的最终保证**：查和插之间有时间窗口，两个请求可能同时查到"没人约"，然后都去插入——这时只有唯一索引能挡住第二个。

**性能上**：先查是一次索引命中，成本很低；靠唯一索引兜底则要触发一次**插入失败 + 事务回滚**，代价明显更高。所以理想形态是"**用查询承担绝大多数冲突的友好提示，用唯一索引兜住真并发**"。

**只靠先查是错的**（会超卖），**只靠唯一索引也是不友好的**（所有冲突都走异常路径、且用户看到的报错语义差）。这个组合拳我实测验证过：8 线程并发抢同一座位，最终 1 条成功、其余走异常路径被拦。

### 22. 一次预约请求的完整链路（网关 → 服务 → 缓存/锁 → 数据库）中有几处校验？为什么不能只在最前面查一次？

**答：** 一共 **5 层**校验，每层职责不同：

| 层 | 校验内容 |
| --- | --- |
| 1. 网关 | 路由匹配（本项目网关不做业务鉴权，只保护自己的文档页） |
| 2. 过滤器 | JWT 验签 + Redis 白名单 + 账号状态（`state=2` 禁用直接 401） |
| 3. Controller | 参数绑定与格式校验（`@Valid`、必填字段） |
| 4. Service（锁内、事务内） | 时间窗合法性（不可预约过去/超 7 天/时段已结束/距结束不足 30 分钟）、座位存在且启用、封禁检查、**一人一约**、座位占用查询 |
| 5. 数据库 | `uk_reservation_active_seat` 唯一索引兜底 |

**为什么不能只在最前面查一次**：因为被校验的对象是**会变的共享状态**。所有校验在"查"的那一刻都是正确的，但"查到"和"写入"之间有窗口，别的请求可能已经把状态改掉了。这类问题叫 **check-then-act（检查-执行竞态）**，光靠"多加几次检查"解决不了，**必须由"原子性"保证**——要么用锁把窗口关掉（第 4 层），要么用数据库约束让第二次写入直接失败（第 5 层）。本项目的做法是两者都上。

### 23. 为什么用数据库唯一索引兜底，而不是只用 Redis 预占座位？两者各自解决什么问题？

**答：** 因为**这两者保证的规则根本不同**，不是二选一的关系：

- **Redis 锁**保护的是"**一个账号只能有一条有效预约**"。这条规则**没法用数据库索引表达**（管理员可以代人预约、历史记录要保留、且它约束的是"用户"而不是"座位"），所以我用锁把同一用户的请求串行化。
- **唯一索引**保护的是"**同一座位同一时段最多一条有效预约**"。这是可以用数据库约束表达的，而且数据库约束是**所有并发路径上最强的保证**——它不依赖 Redis 是否可用、不依赖锁有没有过期、不依赖是不是多实例。

**换句话说**：锁是"减少竞争、保护没法用约束表达的业务规则"，唯一索引是"最终的正确性保证"。反过来如果**只用 Redis 预占**，一旦出现 Redis 主从切换丢锁、锁 TTL 到期而业务还没提交、或者有人绕过应用直接写库——超卖就会真实发生。数据库约束是最后一道**不依赖外部组件**的防线。

### 24. 生成列对插入性能、binlog 复制有什么影响？主从环境下有没有观察到不一致？

**答：** **本项目没有做主从，所以我没有任何主从环境下的实测数据**，这一条我只能讲原理，不能编结论。

**插入性能**：`STORED` 生成列在写入时要计算表达式并把结果同步写进索引。本项目的表达式是 `CASE` + `CONCAT` 三个字段的拼接，成本很低，但要注意**它会让每一次涉及这些列的更新都变成"更新 + 维护索引"**——对 `status` 的每次流转（预约→取消→违约）都要重算并更新唯一索引，这是真实开销。`VIRTUAL` 列不存值，写开销更小。

**binlog 方面**：MySQL 在 binlog 里记录的是**行的最终状态**（`binlog_row_image=full` 时包含生成列的值），从库重放时**不重新计算生成列表达式**，而是直接写入主库算好的值。所以理论上主从的生成列值应当一致。

**真正的风险点**（如果要上主从，我会重点验证）：主从如果**版本不一致**对生成列的表达式求值可能有差异；另外 `binlog_format=STATEMENT` 下涉及生成列的语句可能被记录成语句而非行，会引入不确定性——**生产上生成列场景我会强制 `ROW` 格式**。

### 25. 预约表、座位表、房间表的表结构与索引怎么设计？查"某房间某时段可用座位"走的是什么索引？

**答：** 三张表的核心字段与索引：

**`reservation`（预约主表）**——除了业务字段，关键是那个生成列：
```sql
active_seat_key VARCHAR(80) GENERATED ALWAYS AS (...) STORED,
UNIQUE KEY uk_reservation_active_seat (active_seat_key),
KEY idx_reservation_user_status (user_id, status),       -- 一人一约检查
KEY idx_reservation_seat_slot (seat_id, `date`, time_slot),
KEY idx_reservation_status_expires (status, expires_at), -- 定时清理扫描
KEY idx_reservation_date_status (`date`, status)
```

**`seat`（座位）**：`KEY idx_seat_room (room_id)`、`KEY idx_seat_pos (room_id, row_no, col_no)`、`KEY idx_seat_qr_token (qr_token)`（扫码签到按 token 查）。

**`room`（房间）**：`KEY idx_room_floor (floor)`。

**"查某房间某时段可用座位"的实际情况**：本项目**没有做这种反查**——座位可用性是通过**前端拿房间的 `seat_info` 二维布局 + 当前时段的有效预约列表，在内存里做差集**得到的（`RoomController` 把预约对应的格子在布局数组里标成 1 或 3）。所以没有专门为它建索引。

**如果要做反查**：先按 `idx_reservation_seat_slot` 或 `idx_reservation_date_status` 拿到该时段已占用的 `seat_id` 集合，再与 `room_id` 下的座位做差；**注意索引列顺序**——把等值条件列放前面（`date`、`time_slot` 都是等值），如果要按房间过滤，更合适的是 `(date, time_slot, room_id)` 或直接按 `room_id` 先缩小座位集合。

### 26. "历史记录完整保留 + 有效预约唯一"这一目标，用软删除加唯一索引会遇到什么矛盾？你怎么解决？

**答：** 矛盾很具体：**软删除（`deleted=1`）不会让行消失，所以它仍然参与唯一索引**。假设 `UNIQUE(seat_id, date, time_slot, deleted)`——删掉第一条后 `deleted=1`，再删第二条又是 `deleted=1`，**两次软删的记录会因为前三列相同而撞唯一键**，用户"取消两次"就失败了。等价地，任何"同一对象允许有多个历史态"的表，都会遇到这个矛盾。

**本项目的解法有两个层面：**

1. **根本手段：让无效行在约束里"不存在"**。这就是那个生成列的作用——非有效状态返回 `NULL`，而**唯一索引允许多个 NULL**。所以历史记录有多少条都不冲突。这比软删除标记更彻底：软删除只是标记状态，`NULL` 是**真的从约束里退出**。
2. **本项目没有用软删除**：`reservation` 表没有 `deleted` 列，删除就是物理删除（管理员删除预约那条接口）。历史是靠**状态流转**保留的（`CANCELLED`/`BREACH`/`RELEASED`），不是靠 `deleted` 标记。

**如果业务上非要软删除**，常见两种解法：把删除时间戳并进唯一键（`UNIQUE(seat_id, date, time_slot, deleted_at)`，因为时间戳各不相同所以多个删除行不冲突），或者用"活动标记列 + NULL"（本质和本项目的做法一样）。**我倾向于后者**，语义更干净。

### 27. 如果业务扩展为"候补排队、到号自动分配座位"，当前数据模型需要做哪些改造？

**答：❌ 项目没做候补排队**，当前模型是"抢到了就有、抢不到就没有"。这个问题我只能给设计思路。

**改造要点：**

1. **新增候补表** `reservation_waitlist`：`(seat_id 或 room_id, date, time_slot, user_id, enqueue_seq, status)`，索引 `(seat_id, date, time_slot, enqueue_seq)` 用于按顺序取号。**排序键要用单调递增的序号而不是时间戳**，避免同一毫秒并发时顺序不稳。
2. **唯一约束要分开设计**：候补和正式预约是两套唯一性——候补要允许"一个人排多个座位"，所以不能把候补也塞进 `active_seat_key` 那套约束里，否则会和"一人一约"打架。
3. **座位释放时的触发点**：现在座位释放有三个来源（取消、超时未签到、时段结束），所以"通知候补"要挂在**状态流转成功之后**——正好本项目里状态流转都是带原状态条件的原子 `UPDATE`，返回影响行数为 1 才说明真的释放了，这就是天然的触发信号（且天然幂等，多实例不会重复通知）。
4. **一致性要求**：分配座位必须**原子**——把"候补记录改为已分配 + 插入正式预约"放进一个事务，并且**仍然依赖 `uk_reservation_active_seat` 兜底**，防止候补分配和正常抢座同时插入同一座位。
5. **超时机制**：候补到号通常要给用户一个确认时限，超时自动顺延给下一个——这就复用了本项目现有的"`expires_at` + 定时扫描 + 原子状态流转"那套模式，不用新造轮子。

### 28. 8 线程并发抢座用例具体怎么写的？如何确保真正同时发起（CyclicBarrier 等）？断言了哪些结果？

**答：** 用例在 `SeatBookingConcurrencyTest` 里，用 **`ExecutorService` + 双 `CountDownLatch`** 实现真正的同时起跑：

```java
CountDownLatch startGate = new CountDownLatch(1);   // 发令枪
CountDownLatch doneGate  = new CountDownLatch(n);   // 等所有线程结束
for (Runnable task : tasks) {
    pool.submit(() -> {
        try { startGate.await(); task.run(); success.incrementAndGet(); }
        catch (Exception ignored) { /* 预期中的失败 */ }
        finally { doneGate.countDown(); }
    });
}
startGate.countDown();                    // 所有线程在这之后才真正开始跑
doneGate.await(30, TimeUnit.SECONDS);     // 最多等 30 秒，避免挂死
```

**为什么用 `CountDownLatch` 而不是 `CyclicBarrier`**：这里只需要"发令"一次，`CountDownLatch` 语义更直接；`CyclicBarrier` 适合需要多轮同步的场景。另外**每个线程用不同的 userId**，这样"一人一约"的锁不会互相干扰，测的就是座位维度的竞争。

**断言了三条：**
1. `success == 1` —— 8 个线程里只有 1 个成功；
2. 数据库里该座位该时段**有效预约只有 1 条**（按状态过滤，**直接查库校验，不信内存计数**）；
3. 另外两条用例分别验证"同一用户并发提交两个不同座位只产生 1 条有效预约"和"取消后该座位可被重新预约"。

**⚠️ 一点要如实说明**：这是**单机验证**（一个 JVM、一个数据库）。多实例下这组用例本身跑不了（需要独立进程 + HTTP 调用），但**结论仍然成立**——因为约束在数据库上，不在应用内存里。详见下一题。

### 29. "同一座位仅 1 人成功"的结论是单机验证还是多实例验证？多实例下唯一索引是否依然成立？

**答：** **是单机验证**，我应该主动说明这一点：用例跑在一个 Spring 上下文里，8 个线程走的是同一个 `ReservationService` Bean、同一个数据库连接池——**验证的是"应用内并发"，不是"多实例并发"**。

**多实例下唯一索引是否依然成立：成立，而且是这类问题里最可靠的一层。** 理由是：
- 唯一索引是**数据库层的约束**，所有实例最终都写同一个数据库，无论请求从哪个实例进来、线程怎么调度，第二次插入都必然撞唯一键；
- 它**不依赖 Redis 锁**——就算多实例下 Redis 锁因为 key 设计或 TTL 失效没有兜住，数据库仍然会拦住；
- 它也**不依赖应用是否有状态**，所以横向扩容不改变结论。

**⚠️ 有一点必须补充**：结论"多实例下依然成立"指的是**座位维度**。**用户维度**（"一人一约"）靠的是 Redis 锁 + 查询，多实例下锁仍然有效（锁在共享 Redis 里），但如果 Redis 不可用，这条规则就退化成"先查再插"的竞态——**这是当前设计里依赖外部组件的脆弱点**，我可以主动指出来。

**如果要做多实例验证**：起两个不同端口的实例（或用容器起两份），用 HTTP 客户端并发调网关，断言成功响应只有 1 个、库里有效记录 1 条。用例本身要改造成 `@SpringBootTest(webEnvironment = RANDOM_PORT)` + `TestRestTemplate`，或者干脆用外部压测脚本。

## C. Redis 分布式锁与 Lua

### 30. 分布式锁为什么选 Redis 而不是 ZooKeeper、etcd 或数据库？你的场景最看重锁的哪些特性（性能、可靠性、公平性）？

**答：** 这个场景最看重的是**性能**和**实现简单**，公平性完全不重要。理由是：锁的临界区极短（几次数据库操作），锁的持有时间是毫秒级；而抢座冲突是**高频短临界区**——用 ZooKeeper 每次加解锁都要走 ZAB 协议和临时顺序节点，吞吐量差一个数量级，为了一个 10ms 的临界区付这个成本不值。

**四者对比：**
- **Redis**：性能最好，`SET NX PX` 一条命令搞定；缺点是**极端情况下不可靠**（主从异步复制，主挂了可能丢锁）。
- **ZooKeeper / etcd**：基于**一致性协议**（ZAB / Raft），可靠性更高，还有临时节点/租约能在会话断开时自动释放锁；代价是延迟高、吞吐低。
- **数据库**：`SELECT ... FOR UPDATE` 或有唯一索引的锁表也能做，好处是不引组件，坏处是锁竞争直接压到数据库、容易和业务事务耦合出死锁。

**为什么这里可以接受 Redis 的不可靠**：因为**锁不是唯一的保证**，座位维度的正确性由数据库唯一索引兜底。锁失效的后果只是"多几个请求走到数据库然后失败"，而不是"超卖"。**如果这个场景要求锁是唯一保证（比如扣款），我会改用 etcd/ZooKeeper 或带 fencing token 的方案。**

### 31. 锁的 key 与 value（持有者标识）怎么设计？为什么要存持有者标识？

**答：** key 是 `lock:reservation:user:{userId}`（用 `RedisDistributedLock.key(...)` 统一拼接，避免各处写法不一致）；value 是**随机 UUID**，也就是持有者标识。

**为什么要存持有者标识**——这是防止"误删他人锁"的关键。假设不存（value 写 `1`），会出这个事故：

1. A 拿到锁，业务卡住（GC 停顿、网络慢），**锁 TTL 到期自动释放**；
2. B 拿到同一把锁，正在执行业务；
3. A 醒过来执行 `DEL lock:key` —— **把 B 的锁删掉了**；
4. C 于是也能拿到锁，B 和 C 并发执行 → 临界区保护失效。

value 用了 UUID 之后，释放时先比对"这把锁现在是不是我持有的"，不是我的就不删。**注意这个比对必须和删除一起原子完成**（见第 34 题的 Lua）。

**key 为什么按用户而不是按座位**，见第 36 题。

### 32. 加锁为什么推荐 `SET key value NX PX` 而不是 SETNX+EXPIRE？两条命令的问题在哪？

**答：** 因为 `SETNX` + `EXPIRE` 是**两条命令，两条命令之间不是原子的**。经典事故：

1. A 执行 `SETNX` 成功——**拿到锁**；
2. A 在 `EXPIRE` 之前**进程崩溃 / Redis 连接断开 / 网络抖动**；
3. 这把锁**永远不会过期**（没有设置 TTL）→ 死锁，**后续所有用户都抢不到座位**，而且只能人工删 key 才能恢复。

`SET key value NX PX 10000` 把"不存在才设置"和"设置过期时间"合并成**一条原子命令**，从根上消除了这个窗口。**另外 Redis 2.6.12 之后 `SET` 就支持 `NX`/`PX` 选项了**，所以老写法没有任何理由继续用。

**项目里的实际调用**是 Spring Data Redis 的 `opsForValue().setIfAbsent(key, token, Duration)` —— 它内部发的就是带 `PX` 的 `SET NX`。

### 33. 锁的过期时间设多少？业务执行超时怎么办？需要看门狗续期吗？Redisson 是如何处理的？

**答：** 项目里设 **10 秒**（`USER_LOCK_TTL`）。选择依据是：临界区只有几次数据库操作（一次占用查询、一次插入，加一次提交），正常在几十毫秒内完成，10 秒已经是两个数量级的余量。

**业务真的超时了怎么办**：**设计上不依赖"锁一定不过期"**。如果锁提前过期，后果是别的请求能进来，但它最终会在插入时撞唯一索引失败——**不会超卖**，最坏是用户看到"该座位刚刚被预约"。**这个设计的前提是"锁只是减少竞争、数据库约束才是最终保证"**；如果锁是唯一保证，那就必须处理续期。

**需要看门狗吗**：本项目**不需要**，因为临界区足够短、且不依赖锁的强保证。看门狗（watchdog）解决的是"业务执行时间不确定、可能长于 TTL"的场景。

**Redisson 的处理方式**：`lock()` 不指定 leaseTime 时，默认 `lockWatchdogTimeout` 30 秒，并**注册一个定时任务每 10 秒（TTL/3）给锁续期**，只要客户端还活着锁就不会过期——**所以它其实是"业务不结束、锁不释放"的语义**。用 Redisson 要特别注意：**必须显式传 leaseTime 或确保 finally 里 unlock**，否则客户端进程被杀后锁要等 30 秒才自动释放。

### 34. 解锁为什么必须用 Lua？请描述不用 Lua 时"误删他人锁"的典型场景。

**答：** 因为"**比对 value**"和"**删除 key**"是两步操作，**两步之间同样有竞态窗口**：

1. A 持有锁（value = tokenA），业务卡住，**锁 TTL 到期**；
2. B 拿到同一把锁（value = tokenB）；
3. A 执行 `GET lock:key` —— 如果 A 是在**锁过期前**发起这次 GET 的，它可能读到 `tokenA`、**比对通过**；
4. **就在这一刻**，锁到期、B 拿到锁把 value 改成 `tokenB`；
5. A 执行 `DEL` → **删掉的是 B 的锁**。

所以必须让"读值比对 + 删除"在 Redis 服务端**原子执行**，而 Redis 保证**单个 Lua 脚本的执行是原子的**（单线程执行脚本、中间不处理其他命令），于是没有窗口。项目的脚本就一行逻辑：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end
```

**Redis 的原子性边界要讲清楚**：Lua 脚本的原子性是"**执行期间不被其他命令打断**"，**不是"事务回滚"**——如果脚本中途报错，前面执行过的写操作不会回滚。所以脚本要写得简单、不要在里面做复杂逻辑。

### 35. 自研锁与直接用 Redisson 的差别是什么？各自的风险与收益？

**答：** 本项目**是自研的**（`RedisDistributedLock`，约 50 行）。做这个选择的原因是：这个场景只需要"**不可重入、短持有、不续期**"的简单互斥锁，Redis 的 `SET NX PX` + Lua 释放已经完整覆盖，引入 Redisson 会多一个依赖和一层抽象。

**Redisson 的收益（自研的代价）：**
- **可重入**（用 Hash 记录重入次数）——本项目不需要，因为同一线程不会二次加锁；
- **看门狗自动续期**——本项目不需要，因为临界区短；
- 还有 `RedLock`、读写锁、信号量等语义，以及**久经考验的边界处理**（超时、连接断开、脚本降级）。

**自研的风险**（我应该诚实说）：手写锁的边界情况很容易漏——比如**没有处理"Redis 命令超时"**（`setIfAbsent` 超时时锁到底建没建立是不确定的）、没有可重入、没有续期。**生产环境我倾向于直接用 Redisson**，把精力放在业务上；**自研的合理前提是"锁不是唯一保证"**，正是本项目的情况。

**这个取舍怎么讲才加分**：不是"我自研了锁所以牛"，而是"**我评估过这个场景不需要 Redisson 的那些能力，且锁不是唯一防线，所以选了更简单的实现；如果换成扣款这类锁是唯一保证的场景，我会用 Redisson 甚至 etcd**"。

### 36. 锁粒度为什么按"用户"而不是按"座位"？如果按座位加锁，好处和坏处分别是什么？

**答：** 这是本项目最核心的一个设计决策，答案是：**因为锁和唯一索引各自保护不同的规则，锁要保护的恰恰是"用户维度"那条。**

- **座位维度**（"同一座位同一时段只能有一条有效预约"）**用数据库唯一索引保证**——这是所有并发路径上最强的保证，不需要锁。
- **用户维度**（"一个账号只能有一条有效预约"）**没法用唯一索引表达**（管理员可以代人预约、历史要保留、约束对象是用户不是座位），所以**必须用锁**把同一用户的请求串行化。

**如果按座位加锁**：好处是同一座位的并发请求会串行，数据库不会频繁撞唯一键（减少异常路径）。**坏处更明显**：
1. **热点座位的锁变成瓶颈**——所有抢这个座位的人都在等同一把锁，吞吐被锁的串行化限制住，而实际上他们中的大多数注定失败，等锁是纯浪费；
2. **保护不了"一人一约"**——同一用户抢**不同座位**时锁 key 不同，两个请求会并发放行，用户最终有两条有效预约，业务规则被破坏；
3. 锁的粒度越细，**死锁风险越高**（如果要同时锁多个资源，得约定加锁顺序）。

**更好的形态**（我可以指出当前设计的不足）：`用户锁 + 座位唯一索引` 已经是对的；如果要进一步降低数据库异常路径，可以再加一层**座位维度的锁或"座位状态"的原子更新**，但那是拿吞吐换异常率，**这个业务量级不值得**。

### 37. 获取锁失败时是立即返回、自旋还是阻塞等待？大量请求同时失败会造成什么体验问题？

**答：** 项目里是**立即返回失败**——`tryLock` 拿不到就抛 `IllegalStateException("您有一个预约请求正在处理，请勿重复提交")`，**不自旋、不阻塞**。

**为什么这样选**：按用户加锁之后，**锁冲突的语义是"同一个用户在极短时间内重复提交"**（双击、弱网重试、脚本刷接口），而不是"高并发抢同一资源"。对于重复提交，**正确的响应就是拒绝并提示**，自旋等待毫无意义——用户等 200ms 再提交一次，结果还是同样的重复请求。而且立即失败能**把压力挡在数据库之前**（失败请求不消耗数据库连接）。

**大量请求同时失败会造成什么体验问题**：如果这个提示大面积出现，说明**不是用户在重复提交，而是系统出问题了**——比如锁 TTL 设置过短、或 Redis 变慢导致锁实际持有时间被拉长。所以这条错误的频率**是个很好的监控指标**：正常应该是低频偶发，一旦飙升就说明锁的配置或 Redis 健康度出了问题。

**如果场景换成"抢同一座位"**（即按座位加锁），那立即失败就不合适了——用户希望的其实是"排队等结果"，这时应该用**阻塞等待 + 超时**（Redisson 的 `tryLock(waitTime, leaseTime, unit)`），但要配合**限流**，否则等待线程会堆积把连接池和内存拖垮。

### 38. Redis 主从切换导致锁丢失（Redlock 争议）你怎么看？在你的部署形态下这是真实风险吗？

**答：** **当前部署形态下不是真实风险——因为用的是单实例 Redis，没有主从。** 但我要如实说明：这不是"设计上规避了风险"，而是**部署上恰好没有这个场景**；一旦上主从，风险就真实存在。

**风险本身是什么**：Redis 主从是**异步复制**。A 在主节点拿到锁 → 主节点还没把这条写命令同步给从节点就宕机了 → 从节点提升为新主 → **这把锁在新主上不存在** → B 也能拿到同一把锁 → 互斥失效。这类问题**没有任何基于单一 Redis 主从的实现能消除**，包括 Redisson 的普通锁。

**Redlock 的争议（我了解到的）**：antirez 提出"向 N 个独立 Redis 实例加锁，多数派成功才算拿到"来规避单点；但 Martin Kleppmann 反驳说，**Redlock 依赖各实例的时钟假设和"锁只在租约期内有效"的不变量，而这些在没有 fencing token 的情况下无法保证正确性**——因为一旦发生 GC 停顿或网络延迟，客户端以为自己还持有锁、实际早已过期，它对共享资源的写入会覆盖新持有者的写入。**他的核心论点是：分布式锁要正确，必须让被保护的资源本身能拒绝过期持有者的写入（fencing token / 版本号递增）。**

**我的结论**：本项目的情况恰好印证了 Kleppmann 的观点——**真正保证正确性的不是锁，而是数据库端的唯一索引**。所以主从切换丢锁也不会超卖。**如果哪天锁变成唯一保证**，我不会指望 Redlock，而会：要么用 etcd/ZooKeeper 这类一致性协议，要么给资源加 **fencing token**（比如用自增版本号，写时带上并让数据库拒绝过期版本）。

### 39. 如果 Redis 整体不可用，抢座功能如何降级？纯靠数据库唯一索引是否足够？

**答：** **当前的实现无法降级——Redis 挂了整条预约链路就直接不可用**，这一条我要如实说，不能粉饰。

原因有两处依赖：一是 `RedisDistributedLock.tryLock` 会抛异常；二是 **JWT 的 Redis 白名单**在 `JwtAuthenticationFilter` 里是硬依赖（`hasToken` 查不到就 401），所以连登录鉴权都会失效。

**纯靠数据库唯一索引是否足够？** 分两个层面回答：
- **座位维度：足够。** 唯一索引是数据库约束，Redis 挂了它照样拦得住，**不会超卖**。
- **用户维度：不够。** "一人一约"靠的是"Redis 锁 + 锁内查询"，Redis 不可用后这条会退化成 check-then-act 竞态，**同一用户可能产生两条有效预约**。

**如果要做降级，我的方案是分级的：**
1. **锁降级为"数据库锁"**：`SELECT ... FOR UPDATE` 按用户维度锁一行（比如锁 `user` 表该用户的行），或在应用内用 `ConcurrentHashMap` 的用户级 `ReentrantLock`——**单实例下后者完全够用且零依赖**，多实例下退化为"同一用户请求可能落到不同实例"，此时接受用户维度规则的**弱化**（座位维度仍由唯一索引保证，不会超卖）。
2. **鉴权降级**：白名单校验失败时**不能一律放行**（那等于关闭鉴权），而是**只做 JWT 验签、跳过白名单**——这样登出立即失效的能力暂时丧失（退化为 TTL 到期失效），但鉴权本身仍在。
3. **监控与开关**：这两个降级都要有显式开关和告警，不能静默生效。

**权衡原则**：**座位不能超卖是硬要求（由数据库保证），"一人一约"是业务规则（Redis 不可用时可以弱化）**——降级的取舍要落在"哪条规则绝不能破"上。

### 40. Lua 脚本执行是原子的，但脚本复杂或耗时会阻塞什么？你的脚本逻辑有多复杂？

**答：** **阻塞的是整个 Redis 实例**。Redis 执行命令是单线程的，Lua 脚本在服务端被当作**一条命令**执行，脚本运行期间**不会处理其他任何客户端的命令**（包括读）。所以：慢脚本 = 全实例卡住；更糟的是脚本如果**进入死循环**，Redis 会一直卡到 `lua-time-limit`（默认 5 秒）之后才开始对其他命令返回 BUSY 错误，而且这个脚本**不会被自动杀掉**。

**我的脚本极简**，就一次 `GET` + 一次比较 + 一次 `DEL`：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end
```

时间复杂度 O(1)，耗时在微秒级。**几条我遵循的规则**：脚本里不做循环、不做批量操作、不做复杂计算；**key 必须通过 `KEYS[]` 传**（不能在脚本里拼 key，否则 Cluster 下无法路由）；不要在脚本里做 `KEYS *` 这类扫描。

**如果确实需要复杂逻辑**（比如批量扣减），正确做法是**拆成多个小脚本**，或者把逻辑放到应用层用 pipeline 组合，而不是写一个大脚本。

### 41. Redis Cluster 下 Lua 脚本的多个 key 必须同 slot，你如何保证？用过 hash tag 吗？

**答：❌ 本项目是单实例 Redis，没有涉及 Cluster，也就没有用 hash tag。** 这一条我只能讲原理。

**问题本质**：Cluster 把 key 按 `CRC16(key) % 16384` 分到不同节点，**一个 Lua 脚本只能在一个节点上执行**，所以脚本里所有 key 必须落在同一个 slot，否则直接报错 `CROSSSLOT Keys in request don't hash to the same slot`。

**hash tag 的用法**：把想让它们同 slot 的部分用 `{}` 包起来，**只有 `{}` 内的内容参与计算**。例如 `lock:{order:1001}:user` 和 `lock:{order:1001}:seat` 都会按 `order:1001` 计算，落在同一 slot。

**对本项目的意义**：我的释放脚本只操作**一个 key**（`KEYS[1]`），所以天然不存在 CROSSSLOT 问题——这也是"**锁脚本尽量只碰一个 key**"这条实践的好处。

**如果要做多 key 的原子操作**，我会用 hash tag 把两者绑到同一 slot；但要清楚代价：**同一 slot 的 key 会落在同一节点，热点会集中**——hash tag 用多了会破坏集群的均匀分布。

### 42. 怎么验证分布式锁的正确性？做过跨进程或跨机器测试吗？

**答：** **⚠️ 做了一部分，跨机器测试没做**，我如实说明边界。

**已经做的（`RedisDistributedLockTest`，5 个用例）：**
- **互斥性**：mock 掉 `ValueOperations`，第一次 `setIfAbsent` 返回 true 拿到 token、第二次返回 false 拿不到；
- **必须带 TTL**：验证调用参数里有 `Duration`（防止有人改成不带过期的写法，那会导致死锁）；
- **释放时传持有者 token**：验证 `execute(script, keys, token)` 的参数正确，确保"误删他人锁"的防护没有被改掉；
- **token 为空时不发命令**（空操作安全）；
- **key 拼接格式统一**。

**并发抢座用例**（`SeatBookingConcurrencyTest`）从**业务侧**间接验证了锁 + 唯一索引的组合：8 线程抢同一座位只有 1 个成功、同一用户并发提交两个座位只产生 1 条有效预约。

**⚠️ 没做的部分：**
- **跨进程/跨机器验证**——没做。跨进程要能证明"不同 JVM 之间锁真的互斥"，需要起两个进程或直接用 `redis-cli` 在锁被持有时尝试加锁；
- **锁在极端情况下的行为**没有专门测（TTL 到期后锁自动释放、持有者崩溃后锁的命运）。

**如果补，我会这样测**：用例 A 在 `tryLock` 后不释放并 sleep 超过 TTL，用例 B 在另一个线程/进程尝试加锁，断言 B 能拿到（证明 TTL 生效）；再用 `redis-cli` 手工验证 value 比对逻辑。

### 43. 锁与限流是否共用同一个 Redis 实例？如何避免相互影响？

**答：** **共用同一个 Redis 实例**，但**没有做隔离**——而且我这个项目**根本没有限流**（见第 10 题，Sentinel 已移除），所以实际上不存在"锁与限流互相影响"这个问题。

**共用实例时的典型影响路径**（这是原理，值得知道）：
1. **内存争抢**：限流的计数器/令牌桶如果 key 很多，可能触发 `maxmemory-policy` 淘汰，**把锁的 key 也淘汰掉**——这是最危险的一种，锁被淘汰等于锁消失。所以**锁的 key 绝不能被 LRU 淘汰**：实践上要么给锁配置独立的实例/db，要么确认 `maxmemory` 足够、或对锁用的 db 单独规划。
2. **慢命令互相拖累**：大 key 扫描（`KEYS`、超大 hash 的 `HGETALL`）或慢脚本会阻塞单线程，**限流的慢命令会连带拖慢加锁**。
3. **连接数**：两者共用一个连接池时，突发流量可能把连接打满。

**如果要做隔离，我的优先级是**：① 锁和限流的 key 用**不同的 db 或至少不同前缀**，并保证锁的 key 永不被淘汰策略选中；② 业务量再大就**物理隔离**（锁用一个独立的小实例，容量和超时都单独规划）；③ 禁掉/限制 `KEYS` 这类命令。

## D. 锁与事务的边界

### 44. "加锁必须在事务之外、释放必须在事务提交之后"——请完整解释原因，并说明不这样做会出现什么具体故障。

**答：** 原因归结成一句：**锁要保护的是"从读到写"的整个过程，而事务真正对外生效的时刻是提交，所以锁必须覆盖到提交之后。**

**如果"在事务提交前就释放锁"**（最常见的形式是在 `@Transactional` 方法内部加锁，方法返回时锁先释放、事务后提交），具体故障是：

1. 用户 A 的请求进入事务，锁内查询"该用户没有有效预约"，准备插入；
2. A 的方法体执行完，**锁在 finally 里被释放**——**但事务还没提交**（提交发生在代理的外层，在方法返回之后）；
3. 用户 A 的**第二个请求**（双击/重试）在同一时刻进入，立刻拿到锁，执行同样的查询——**它看不到 A 尚未提交的那条插入**；
4. 第二个请求校验通过，也去插入；
5. 两个事务先后提交 → **同一用户产生两条有效预约**，业务规则被破坏。

注意这里有个区别：如果两次请求是**同一座位**，那还能靠唯一索引兜住；但**"一人一约"没有任何数据库约束兜底，就真的破了**——这正是本项目必须把锁放在事务外的原因。

**这就是为什么本项目用 `TransactionTemplate` 显式控制顺序**：

```java
try {
    return transactionTemplate.execute(status -> doCreateReservation(...));  // 事务在这里提交
} finally {
    redisLock.unlock(lockKey, lockToken);                                    // 提交之后才释放
}
```

**还有一个更隐蔽的坑**：如果直接在方法上加 `@Transactional`，然后**在同类里调用另一个带 `@Transactional` 的方法**，因为自调用不走代理，**内层事务根本不生效**（见第 51 题）——那样连"锁和事务谁先谁后"都无从谈起，事务压根不存在。

### 45. 在 @Transactional 方法内部加 Redis 锁会发生什么？为什么会出现"后一个请求读到旧数据而校验通过"？请澄清这里 MVCC 快照读的真实表现。

**答：** 后果见上一题。这里我**特意澄清 MVCC 的精确表现**，因为"读到旧数据"这个说法很容易讲错：

**准确的说法不是"脏读"**（脏读是读到别人未提交的数据，InnoDB 在 RR 下不会发生）。真实机制是**一致性快照**：

- InnoDB 默认隔离级别是 **RR（可重复读）**，事务的**读视图（read view）在第一次快照读时建立**；
- 第二个请求的事务在锁内执行 `SELECT COUNT(*) ... WHERE user_id=? AND status IN ('PENDING','CHECKED_IN')` 时，它看到的是**自己 read view 建立时刻已提交的数据**；
- 第一个请求的插入**还没提交**，所以**对第二个事务不可见**——它读到的是"该用户没有有效预约"（这是**已提交状态的一致视图**，不是脏读）；
- 于是第二个事务认为自己可以插入，**两个事务都提交后，规则被破坏**。

**结论要讲成**：问题不是"读到了未提交的脏数据"，而是"**读到了一个已经过时、但当时确实成立的一致性快照**"。**MVCC 保证了读的一致性，但它保证不了"读到之后到你写入之前状态没变"**——后者只能靠**锁**（把窗口关上）或**约束**（让第二次写入失败）来解决。

**补充一个容易忽略的点**：如果第二个事务执行的是**当前读**（`SELECT ... FOR UPDATE`、`UPDATE`、`INSERT`）而不是快照读，它会读最新版本并加锁——**但"是快照读还是当前读"取决于语句类型**，这也是为什么"用快照读做业务校验"是不可靠的。

### 46. 为什么用 TransactionTemplate 而不是 @Transactional？编程式事务与声明式事务的差异与适用场景是什么？

**答：** 因为**加锁必须在事务之外、释放必须在提交之后**，而方法级的 `@Transactional` 无法表达这个顺序：注解的提交发生在**方法返回之后**（由代理完成），而方法内的 `finally` 会先执行——两者顺序天然是反的。所以必须用编程式事务把顺序显式写出来：

```java
String lockToken = redisLock.tryLock(lockKey, USER_LOCK_TTL);
if (lockToken == null) { throw new IllegalStateException("您有一个预约请求正在处理，请勿重复提交"); }
try {
    return Boolean.TRUE.equals(transactionTemplate.execute(status -> doCreateReservation(...)));
} catch (DuplicateKeyException e) {
    throw new IllegalStateException("该座位该时段刚刚被预约，请选择其他座位");
} finally {
    redisLock.unlock(lockKey, lockToken);
}
```

**两种事务的差异与适用场景：**
- **声明式（`@Transactional`）**：通过 AOP 代理实现，声明简单、和业务代码解耦，**适合绝大多数方法**——本项目里 `cancelReservation`、`checkIn`、`saveByAdmin`、批量删除这些**不需要在事务外拿锁**的方法就用的它。
- **编程式（`TransactionTemplate`）**：把事务边界写成代码，**适合需要精确控制边界顺序的场景**——就是这里：锁必须在事务外拿、在提交后放；另外**跨多个 DAO 且中途有非事务操作**、或需要按分支决定提交/回滚时也适合。

**顺带一个声明式的坑**：`@Transactional` 默认**只对 `RuntimeException` 回滚**，受检异常不回滚——所以项目里统一写成 `@Transactional(rollbackFor = Exception.class)`。

### 47. 你如何保证"事务提交之后"才释放锁？try-finally 够吗？TransactionSynchronizationManager.afterCommit 适合什么场景？

**答：** 分两个层面：

**（1）释放 Redis 锁：用 `try-finally` 就够，但前提是事务本身也是编程式的。** 因为 `transactionTemplate.execute(...)` 是**同步阻塞**的——它在返回之前就已经完成了提交（或回滚），所以 `finally` 里的 `unlock` 天然在提交之后执行：

```java
try {
    return transactionTemplate.execute(...);   // 返回时提交已完成
} finally {
    redisLock.unlock(...);                     // 所以这里必定在提交之后
}
```

**如果反过来写**（`@Transactional` 方法内部 `try-finally` 释放锁），`finally` 在方法体内执行，而提交在方法返回后由代理完成 → **顺序反了，锁先释放**，就是第 44 题的故障。

**（2）`TransactionSynchronizationManager.afterCommit` 适合"提交成功之后才该发生的副作用"**，本项目就用在**座位状态的 WebSocket 推送**上：

```java
if (TransactionSynchronizationManager.isSynchronizationActive()) {
    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
        @Override public void afterCommit() { broadcastSeatStatus(reservation, statusOverride); }
    });
} else {
    broadcastSeatStatus(reservation, statusOverride);
}
```

**为什么要这样**：如果直接在事务里推送，**一旦事务回滚，前端已经收到了一个并不存在的状态变化**——用户看到"座位已被预约"，但库里其实没这条记录，状态永久不一致。用 `afterCommit` 保证"**只有真正提交了才通知**"。

**两者的区别要点**：`afterCommit` 是"**提交后触发**"，它**没有能力回滚事务**，里面的异常也**不会影响已提交的事务**（异常会被吞掉并记日志），所以里面只适合做"通知类"的副作用，**不能放"必须成功"的业务逻辑**。

### 48. 如果进程在提交后、释放锁前崩溃，锁会怎样？业务会怎样？依赖 TTL 兜底是否存在窗口问题？

**答：** 先说结论：**业务是安全的，锁靠 TTL 自愈，但确实存在一个"用户被误拦"的短窗口。**

**逐步分析：**
1. 事务已提交 → **数据是持久化的，业务结果正确**（预约记录已在库里）。
2. 进程崩溃，`finally` 没执行 → **锁没有被删除**，它会在**最多 10 秒（`USER_LOCK_TTL`）后自动过期**。
3. 在这 10 秒内，如果该用户**再次发起预约请求**，`tryLock` 会失败 → 用户收到"您有一个预约请求正在处理，请勿重复提交"。
4. 但此时业务其实已经成功了 → **用户看到的是一个误导性的错误提示**，他可能以为没约上；如果他刷新列表，会看到预约其实已经存在（前端有 `activeCount` 接口可以拿真实状态）。

**所以：正确性没有受影响的窗口，只有"提示体验"的窗口**，最长 10 秒。

**可以怎么改进**：
- 让"锁"不再承担"防重复提交"的职责，改用**幂等键**：客户端带一个请求号，服务端在**数据库里**建幂等表或直接用唯一索引（本项目的 `(seat_id, date, time_slot)` 唯一索引已经是这个角色），这样"重复提交"返回的是**幂等的结果（成功）**而不是错误——比"报错让用户猜"更准确；
- 或者把锁 TTL 收得更短（比如 3 秒），但要保证大于正常情况下临界区的 P99，否则会引入新的竞态。

**一句话总结**：**"锁没释放"的后果是短暂的可用性问题，不是数据问题**——这正是把最终正确性交给数据库约束的好处。

### 49. 唯一键冲突被转为友好提示，这个捕获发生在事务内还是事务外？冲突回滚后锁的释放顺序会受影响吗？

**答：** **捕获发生在事务之外**，这一点很关键，看代码结构就清楚了：

```java
try {
    return Boolean.TRUE.equals(transactionTemplate.execute(status -> doCreateReservation(...)));
} catch (DuplicateKeyException e) {         // ← 在 execute() 外面
    log.info("并发抢座被唯一索引拦截: seatId={}, date={}, timeSlot={}", ...);
    throw new IllegalStateException("该座位该时段刚刚被预约，请选择其他座位");
} finally {
    redisLock.unlock(lockKey, lockToken);
}
```

**为什么必须在事务外**：
1. **异常必须冒泡出 `execute()`，`TransactionTemplate` 才知道要回滚**。如果在 `doCreateReservation`（事务回调内部）里就吞掉异常，事务会被当作成功提交——**而那条插入其实是失败的**，会出现"事务提交了但数据没写进去"的诡异状态。
2. `DuplicateKeyException` 在抛出时**Spring 已经把当前事务标记为 rollback-only**，只有走到事务边界才会真正回滚并抛出。在事务内捕获它再抛别的异常，容易踩到 `UnexpectedRollbackException`（事务被标记回滚但外层以为能提交）。

**冲突回滚后锁的释放顺序：不受影响，仍然是"回滚完成后才释放"**。因为：
- `transactionTemplate.execute()` **内部会先完成回滚**（异常抛出前回滚已发生），然后异常才传播到 `catch`；
- `catch` 里把异常转成业务异常再抛，最后 `finally` 执行 `unlock`；
- 所以顺序恒为：**回滚 → 捕获转换 → 释放锁**。

**这里的一个要点**：**回滚和释放锁的顺序不能反**。如果先释放锁再回滚，另一个请求会在"数据还没回滚干净"的时间窗口里进来——虽然唯一索引最终仍会挡住它，但那属于把本可以避免的异常路径又打开了一次。

### 50. 事务隔离级别是什么？RR 下间隙锁与唯一索引的冲突检测会引发死锁吗？你遇到并解决过吗？

**答：** 隔离级别是**MySQL InnoDB 的默认 RR（可重复读）**，项目没有做任何修改。

**死锁风险：⚠️ 理论上存在，但本项目没遇到过，我不能说"我解决过"。** 我讲清机制：

- **间隙锁（Gap Lock）**出现在**范围条件**的加锁读上——`SELECT ... WHERE col > x FOR UPDATE`、或非唯一索引上的等值条件更新。
- **唯一索引上的等值查询会退化成记录锁**，不产生间隙锁——**这正是本项目"幸运"的地方**：`uk_reservation_active_seat` 上的冲突是**等值唯一键冲突**，加的是记录锁，间隙锁的参与面很小。
- **真正的死锁典型形态是"加锁顺序不一致"**：两个事务分别锁住 A、B，再互相请求对方的锁。本项目的预约流程里**只有一个插入 + 若干查询**，没有"多行按不同顺序更新"的模式，所以天然不容易构成环。

**唯一键冲突会不会死锁**：会，有一种著名情况——**并发插入同一唯一键时，先插入成功的事务持有该记录的锁，第二个插入会等待；如果此时还有第三个事务参与、或第一个事务回滚，就可能形成 `Deadlock found when trying to get lock`**。缓解手段是：**把可能冲突的操作放在事务的最前面**（尽早暴露冲突而不是持有其他锁之后才冲突）、**缩短事务**、**必要时降级到 RC**（RC 下间隙锁基本消失，死锁概率显著降低）。

**⚠️ 我要如实说明**：我没有在生产或压测环境下遇到过这个死锁，也没有专门构造用例去触发它。**如果被追问**，我会说"RR 下间隙锁确实可能参与死锁，本项目因为走的是唯一索引等值冲突、事务很短，所以没有实际遇到；要验证得用 `SHOW ENGINE INNODB STATUS` 看最近的死锁信息，或用高并发压测来触发"。

### 51. 事务方法自调用（this 调用）导致事务失效的场景你了解吗？项目里有没有踩到？

**答：** 了解，原理是：`@Transactional` 靠 **AOP 代理**实现——外部调用先经过代理，代理在方法前后织入"开启事务 / 提交或回滚"。而**方法内部用 `this` 调用另一个方法时，不经过代理**（`this` 是原始对象不是代理对象），所以被调用方法上的 `@Transactional` **完全不生效**，它会在**调用方的事务上下文**里执行（如果调用方有事务）或者**根本没有事务**（如果调用方没有）。

**典型的失效形态：**
- 同类内 `this.b()`，而 `b()` 上有 `@Transactional` → b 的注解无效；
- `private` / `final` / `static` 方法上的 `@Transactional` → 代理无法覆盖，同样无效；
- 构造器里调用事务方法 → 此时代理还没生成。

**项目里有没有踩到：没有，但我用另一种方式绕开了同类问题。** 本项目 `ReservationServiceImpl` 的写方法用 `@Transactional`，读方法没加，**没有出现"事务方法内部调用另一个事务方法"的结构**；而**需要精确事务边界的 `createReservation` / `scanCheckin` 用的是 `TransactionTemplate`（编程式）**——编程式事务**不依赖代理**，所以**天然没有自调用失效的问题**。这也是我在这个场景选它的附带好处。

**如果确实需要自调用生效**，三种解法：① `AopContext.currentProxy()`（需要 `@EnableAspectJAutoProxy(exposeProxy = true)`）；② 注入自己（`@Lazy` 注入自身 Bean）；③ **把方法拆到另一个 Bean 里**（最干净，我一般选这个）。**最推荐的是第 3 种**，因为它同时也让职责划分更清楚。

### 52. 长事务的风险：事务内做 Feign 调用、发 MQ、写日志会怎样？你如何控制事务范围？

**答：** **长事务的风险是"占着资源等外部 I/O"**，具体四类：

1. **占着数据库连接不放**——连接池被长事务吃满后，**整个服务的新请求都会排队等连接**，表现为"数据库看着不忙但接口全超时"。
2. **拉长锁持有时间**——事务里更新的行锁一直不释放，其他事务等锁，容易升级成锁等待超时甚至死锁。
3. **制造"不可回滚的副作用"**：**发 MQ 和调外部接口都是不可回滚的**——消息已经投出去了，事务再回滚，下游就基于一个不存在的业务事实做了动作（比如扣了信用分）；Feign 调用同理，对方的写操作不会因为你这边的回滚而撤销。
4. **MVCC 层面**：长事务会让 undo log 无法及时清理，回滚段膨胀，影响其他事务的读性能。

**本项目如何控制事务范围**：核心原则是**"事务里只放数据库操作"**。
- **WebSocket 推送**不在事务里做——用 `TransactionSynchronizationManager.afterCommit` **挪到提交之后**（第 47 题）；
- **没有 Feign、没有 MQ**（服务间零调用），所以这两类风险在本项目里不存在；
- 事务内**没有日志、没有 HTTP 调用**，方法体就是几次数据库读写；
- 另外**用 `TransactionTemplate` 而不是大方法上打注解**，事务的起止点肉眼可见，不容易无意中扩大范围。

**如果将来要加消息/远程调用**，我的做法是：**"业务表写入 + 消息表写入"放在同一个本地事务里，事务提交后再异步投递消息**（本地消息表模式），而不是"在事务里直接发 MQ"——这样即使投递失败也能靠扫描重发补上。

### 53. 既然加了 Redis 锁，为什么还需要数据库唯一索引？两者分别防的是哪类问题（重复提交 vs 并发插入）？

**答：** 因为它们**防的不是同一件事，而且锁在极端情况下会失效**。

**各自防什么：**

| | Redis 锁 | 数据库唯一索引 |
| --- | --- | --- |
| 保护规则 | **一人一约**（同一用户只能有一条有效预约） | **一座一时段一约**（同一座位同一时段最多一条有效预约） |
| 为什么是它 | 这条规则**无法用索引表达**（管理员可代约、历史要保留、约束对象是用户不是座位） | 这条规则**能被约束精确表达**，且数据库约束是最强保证 |
| 失效场景 | Redis 挂了、主从切换丢锁、TTL 到期业务未提交 | 只有数据库写坏了才失效（那已经不叫超卖了） |

**为什么"有锁还不够"——锁会失效的具体情形：**
1. **锁 TTL 到期而业务未完成**（GC 停顿、数据库慢、网络抖动）；
2. **Redis 主从切换**：主节点还没把加锁命令同步给从节点就宕机，锁在新主上不存在；
3. **有人绕过应用直接写库**（DBA 修数据、另一个服务或脚本写入）——**锁只能约束走应用的请求，约束不了 SQL**；
4. **多实例 + key 设计失误**（比如锁的 key 少了业务维度），导致不同实例锁的不是同一把。

**核心逻辑一句话**：**锁是"应用层的君子协定"，唯一索引是"数据库层的法律"**。君子协定负责减少冲突、保护那些法律没法表达的规则；法律负责最终的正确性。**反过来也成立**：如果只上唯一索引不加锁，"一人一约"就没人管了——所以两者必须都有。

### 54. 有没有考虑用乐观锁 version 或状态条件更新替代分布式锁？为什么？

**答：** 考虑过，**在这个场景里不适用**，但**状态条件更新在项目里是大量使用的**——所以要分开回答：

**（1）乐观锁 `version` 不适用于"抢座插入"**：乐观锁的语义是"**读出旧版本 → 修改 → 写回时校验版本没变**"，它天然适合**更新已有行**。抢座是**插入新行**，**没有"旧版本"可比对**——硬要套就得先查一次再插，那又回到了 check-then-act 的竞态，只是把竞态换了个位置。**唯一键本身就是"插入场景的乐观锁"**：靠约束失败来发现冲突，比 version 更直接。

**（2）状态条件更新（CAS）项目里用得很多**，而且正是"不用锁"的典型手段。比如预约取消、签到、以及定时清理的状态流转，全部写成：

```sql
UPDATE reservation SET status = :to, updated_at = NOW()
WHERE reservation_id = :id AND status = :from
```

**用影响行数判断是否成功**（`updated == 1` 才算处理成功）。它的价值有三个：
- **原子**：判断"当前状态对不对"和"改成新状态"在**同一条语句**里完成，没有窗口；
- **幂等**：多实例并发执行同一条 SQL，只有一个能把 `updated` 变成 1，其余是 0——**违约次数因此不会重复累加**（第 60 题）；
- **防非法流转**：`WHERE status = :from` 天然拒绝了"已取消 → 已签到"这类非法跳转。

**（3）那为什么"一人一约"没用 CAS 而用了锁？** 因为这条规则是**"检查是否存在（可能 0 行也可能多行）+ 插入"**，不是"更新某一行"——**目标行还不存在，没有可以附加状态条件的对象**。用锁把这段串行化是最直接的解法。

**如果一定要去锁**，可行方案是**让"一人一约"也变成约束**：比如在用户表上维护一个 `active_reservation_id` 字段，用 `UPDATE user SET active_reservation_id = ? WHERE user_id = ? AND active_reservation_id IS NULL` 的影响行数来判断——**这是把"一人一约"转成条件更新的办法**，可以去掉对 Redis 锁的依赖。**这是我已知的、当前设计的改进方向**，代价是用户表被预约服务写入（耦合上升）。

### 55. 请复述 8 线程抢座测试的执行顺序与断言逻辑；如果改成多实例部署下验证，你会怎么做？

**答：** **执行顺序（`SeatBookingConcurrencyTest`）：**

1. `@BeforeEach` 造数据：先清理测试房间的残留预约和座位，再插入两个测试座位（`room_id=999001`），并记录 `seatA`、`seatB`；
2. 起 8 个任务，每个用**不同的 userId**（`900000+i`），都抢 `seatA`、同一天同一时段（**明天 + MORNING**，避开"距离时段结束不足 30 分钟"这类当天限制）；
3. 用 `CountDownLatch` 双闸门：8 个线程各自 `await(startGate)`，主线程 `startGate.countDown()` 后**同时跑**；
4. 每个任务调 `reservationService.createReservation(...)`，成功就 `success.incrementAndGet()`，**抛异常就吞掉**（那是预期中的失败）；
5. `doneGate.await(30, SECONDS)` 等全部结束（**带超时，避免用例挂死**）；
6. 断言：`success == 1`，并且**直接查库**确认该座位该时段的有效预约（`PENDING`/`CHECKED_IN`）**只有 1 条**；
7. `@AfterEach` 清理（删掉测试预约和测试座位）。

**注意断言是"查库"而不是"信内存计数"**——内存计数只能说明应用认为自己成功了，查库才能证明数据库里真的只有一条。

**其他两条用例**：`oneActiveReservationPerUser`（同一用户并发提交两个不同座位，断言成功数 == 1、该用户有效预约 == 1）、`seatCanBeBookedAgainAfterRelease`（取消后重新预约成功）。

**⚠️ 多实例验证我会怎么做**：这是**当前没做**的部分，方案是：
1. **起两个真实实例**（不同端口，或用容器起两份），指向同一个 MySQL 和同一个 Redis；
2. **不走 Service Bean 直调，改走 HTTP**——用 `TestRestTemplate` 或独立脚本，**并发打到网关**，让请求被负载均衡分到不同实例（这一点很关键：**必须确保请求真的落到不同实例**，否则测的还是单实例）；
3. **断言不变**：成功响应只有 1 个、库里有效预约只有 1 条；
4. **额外验证"锁"在跨实例下也生效**：把两个实例打到**不同用户**的场景，验证"一人一约"在跨实例下仍被锁住（这是唯一索引覆盖不到的那条规则，也是多实例验证真正要测的东西）。

### 56. 原实现"每个业务方法开头同步清理、查询不带时间条件、等于全表扫描"——这个问题你是如何发现的？用了 EXPLAIN、慢查询日志还是 SQL 监控？

**答：** **⚠️ 我如实说明：不是靠监控发现的，是靠读代码发现的。** 我没有开慢查询日志、也没接 SQL 监控——因为项目规模小，而且当时**MyBatis-Plus 配了 `log-impl: StdOutImpl`，所有 SQL 都打到了控制台**，读日志就能看出问题。（顺带说明：这个配置我后来**移除了**，因为把全部 SQL 打到标准输出在生产环境不可接受。）

**具体是怎么读出来的**：`ReservationServiceImpl` 里每个业务方法（`createReservation`、`cancelReservation`、`checkIn`、`getReservation`、`saveByAdmin`……**共 8 处**）**开头第一行都是 `enforceExpiration()`**。再看这个方法的实现，它做了两次查询：

```java
// 第 1 条：带时间条件，还能接受
this.list(wrapper.eq(PENDING).lt(Reservation::getExpiresAt, now));
// 第 2 条：只按状态过滤，没有任何时间条件 ← 问题在这
this.list(new LambdaQueryWrapper<Reservation>().eq(Reservation::getStatus, CHECKED_IN));
```

第 2 条把**全表所有 `CHECKED_IN` 的记录**捞进内存，再逐行 `LocalDate.parse` 和 `now.isAfter(slotEnd)` 比较。**这意味着"用户每刷新一次预约列表"就会触发一次全表扫描 + 逐行解析**——列表接口的响应时间被一个和它无关的清理动作绑住了，数据量一涨就崩。

**如果重来，我会用更专业的手段**：① 开**慢查询日志**（`slow_query_log` + `long_query_time`）定位；② 对可疑 SQL 做 **`EXPLAIN`** 确认是否全表扫（看 `type=ALL`、`rows` 数量）；③ 上 **SQL 监控**（本项目已经引了 Druid 依赖，它有 `StatFilter` 能统计慢 SQL）。

### 57. 改造后的定时任务用什么实现（@Scheduled/Quartz/XXL-Job）？多实例下如何保证任务不重复执行？

**答：** 用的是 **Spring 的 `@Scheduled`**——新增 `ReservationExpirationScheduler`，在 `ReservationServiceApplication` 上加 `@EnableScheduling`。

**关键配置选择**：用 `fixedDelayString` 而不是 `fixedRate`——`fixedDelay` 是"**上一次执行结束后**再等 N 毫秒"，`fixedRate` 是"按固定频率发起"。**前者天然不会任务堆积**（如果某次扫描慢，下一次自然顺延），后者在扫描慢时会叠加执行、越堆越多。间隔通过配置项 `reservation.expiration-scan-interval-ms` 设默认 60 秒，另外加了 `initialDelay` 避免应用刚启动就抢资源。**任务方法内整体 try-catch**，因为**定时任务里抛异常会中断后续调度**。

**⚠️ 多实例下的保证：当前是靠"状态条件更新"的幂等性，而不是靠"任务不重复执行"。** 也就是说**多个实例会同时跑这个任务**（`@Scheduled` 没有分布式协调），重复执行是**被允许的**，靠下面两层保证不出错：

1. **状态流转带原状态条件**：`UPDATE ... WHERE reservation_id = ? AND status = 'PENDING'`，**影响行数为 1 才算处理成功**——两个实例同时抢同一条记录，只有一个能拿到 1，另一个拿到 0 直接跳过；
2. **违约次数只在"流转成功"时才自增**，所以**不会被重复累加**（第 60 题）。

**如果要做"任务只跑一次"，方案按代价排序**：① **Redis 分布式锁 / `SETNX` 抢任务锁**（最轻，本项目已有 `RedisDistributedLock`，加几行就能用）；② **数据库悲观锁**（`SELECT ... FOR UPDATE` 锁任务行）；③ 换 **XXL-Job / Quartz 集群模式**（它们自带分片和"仅一个实例执行"的能力，适合任务多、需要可视化管理与失败重试的场景）。

**我的判断**：**当前业务量下"允许重复执行 + 幂等"比"保证只执行一次"更简单也更健壮**——不需要引入新组件，而且即使将来上了 XXL-Job，幂等这层仍然必须保留（因为任务可能超时重试、或者被人工触发重跑）。

### 58. 扫描 SQL 长什么样？“状态 + 到期时间”联合索引为什么能让它走索引？索引列顺序为什么这样排？

**答：** 改造后的两条扫描 SQL 都是**等值 + 范围**的组合：

```sql
-- 未签到且已到期
SELECT * FROM reservation WHERE status = 'PENDING' AND expires_at <= ? LIMIT 200;
-- 已签到且时段已结束
SELECT * FROM reservation WHERE status = 'CHECKED_IN' AND expires_at <= ? LIMIT 200;
```

对应索引：`KEY idx_reservation_status_expires (status, expires_at)`。

**为什么能走索引**：这是典型的**最左前缀 + 范围**场景——`status` 是**等值条件**（可以用索引定位到一段连续区间），`expires_at` 是**范围条件**（在定位到的区间里再按顺序扫）。B+ 树索引本身就是按 `(status, expires_at)` 排序的，所以**先按 status 精确定位、再在有序的 expires_at 上做范围扫描**，两步都是索引内操作。

**索引列顺序为什么这样排（`status` 在前、`expires_at` 在后）**——两条规则：
1. **等值条件列放前面、范围条件列放后面**。如果反过来 `(expires_at, status)`，`expires_at` 的范围扫描会**打断最左前缀**，后面的 `status` 就用不上索引定位了（只能靠回表过滤），效率差很多。
2. **区分度不是唯一标准**。`status` 的基数很低（只有 5 个值），单看区分度不该放前面——**但这里"等值在前的规则"优先于区分度**，因为它的目的是让范围列能被有效利用。

**补充两个实践点**：① 加了 `LIMIT 200` 是为了**单次扫描可控**（避免一次捞太多、长事务、内存膨胀），配合"按间隔反复跑"逐步消费；② 如果将来过期数据量很大，可以进一步**按日期分片扫描**或把历史数据归档，避免 `expires_at` 的范围一直往历史方向蔓延。

### 59. "状态流转带原状态条件保证多实例幂等"——UPDATE ... WHERE status = '待签到' 的影响行数如何用于判断处理是否成功？

**答：** 这里用的是**"比较并交换"（CAS）的思想**：把"**确认当前状态**"和"**改成新状态**"放进**同一条 UPDATE 语句**，让数据库在一次操作里完成判断和修改，中间没有窗口。

```java
private boolean transition(Reservation reservation, String fromStatus, String toStatus) {
    boolean updated = this.update(new LambdaUpdateWrapper<Reservation>()
            .eq(Reservation::getReservationId, reservation.getReservationId())
            .eq(Reservation::getStatus, fromStatus)      // ← 原状态条件
            .set(Reservation::getStatus, toStatus)
            .set(Reservation::getUpdateAt, new Date()));
    if (updated) { ... }                              // 影响行数为 1 才算成功
    return updated;
}
```

**影响行数的语义**：
- `updated == 1`：这条记录**在我执行更新的那一刻确实是 `fromStatus`**，我成功把它改成了 `toStatus` —— **我赢得了这次流转**；
- `updated == 0`：要么记录不存在，要么**已经被别人改走了**（另一个实例先跑完了、或被用户实时操作抢先）—— **我没赢，直接跳过，什么都不做**。

**这一层为什么能保证幂等**：并发更新的两个事务在数据库层面**必然串行**（InnoDB 会对这行加排他锁，后到的事务等锁），所以**不可能两个都拿到 1**。这就等价于一把"数据库层的乐观锁"，而且**不需要额外的 version 字段**——因为"状态"本身就是版本。

**一个必须注意的细节**：**`update` 的返回值必须来自影响行数，而不是来自"方法有没有抛异常"**。MyBatis-Plus 的 `update()` 返回 `boolean`（底层是 `affectedRows > 0`），用它判断才是正确的。我在 `cancelReservation`、`checkIn`、`transition` 三处都用了这个模式。

### 60. 违约次数为什么不会重复累加？请从 UPDATE 条件的语义上解释。

**答：** 因为**违约次数的自增严格挂在"状态流转成功"这个条件之下**，而状态流转本身是幂等的（上一题）：

```java
if (transition(reservation, PENDING, targetStatus)) {   // 只有流转成功（影响行数=1）才进入
    released++;
    if (!adminUser) {
        increaseViolation(reservation.getUserId());      // 自增在这里面
    }
}
```

**从 UPDATE 条件的语义上解释**：
1. `transition` 的 `UPDATE ... WHERE reservation_id = ? AND status = 'PENDING'` **只会成功一次**——第一个执行到的事务把 `status` 改成了 `BREACH`，之后所有实例的同一语句**条件不再成立，影响行数恒为 0**；
2. 影响行数为 0 时 `if (transition(...))` 为假，**`increaseViolation` 根本不会被调用**；
3. 所以**同一条预约记录最多只能让违约次数 +1**，无论有多少个实例、扫多少遍。

**自增本身也是原子的**——这点也很重要。`increaseViolation` 里用的是 SQL 自增而不是"读出来 +1 再写回"：

```java
@Update("UPDATE `user` SET violation_count = IFNULL(violation_count, 0) + 1 WHERE user_id = #{userId}")
int increaseViolationCount(@Param("userId") Long userId);
```

**为什么必须用 SQL 自增**：如果写成 `user.getViolationCount() + 1` 再 `updateById`，就是典型的**读-改-写**，两个并发事务同时读到 5、各自写回 6，**丢了一次更新**（丢失更新）。用 `SET col = col + 1` 让数据库在同一条语句里完成，才是原子的。

**这两个约束合起来的效果**：`transition` 保证"**每条预约只处理一次**"，SQL 自增保证"**每次 +1 本身不丢**"。缺任何一个都会出问题：只有自增没有 CAS，重复扫描会把违约次数刷成 3 倍；只有 CAS 不用自增，并发累加会丢更新。

### 61. 用户恰好在扫描瞬间完成签到，会不会被误判违约？你如何避免这种竞态（条件更新、二次校验）？

**答：** **不会误判，靠的正是"状态条件更新"这个机制本身**，不需要额外的二次校验。

**竞态场景**：定时任务查到了某条 `PENDING` 且 `expires_at` 已过的记录，正在准备把它标成 `BREACH`；**同一时刻用户刚好完成签到**（`checkIn` 把状态改成 `CHECKED_IN`）。

**为什么不会误判**：两个操作都是**带原状态条件的原子 UPDATE**，而数据库对同一行的更新**必然串行**：

- 如果**签到先提交**：定时任务的 `UPDATE ... WHERE status = 'PENDING'` 条件不再成立 → 影响行数 0 → **跳过，不计违约**（正确：用户确实签到了）；
- 如果**定时任务先提交**：签到的 `UPDATE ... WHERE status = 'PENDING'` 条件不成立 → 影响行数 0 → `checkIn` 抛"当前状态不可签到"（正确：确实已超时违约）。

**关键点在于：判断"是否超时"这件事不是由"查询结果"决定的，而是由"UPDATE 的条件是否成立"决定的**——查询结果可能已经过时（这正是第 45 题的 MVCC 快照问题），但 UPDATE 是在**当前最新版本**上判断的（它是当前读，会读最新已提交版本并加锁）。**所以"用查询做判断"会有竞态，"用带条件的 UPDATE 做判断"没有**——这是这个模式最本质的价值。

**⚠️ 一点需要如实说明**：**"不会误判"这个结论我是从机制上推出来的，但没有专门构造这条竞态用例去验证**（第 65 题）。

**还有一处边界值得指出**：`expires_at` 的设置在两个地方口径要一致——`createReservation` 里是"当前时段预约 → 创建后 30 分钟 / 未来时段 → 时段开始后 10 分钟"，`checkIn` 里签到成功后**把 `expires_at` 改成时段结束时间**（这样定时任务可以用统一条件扫描）。**如果这两处口径不一致，就会出现"该签到的被判违约"或"该释放的没释放"**，这是这段逻辑最需要保证的一致性。

### 62. 定时任务扫描量很大时如何分批？会不会长时间持锁影响正常业务？

**答：** 分批用的是**最朴素也最有效的方式：`LIMIT` + 高频小批**。

```java
List<Reservation> expiredPending = this.list(new LambdaQueryWrapper<Reservation>()
        .eq(Reservation::getStatus, ReservationStatus.PENDING.name())
        .le(Reservation::getExpiresAt, now)
        .last("limit " + EXPIRATION_BATCH_SIZE));     // 默认 200
```

**为什么这样分批**：每次只处理 200 条，处理完就结束，**下一个扫描周期（默认 60 秒）继续消费**。因为**过期数据的产生速率远低于扫描速率**（过期是"时间到了才产生"，不是突发洪峰），所以**常态下每批都远小于 200 条、一批就能清完**；只有故障恢复后积压了大量数据时才会连续多批消费。

**会不会长时间持锁影响正常业务——设计上避免了三点：**
1. **每次只处理 200 条**，单次运行的耗时可控；
2. **每条记录是一次独立的、极短的 CAS UPDATE**（单行更新 + 用户表自增），不持有长事务——注意 `releaseExpired()` **本身没有加 `@Transactional`**，所以**每条更新是各自独立提交的**，不会形成一个覆盖 200 行的大事务；
3. **扫描走 `idx_reservation_status_expires` 索引**，不做全表扫描。

**⚠️ 但我要指出一个真实的隐患**：**单行更新是很快，但它会在这些行上加排他锁**。如果某条记录**恰好被用户同时操作**（比如用户正在取消这条预约），两边会**互相等待行锁**——由于两条 UPDATE 的 `WHERE` 条件不同（任务看 `status='PENDING' AND expires_at<=now`，用户看 `status='PENDING'`），**理论上存在构成死锁环的可能**。缓解方式：**保持加锁顺序一致**（都按 `reservation_id` 单行操作，天然有序），以及**必要时把批量操作改成按 id 排序后逐条处理**。

**如果数据量真的到百万级**（第 66 题），分批策略要升级为：**按日期/状态分区 + 归档历史数据 + 一次只扫"当前有效窗口"内的数据**，而不是靠 `LIMIT` 硬扛。

### 63. 回收后座位如何恢复可预约状态？Redis 缓存与数据库状态如何同步？

**答：** **座位恢复可预约是"自动发生"的，不需要额外操作**——这正是用生成列表达占位键的好处。

**机制**：座位"被占用"这件事**没有存在座位表上，而是体现在预约表的 `active_seat_key` 上**。所以只要预约的状态从 `PENDING`/`CHECKED_IN` 流转成 `BREACH`/`RELEASED`/`CANCELLED`：**该行的 `active_seat_key` 立刻变成 `NULL`（生成列自动重算）**，唯一索引上的那个占位就释放了，**同一把键可以再次被插入**。**不需要删任何记录、也不需要更新座位表。**

**关于"Redis 缓存与数据库状态同步"——这里要如实澄清：本项目没有做座位状态的 Redis 缓存。**
- Redis 在这个项目里只承担两件事：**JWT 白名单**（`TokenRepository`）和**分布式锁**（`RedisDistributedLock`）；
- **座位可用状态是实时查数据库得到的**（前端拿房间的 `seat_info` 二维布局 + 当前时段的有效预约，在内存里做差集）；
- 所以**不存在"缓存与数据库不一致"的问题**——因为这个缓存根本不存在。

**代价是**：每次看座位图都要查一次数据库（虽然有 `idx_reservation_date_status` 支撑），座位图刷新频率高的话数据库压力会上去。

**⚠️ 如果要做缓存，一致性会立刻变成真问题**，我的方案是：**缓存"有效预约集合"而不是"座位可用与否"这种派生布尔值**，因为**集合的失效点非常明确——就是状态流转成功的那一刻**。然后：
- **先写数据库、提交后再删缓存**（不能先删缓存再写库，否则并发下会把旧值写回缓存）；
- 删除动作挂在 `afterCommit` 上（项目里已经有这个基础设施了，WebSocket 推送就是这么做的）；
- **缓存是"加速"不是"真相"**，任何校验仍然以数据库为准——这样即使缓存丢了/脏了，也不会影响正确性。

### 64. 预约状态机有哪些状态与合法流转？非法流转（如已取消 → 已签到）如何防止？

**答：** 状态枚举是 `ReservationStatus`，共 **5 个状态**：

| 状态 | 含义 |
| --- | --- |
| `PENDING` | 已预约，等待签到（**有效**） |
| `CHECKED_IN` | 已签到入座（**有效**） |
| `RELEASED` | 已释放（管理员/教师到期未签，或已签到时段结束） |
| `BREACH` | 违约（普通用户到期未签） |
| `CANCELLED` | 用户或管理员主动取消 |

**合法流转（按触发点）：**
- `PENDING` → `CHECKED_IN`：用户扫码签到成功
- `PENDING` → `CANCELLED`：用户/管理员取消
- `PENDING` → `BREACH` / `RELEASED`：到期未签到（普通用户记违约 / 管理员教师只释放）
- `CHECKED_IN` → `RELEASED`：时段结束，自动释放座位

**"有效"的定义就是 `PENDING` + `CHECKED_IN` 这两个状态**——它同时决定了生成列的取值和唯一索引的约束范围。

**非法流转如何防止——两层：**

1. **第一层：带原状态条件的 UPDATE（主要手段）**。所有流转都写成 `UPDATE ... WHERE status = :from`，所以**只有"当前确实是 from"才可能成功**。`CANCELLED` → `CHECKED_IN` 这种跳转，因为原状态条件是 `PENDING`（签到只允许从 `PENDING` 转），**在前置状态上就不成立**，影响行数为 0。
   ```java
   // checkIn：只允许从 PENDING 签
   .eq(Reservation::getStatus, PENDING).set(Reservation::getStatus, CHECKED_IN)
   ```
2. **第二层：业务前置校验给友好提示**。`checkIn` / `cancelReservation` 里先查一次记录并判断状态，给出"当前状态不可签到"/"当前状态不可取消"这类明确提示。**注意这一层只是"提示"、不是"保证"**——真正的保证是第一层的条件更新。

**这里有个设计理念值得讲**：**状态机没有用框架**（没引 Spring StateMachine），而是用**"状态 + 条件更新"在数据库层表达**。理由是这个状态机很简单（5 个状态、4 类流转）、且流转点都集中在 `ReservationServiceImpl` 里，用框架反而增加复杂度；**而"非法流转不可发生"这个要求，靠数据库的条件更新比靠框架更可靠**（框架只在应用层拦，条件更新在数据层拦）。

### 65. 定时任务与用户实时操作的并发一致性怎么测试？有没有构造过竞态用例？

**答：⚠️ 没有专门构造过这条竞态用例**，我如实说明——这也是我认为当前测试覆盖里比较明显的缺口。

**已有的测试覆盖**（`SeatBookingConcurrencyTest` 5 条 + `RegistrationSecurityTest` 3 条 + 30 条单测）覆盖的是**预约创建阶段的并发**（多人抢同一座位、同一用户抢多个座位、取消后可重约）和**注册安全**，**没有覆盖"定时任务清扫"与"用户签到/取消同时发生"**。

**如果要构造，我的方案是这样（可落地）：**

1. **同一条记录上的对撞**：造一条 `PENDING` 且 `expires_at` 已过期的记录；用**双 `CountDownLatch`** 同时放行两个线程——一个调 `releaseExpired()`（或直接调 `transition` 走 `BREACH`），一个调 `checkIn()`。
2. **断言不变式**（不是断言"谁赢"，因为调度顺序不确定）：
   - 最终状态**只能是 `CHECKED_IN` 或 `BREACH` 之一**，**不可能两个都发生**；
   - 如果最终是 `CHECKED_IN`，则**用户的 `violation_count` 没有增加**（这是关键——误判违约是这条竞态真正的危害）；
   - 如果最终是 `BREACH`，则签到请求返回"当前状态不可签到"。
3. **放大竞态概率**：单跑一次很可能不撞上，所以要**循环 N 次（比如 200 次）**，每次重建数据，统计"是否出现过双方都成功"——这才是有效的竞态测试写法（竞态测试靠重复而非靠单次触发）。
4. **验证幂等**：**并发调用 `releaseExpired()` 两次**（模拟多实例），断言**违约次数只增加 1**、`released` 计数不重复。

**为什么这个缺口影响可控**：这条竞态的正确性**不依赖测试覆盖，而依赖数据库的行锁语义**（同一行的两个 UPDATE 必然串行，条件不成立的必然影响 0 行）——是**机制层面**的保证。但**测试仍然应该补上**，因为它能防止有人把条件更新改回"查了再改"（那个改动会让正确性从"机制保证"退化成"靠运气"）。

### 66. 用延迟队列（RabbitMQ TTL+DLX、时间轮）替代定时扫描是否更好？数据量到百万级时你怎么选？

**答：** **在这个项目的数据量下，定时扫描更合适；但到百万级我会换方案。** 这是个真实的选型问题，我按维度拆开讲。

**三种方案的本质差异：**

| 方案 | 触发方式 | 精度 | 成本 |
| --- | --- | --- | --- |
| `@Scheduled` 定时扫描 | 轮询数据库 | 最差是扫描间隔（本项目 60 秒） | 最低，不引组件；**代价是轮询空转 + 扫描压力** |
| MQ 延迟队列（TTL + DLX） | 消息到期投递到死信队列 | 高（秒级） | 要引 MQ、每个预约一条延迟消息（消息量大） |
| 时间轮 / JDK `DelayQueue` / Redis ZSet | 内存或 Redis 排序集合 | 高 | 单机时间轮有**重启丢任务**问题；Redis ZSet 方案是很好的折中 |

**为什么本项目选定时扫描**：① 业务对释放的实时性要求不高（晚 60 秒释放座位，不影响正确性）；② 不引入新组件（**项目里连 MQ 都没有**，为一个功能引一套 MQ 不划算）；③ 扫描有索引支撑、每批 200 条，压力可控。

**⚠️ 但 MQ 方案有个坑要讲清楚**：**RabbitMQ 的 TTL + DLX 做延迟队列有个著名问题——队列是"队头阻塞"的**，只有队头消息到期才会投递死信，如果第一条消息 TTL 是 1 小时、第二条是 1 分钟，第二条会被卡住。**正确做法是用"延迟插件"（`rabbitmq_delayed_message_exchange`）或者按延迟粒度拆多个队列**。另外每个预约一条消息，**百万级预约就是百万级消息**，堆积和内存都是问题。

**数据量到百万级时我的选择**：**Redis ZSet 方案**。理由是——
- `ZADD reservation:expire:{timestamp} reservationId` 写入只是 O(log N)，**百万级也就几百 MB**（可以按小时分 key）；
- 定时任务用 `ZRANGEBYSCORE key -inf now LIMIT 0 200` 取到期任务，**和现在的分批扫描逻辑几乎一样**，改动很小；
- 相比 DB 扫描，**它扫的是"到期的任务集合"而不是"过期的业务表"**，表数据可以归档掉，不会随历史数据增长而变慢；
- 相比 MQ 方案，**不引入新组件、也不会队头阻塞**。

**同时必须做的**：① **数据库仍是唯一真相**——Redis 里的任务只是一份"索引"，真正确认仍靠条件更新；② **Redis 数据可丢但可重建**（重启后从库里按 `status='PENDING' AND expires_at <= now` 重建一次）；③ 表按时间分区 + 历史归档。

### 67. 任务的执行日志、失败告警、幂等重跑机制你做了哪些？

**答：⚠️ 只做了日志，告警和重跑机制没做**，我如实说明这三块的现状：

| 能力 | 现状 |
| --- | --- |
| **执行日志** | ✅ 做了。每批处理完如果 `released > 0` 会打一条 info（"过期预约清理完成，本次释放 N 条"）；异常在任务方法内被 catch 并 `log.error` 记录，**不让异常中断后续调度** |
| **失败告警** | ❌ 没做。只是打日志，**没有接告警通道**（邮件/钉钉/webhook），也就是说任务连续失败也没人知道 |
| **幂等重跑** | ⚠️ **"幂等"是被设计的，但没有"重跑入口"**。幂等性由条件更新保证（重跑不会重复计违约），但**任务失败后没有自动重试机制**，也没有手动触发的管理接口 |

**我的判断与改进方案：**
1. **告警**：最规范的是接 **Prometheus + Grafana**，用 Micrometer 暴露"上次执行时间戳、上次处理条数、失败次数"三个指标，**"上次执行时间超过 3 倍间隔"就直接告警**（这是定时任务最有效的健康指标——它同时覆盖了"任务没跑"和"任务卡住"两种情况）。
2. **重跑**：**幂等已经具备，缺的是一个入口**。最合适的是加一个**管理员接口** `POST /reservation/admin/release-expired`（需要 `@RequiresStaff`），需要时手动触发——重跑是安全的，因为条件更新会跳过已处理的记录。
3. **失败重试**：**不要给 `@Scheduled` 加自动重试**（无界重试会放大故障），而是"**下一轮扫描自然会重试**"——因为过期数据**仍然满足 `expires_at <= now`**，只要这个条件没变，下次扫描一定会再捞到它。**这就是"轮询式任务"相比"一次性消息"的天然优势：失败不需要补偿，等待下一轮即可**。

**顺带指出一个当前的隐患**：任务方法里 `try-catch` 住所有异常，虽然防止了调度中断，但**如果异常是系统性的（比如数据库连不上），日志会以每 60 秒一次的频率刷**，而且**任务实际上一直没在干活**——这正是"必须要有告警"的原因，光有日志等于没有。

## F. 安全审计与加固

### 68. "自助注册可覆盖他人账号并自助提权"的漏洞根因是什么（如 INSERT ... ON DUPLICATE KEY UPDATE、主键/唯一键复用、role 字段由前端传入）？请还原完整攻击步骤。

**答：** 这是我在项目里实际审计出来的漏洞，根因是**三个缺陷叠加**，不是单一原因：

1. **注册接口匿名可访问**（在白名单里，不需要 token）；
2. **学号（`userId`）由客户端在请求体里指定**，且落库用的是 MyBatis-Plus 的 **`saveOrUpdate`** —— 它的语义是"**主键非空且已存在就走 UPDATE**"。所以"注册"这个本该只做 INSERT 的动作，实际变成了"**存在就覆盖**"；
3. **`roles` 字段也在注册 DTO 里，由客户端提供**，参数直接 `BeanUtils.copyProperties` 落到实体上。

**完整攻击步骤（我实际验证过）：**

1. **`POST /auth/sendEmailCode`** —— 用自己的邮箱收验证码。`verifyCode` 只校验"邮箱与验证码匹配"，而邮箱填的是**攻击者自己的**，所以这一步必定通过；
2. **`POST /auth/register`**，body 传：
   ```json
   {"userId": 10001, "userName": "...", "email": "攻击者自己的邮箱",
    "code": "收到的验证码", "password": "<攻击者自己生成的哈希>"}
   ```
   —— **`userId: 10001` 是管理员的学号**。因为 `saveOrUpdate` 走 UPDATE，**管理员那行的 `userName`、`email`、`password` 全被覆盖**；
3. **`POST /auth/login`** 用 `userId=10001` + 自己设的口令登录 —— **拿到管理员账号的 token**。

**还有一条更简单的路径，不需要碰别人的账号**：注册时**用自己的学号 + `roles: ["R_SUPER"]`**，直接把自己的角色写成超管。

**当时的影响为什么不止于此**：因为这个漏洞和另一个缺陷叠加了——`UserSession.getAuthorities()` 当时返回空集合（第 76 题），所以**写进去的角色一度只是"数据上的"超级管理员**；但**修好授权之后，这条路径的收益就变成真实的了**。这也是我说"加授权时要连带审一遍认证入口"的原因。

### 69. 修复方案包含哪些层面（接口鉴权、字段白名单、DTO 参数绑定、服务端强制角色）？为什么说参数白名单是根本手段？

**答：** 我的修复是**四个层面一起上**，因为单独任何一层都不够：

1. **业务层：学号必须"不存在才允许创建"**——把 `saveOrUpdate` 换成**先查再 `save`**，已存在直接返回"该学号已注册，请直接登录或使用邮箱重置密码"。这是**针对这个漏洞最直接的修复**（把"覆盖"变成"拒绝"）。
2. **DTO 层：把 `roles` / `state` 字段从注册 DTO 里删掉**——**从参数绑定阶段就让它们无法进入**，服务端固定写 `["R_USER"]` 和 `state="1"`。这比"在 Service 里判断一下、是管理员就忽略"更彻底：**字段不存在，就没有被传入的可能**。
3. **服务端强制**：角色、状态这类**安全敏感字段一律由服务端赋值**，不接受客户端输入（这条规则也应用到了 `/auth/saveOrUpdateUser`：角色变更收窄为**仅 `R_SUPER` 可做**）。
4. **口令处理统一服务端加密**：填了口令就 `passwordEncoder.encode`，没填套用统一初始口令——**不接受客户端提交哈希**（否则等于让客户端决定库里存什么）。

**为什么"参数白名单"是根本手段**：因为它**改变的是"攻击面"而不是"攻击结果"**。逐字段做黑名单校验（"这个字段不能是管理员"）总是会漏——**漏在没被想到的字段上、漏在以后新增的字段上**。而**白名单的思路是"只接收我们明确需要的字段，其余一律不接受"**，那么：
- 以后 DTO 里加了新字段，**默认也是不接收的**（除非显式加进白名单）；
- 攻击者能构造的参数空间被压缩到"业务真正需要的那几个"，**越权参数根本没有入口**。

这条原则在业界叫 **Mass Assignment（批量赋值）防护**——本项目的 `BeanUtils.copyProperties(dto, entity)` 就是典型的批量赋值风险点：**它会把 DTO 里所有同名字段无条件拷到实体上**，包括你没打算让客户端传的那些。**更安全的写法是显式 setter 或 MapStruct 精确映射**。

### 70. 横向越权与纵向越权分别如何防护？你用统一鉴权拦截器还是逐接口校验？

**答：** **⚠️ 现状是"混合"，而且有明确的遗留风险**，我如实说明。

**两者的区别：**
- **横向越权**：同级用户访问**别人的数据**（A 查/改 B 的预约）；
- **纵向越权**：低权限用户执行**高权限操作**（学生删用户、删房间）。

**本项目的防护现状：**

| 类型 | 防护手段 | 覆盖情况 |
| --- | --- | --- |
| **纵向越权** | 自定义注解 `@RequiresStaff`（`hasAnyRole('ADMIN','SUPER')`）+ `@EnableMethodSecurity` | **只覆盖了部分高危接口**：用户列表/删除用户/保存用户/导入学生与教师、房间与座位的增删。**其余管理类接口仍然只有"是否登录"级别的校验**——这是明确的待办 |
| **横向越权** | **在业务代码里逐个判断归属**：如 `cancelReservation` 里 `if (!isAdmin && !Objects.equals(db.getUserId(), userSession.getUserId())) throw "无权取消该预约"`；`checkIn` 里判断"仅预约人可签到" | **逐接口手写**，没有统一的拦截器/切面 |

**为什么是"逐接口"而不是统一拦截器**：因为**归属判断的规则每个接口都不一样**——预约看 `user_id`、房间看管理角色、统计看数据范围；而且有些接口是"管理员可以看全部、普通用户只能看自己"（`getUserList` 里就是按 `R_SUPER`/`R_ADMIN`/普通用户分三档过滤）。**统一拦截器表达不了这些差异**，硬做会变成一个巨大的 if-else。

**但"逐接口"的代价我必须指出**：**依赖开发者记得写**，漏一个就是一个横向越权。**更稳的形态是"数据权限"**——比如在 SQL 层自动追加 `AND user_id = :currentUserId`（用 MyBatis 插件或 AOP 改 SQL），**让越权在数据访问层就发生不了**，而不是靠每个 Service 记得判断。这是本项目明确可以改进的地方。

**⚠️ 最大的遗留风险（我必须主动说）**：项目里有一个 `/auth/loginByUserId` 接口，**不需要密码、只凭学号就能换取 token**——这等于**所有人都能拿到任意用户（包括管理员）的 token**。它是继承下来的兼容接口，我**没有直接删掉**（担心前端在用），而是加了开关 `auth.legacy-login-by-user-id-enabled`，**默认仍是 `true`（保持原行为）**。**对外部署必须置为 `false`**。这一条我在 README 的「已知限制」里写明了。

### 71. JWT 的结构与签名算法是什么？密钥如何管理与轮换？HS256 与 RS256 如何选择？

**答：** **结构**：JWT 是三段用 `.` 连接的 Base64URL 字符串 —— `Header.Payload.Signature`。
- **Header**：`{"alg":"HS256","typ":"JWT"}`，声明签名算法；
- **Payload（claims）**：本项目放了 `userId`、`userName`、`roles`、`state`，以及标准声明 `iat`（签发时间）和 `exp`（过期时间）；
- **Signature**：`HMACSHA256(base64UrlEncode(header) + "." + base64UrlEncode(payload), secret)`。

**⚠️ 必须强调的一点**：**Payload 只是 Base64 编码，不是加密**——任何人都能解开看到内容，**所以绝不能放敏感信息**（本项目放的是 userId 和角色，可以接受；绝不能放密码）。

**密钥管理（本项目的实际做法）**：密钥**从配置读取**（`jwt.secret`），**启动时校验长度**（HS256 要求至少 256 位，否则 `Keys.hmacShaKeyFor` 会直接失败），并且**所有服务必须用同一个密钥**（因为每个服务各自验签）。**密钥不进代码库**，通过环境变量 `JWT_SECRET` 注入。

**轮换怎么做（当前没做，方案）**：单密钥无法平滑轮换（换了会导致存量 token 全部失效）。标准做法是**双密钥过渡**——验签时同时接受"当前密钥"和"上一个密钥"（用 Header 里的 `kid` 区分），签发只用新密钥；等老 token 全部过期后移除旧密钥。**因为 access token 的 TTL 是 24 小时，所以轮换周期要大于 TTL 才能无损。**

**HS256 与 RS256 的选择：**

| | HS256（对称） | RS256（非对称） |
| --- | --- | --- |
| 密钥 | 签发方和验签方**共享同一个密钥** | 私钥签发、**公钥验签**（公钥可公开） |
| 适合 | **单体 / 服务数量少、且都能安全保管密钥** | **多服务、或需要让第三方验签**（公钥外发无风险） |
| 风险 | **任何一个验签方泄露密钥 = 所有人可伪造 token** | 私钥只需签发方保管，泄露面小 |

**本项目选 HS256 的理由**：服务都在内网、同一个密钥由环境变量统一下发，没有"需要对第三方开放验签"的需求，而且 HS256 的性能更好（RSA 验签比 HMAC 慢一个数量级）。**如果服务数量变多、或要把验签能力开放给外部，就应该换 RS256。**

### 72. "JWT 过期时间被静态常量固定导致新签发令牌立即失效"的根因是什么（类加载时只求值一次）？为什么表现为"立即失效"？

**答：** **根因是 `static final` 的初始化时机**。原来的代码是：

```java
public static final Date EXPIRE_TIME = new Date(System.currentTimeMillis() + 1000 * 60 * 60 * 24);
```

`static final` 字段**在类加载时求值一次**，之后**永远不再重算**。所以 `EXPIRE_TIME` 实际等于"**服务启动那一刻 + 24 小时**"，而**不是"每次签发时刻 + 24 小时"**。

**为什么表现为"立即失效"**：把时间轴展开看就清楚了——

- 服务在 T0 启动，`EXPIRE_TIME` 被固定为 **T0 + 24h**；
- 在 T0 + 23h 时用户登录，签发的 token 过期时间**仍然是 T0 + 24h**（不是 T0+47h）→ **这个 token 只剩 1 小时有效期**；
- 服务连续运行超过 24 小时后（T > T0 + 24h），**任何时刻签发的 token，其 `exp` 都已经在过去** → 用户拿到 token 后**下一次请求就 401**，表现为"登录成功但立刻失效"。

**这是最容易漏掉的一类 bug**：因为它**只在服务连续运行超过 TTL 之后才暴露**——本地开发时改完代码重启，永远测不出来；只有在长时间运行的环境里才会突然出现，而且现象是"登录接口返回 200 但后续全 401"，很容易被误判成前端存 token 的问题或者过滤器的问题。

**修复方式**：**过期的计算必须发生在"签发的时刻"**，所以改成每次签发时现算：

```java
private String build(Map<String, Object> claims, Duration validity) {
    Instant issuedAt = Instant.now();
    return Jwts.builder().signWith(key).claims(claims)
            .issuedAt(Date.from(issuedAt))
            .expiration(Date.from(issuedAt.plus(validity)))    // ← 每次现算
            .compact();
}
```

**同时做的改进**：把 TTL 从硬编码常量改成**配置项**（`jwt.ttl-hours` / `jwt.refresh-ttl-hours`），并顺手把密钥也外置、加上了启动时的长度校验。

### 73. 修复后过期时间如何计算（签发时间 + TTL）？时区与 Clock 的问题你怎么处理？

**答：** **计算方式是 `expiration = issuedAt + ttl`，两个值都在签发那一刻取**：

```java
Instant issuedAt = Instant.now();                       // 签发时刻
.expiration(Date.from(issuedAt.plus(validity)))          // + TTL
```

TTL 来自配置（`jwt.ttl-hours` 默认 24 小时、`jwt.refresh-ttl-hours` 默认 168 小时），用 `Duration` 表达，**避免"1000*60*60*24"这种魔法数字**（原代码正是这种写法，既难读也容易算错）。

**时区问题的处理**：这里**刻意用 `Instant`（绝对时间点）而不是 `LocalDateTime`**——`Instant.now()` 是 UTC 时间轴上的绝对时刻，**不带时区，所以不存在时区歧义**；而 `Date` 本身也是"从 epoch 起的毫秒数"，同样是绝对时刻。**JWT 的 `exp`/`iat` 按规范就是从 epoch 起的**，所以整条链路上都不需要做时区转换。

**本项目里真正需要注意时区的地方不是 JWT，而是业务时间**：`TimeSlot` 用的是 `LocalTime`（"上午 8:00"这种**本地墙上时间**），时段的判断依赖**服务器本地时区**。所以：
- 我已经在数据库连接串里**显式指定了 `serverTimezone=Asia/Shanghai`**，避免 MySQL 8 出现"服务器时区无法识别"的报错，也避免 JDBC 驱动自己猜时区导致时间偏移；
- 容器部署时要**显式设置 `TZ`**（docker-compose 里配了 `TZ: Asia/Shanghai`），否则容器默认 UTC，会让"上午的时段"判断整体偏 8 小时——**这是部署环境里非常常见的一个坑**。

**关于 `Clock`**：**本项目没有注入 `Clock`**，直接用 `Instant.now()`。**这是可以改进的地方**——如果当初用了 `Clock`（注入 `Clock.systemDefaultZone()`），那么在测试"过期回收"这类时间相关的逻辑时，就可以注入 `Clock.fixed(...)` 来**精确控制时间**，不用真的等 30 分钟或去改数据库里的 `expires_at`。**时间相关的逻辑应该依赖可注入的时钟，而不是直接调 `now()`**——这是本项目在可测试性上的一处遗憾。

### 74. JWT 无法主动失效的问题怎么解决（黑名单、refresh token、短 TTL）？你的项目如何处理登出？

**答：** **本项目用的是"白名单 + Redis"方案**：登录签发 token 时**把它写进 Redis**（`TokenRepository.saveToken`），过滤器在校验 JWT 之前**先查这个 token 在不在 Redis 里**，登出时把它从 Redis 删掉 → **之后带着这个 token 的请求立刻 401**。

**注意这里是"白名单"不是"黑名单"**：黑名单是"记录已失效的 token"，白名单是"只认登记过的 token"。白名单的好处是**能发现完全伪造/从未签发过的 token**（黑名单只能拦住"登出过的"）。

**代价（必须讲清楚）**：
1. **JWT 从此不再是"无状态"的**——每次请求都要查一次 Redis，**多了一次网络往返**，JWT 相比 session 的性能优势被抵消了一部分；
2. **Redis 变成强依赖**——Redis 挂了，**所有登录态立刻失效**（过滤器查不到就 401），这是本项目的一个脆弱点（第 39 题）；
3. **内存占用随在线用户数增长**（每个 token 一个 key）。

**三种方案的取舍：**

| 方案 | 主动失效 | 代价 |
| --- | --- | --- |
| **黑名单/白名单（Redis）** | ✅ 立即生效 | 有状态、依赖 Redis、多一次查询 |
| **短 TTL + refresh token** | ⚠️ 只是"缩短窗口"（access token 5–15 分钟内仍然有效） | 需要实现续期流程；**真正要立刻失效（如改密、封号）时仍需黑名单配合** |
| **纯短 TTL** | ❌ 只能等过期 | 最简单，适合对失效实时性无要求的场景 |

**一个容易忽略的坑（我在项目里处理了）**：**Redis 里 token 的 TTL 必须和 JWT 自身的有效期一致**。原代码把 Redis TTL 硬编码成 24 小时，而 JWT 的 TTL 是可配置的——一旦有人把 `jwt.ttl-hours` 调小，就会出现"**JWT 已过期但白名单还在**"（无害）或调大时"**JWT 还有效但白名单已过期，用户被莫名踢下线**"（有害）。所以我把 Redis 的 TTL **从 `JwtTokenProvider.getTtlSeconds()` 读取**，保证两边**同源**。

**如果要做更完整的方案**，我会：access token 用**短 TTL（15 分钟）+ 无状态**（不查 Redis），refresh token 用**长 TTL + Redis 存储 + 一次性使用（rotation）**，敏感操作（改密、封号）时**主动清理该用户的所有 refresh token** 并维护一个**用户级的版本号**（token 里带 `tokenVersion`，改密后 +1，旧 token 全部失效）——这样既保住了无状态的性能，又能做到"踢下线"。

### 75. 自定义序列化适配器写坏角色数据的根因是什么（Jackson 配置、字段名不匹配、枚举映射）？你是如何定位的？

**答：** 根因是**调错了 Gson 的 API**——用的是 `toString()`，而不是 `getAsString()`。

项目用 **Gson** 做 JSON 映射（不是 Jackson：启动类里显式排除了 `JacksonAutoConfiguration`），`user.roles` 字段上挂了一个自定义适配器 `StringToString1DTypeAdaptor`，负责在"字符串里存的 JSON 数组"和"真正的 JSON 数组"之间转换。它的反序列化写成了：

```java
public String deserialize(JsonElement el, Type type, JsonDeserializationContext ctx) {
    return el.toString();      // ← 错在这里
}
```

**区别在于**：`JsonElement.toString()` 返回的是**该元素的 JSON 表示**——对**字符串**输入，它会把**外层的引号和内部的转义一起带出来**；`getAsString()` 返回的是**字符串的"值"**。

| 客户端提交 | 正确入库 | 实际入库 |
| --- | --- | --- |
| `"roles": "[\"R_ADMIN\"]"`（字符串） | `["R_ADMIN"]`（**11** 字符） | `"[\"R_ADMIN\"]"`（**15** 字符，多了外层引号和反斜杠） |
| `"roles": ["R_ADMIN"]`（数组） | `["R_ADMIN"]` | `["R_ADMIN"]` ✅（数组走 `toString()` 是对的） |

**我是怎么定位的**：**改一个用户的角色时，看到数据库里那串多了引号**，觉得不对；然后把两边的 **hex 打出来对照**确认——

```
正确 5B22525F41444D494E225D          （[ " R _ A D M I N " ]）
实际 225B5C22525F41444D494E5C225D22  （" [ \ " ... \ " ] "）
```

一眼就看出来多了 `22`（`"`）和 `5C`（`\`）。根因确认后修复是**一行**：区分类型——数组取 `toString()`、字符串用 `getAsString()`、`null` 原样返回。**两个适配器（roles 和 seat_info）都有这个 bug，一起修了。**

**这个 bug 的两个后果，第二个才更值得讲**：
1. **静默降权**：坏值让 `UserSession.parseRoles` 解析失败（Gson 把一个 JSON 字符串往 `List<String>` 上解析会抛 `JsonSyntaxException`），我的实现里**catch 后回退成空集合** → **那个用户下次登录就失去全部角色**；
2. **让上一次的修复打了对折**：我新加的"只有超管能改角色"这条校验，判断依据是 `RolePolicy.rolesChanged`，而它比较的是**解析后的集合**——坏值和正确值永远不相等，于是**管理员提交未改动的表单也会被判定为"改了角色"而吃 403**，那条"角色没变就不拦"的设计目标**根本没达成**。

**这件事教我的不是"要多写测试"，而是：校验的正确性取决于它的输入。** 你新加一个判断，得回头确认喂给它的数据本身是不是干净的。所以我补的用例里最重要的是**"往返一致"**——**写进去什么，读出来必须还是什么**；而且我**特意把代码回退成有 bug 的版本跑了一遍，确认那条用例真的会红**。

### 76. "用户静默失去权限"暴露了系统哪些工程缺陷（权限缓存、鉴权日志、缺少测试）？你补了哪些防护？

**答：** 这个问题的真正危害是**"静默"**——数据坏了、用户权限没了，但**没有任何信号**。它暴露了四个工程缺陷：

| 缺陷 | 具体表现 |
| --- | --- |
| **序列化/反序列化没有闭合性校验** | 写进去和读出来**形状不一致**却没人发现——缺"往返一致"这类测试 |
| **权限解析失败时静默降级** | `parseRoles` 解析失败**catch 后返回空集合**，把"数据坏了"伪装成"这个人没有角色"，**失败方向虽然是安全的（fail-closed），但完全无声** |
| **缺少鉴权可观测性** | **没有一条日志记录"某用户被赋予了哪些权限"**，所以权限变空这件事在日志里查不到 |
| **缺少针对权限链路的测试** | 30 条单测里原本**没有一条覆盖"roles 数据 → Spring Security 权限"的完整映射**，只在最后才补上 |

**我补的防护：**
1. **往返一致性测试**（`GsonAdaptorRoundTripTest` 10 条用例）——**"写进去什么，读出来必须还是什么"**，并且覆盖了**字符串/数组两种输入形态**和 `null`；**我还把代码回退到有 bug 的版本验证这组用例真的会红**（否则测试只是装饰）。
2. **权限映射测试**（`UserSessionTest` 7 条）——把 `roles` JSON → `ROLE_*` 权限的映射固化下来，包括 `R_ADMIN` → `ROLE_ADMIN` 的转换和空值处理。
3. **让失败"可见"**：`parseRoles` 在解析失败时**记日志**（而不是静默返回空集合），并把方法注释写清"解析失败按无权限处理"——**失败方向保持 fail-closed，但不再无声**。
4. **把判断收敛到一处**（`RolePolicy`）——原来同一段角色判断**散落在 15 处**（9 个注解 + 6 段内联），**任何一处写法不一致都可能造成"这里认、那里不认"**。收敛之后，"权限怎么判"只有一个答案。

**如果要做得更彻底**，我会再加两条：**① 权限变更的审计日志**（谁在什么时候把谁的权限改成了什么——这既是排障手段也是合规要求）；**② 关键路径的"不变量"监控**（比如"超级管理员的数量不应为 0"这类断言，一旦被破坏就告警）。

### 77. 数据库口令与三方密钥改环境变量注入：Docker 下怎么传（env_file/secret）？本地开发怎么管理（.env、配置中心）？

**答：** **本项目的做法最简单**：配置文件里全部写成**带默认值的占位符**，敏感项**没有默认值或默认值仅供本地**，运行时由**环境变量覆盖**：

```yaml
url: jdbc:mysql://${DB_HOST:localhost}:${DB_PORT:3306}/${DB_NAME:library_db}?...
username: ${DB_USERNAME:root}
password: ${DB_PASSWORD:123456}          # 默认值只服务于本地开发
...
jwt:
  secret: ${JWT_SECRET:dev-only-secret-change-me-...}   # 生产必须覆盖
```

**清理掉的东西**（原本明文提交在仓库里，这是最严重的一类问题）：数据库口令、**邮箱授权码**、**百度人脸 API 的 key/secret**、JWT 签名密钥、网关 Swagger 的账号密码。**这些一旦进了 Git 历史，即使删掉也还在历史里**——所以我是**重建了仓库历史**（而不是只改当前文件）。

**Docker 下怎么传，按安全性排序：**
1. **`secrets`（最推荐，Swarm/K8s）**：密钥以文件形式挂载到容器内（`/run/secrets/xxx`），**不出现在 `docker inspect` 和环境变量列表里**，也不落进镜像层；
2. **`env_file`**：把变量写在独立文件里（`.env`），**该文件必须加进 `.gitignore`**，容器启动时读取。比"写在 compose 里"好（compose 文件常常会被提交），但**变量仍然会出现在容器的 env 中**（`docker inspect` 能看到）；
3. **直接在 compose 的 `environment` 里写**：最方便也最差，**除非这个 compose 文件永不提交**。

**本地开发怎么管理：**
- 我采用的方案是**配置文件里给"仅供本地"的默认值 + 环境变量覆盖**，这样**克隆下来就能跑**（不需要先配一堆变量），而生产必须显式覆盖；
- **更规范的做法是 `.env` + `.env.example`**：`.example` 提交进仓库（只有键名、没有值），真实 `.env` 加进 `.gitignore`；
- **`.gitignore` 里我专门列了这几条**：`application-local.yml`、`*.local.yml`、`.env`——**给"本地覆盖"留好出口，避免有人图省事把真口令写回 `application.yml`**；
- **配置中心（Nacos Config）**：本项目**没用**（第 5 题）。它的优势是密钥不必落在每个服务的配置文件里、支持按环境隔离和热更新；代价是要保证配置中心自身的安全（**访问要鉴权、传输要加密**）——**否则把明文密钥从 Git 挪到配置中心，只是换了个地方泄露**。

**还应该做但我没做的**：**密钥定期轮换**、**接入密钥管理服务（Vault / KMS）**、以及**在 CI 里加密钥泄露扫描**（如 gitleaks）——**最后这条成本最低、收益最高**，因为它能在"提交的那一刻"就拦住，而不是等到审计时才发现。

### 78. 敏感数据保护：密码哈希、人脸数据、日志脱敏分别怎么做的？

**答：** 分三块如实说明：

**（1）密码哈希 —— ✅ 用了 BCrypt，但有几处要改进**
- 用的是 Spring Security 的 `BCryptPasswordEncoder`（自带随机盐、可调 cost），**不是 MD5/SHA**——因为 MD5 无盐、可彩虹表、且计算太快（容易被暴力破解）；
- **登录**用 `passwordEncoder.matches(明文, 哈希)` 比对，**不比对哈希串本身**；
- **改进点（我应该主动指出）**：
  - **初始口令是统一的 `123123`**，且它是弱口令——README 的「已知限制」里明确写了"对外部署必须强制首次登录修改"；
  - **`DEFAULT_PASSWORD_HASH` 硬编码在代码里**：客户端不传口令时就用它。**更好的做法是"必须设置口令"或在首次登录时强制改密**；
  - 注册接口我**不接受客户端提交哈希**（否则等于让客户端决定库里存什么），一律服务端加密。

**（2）人脸数据 —— ⚠️ 这里要说清现状**
- 项目接的是**百度 AI 的人脸库**（第三方），**特征提取和比对在百度侧完成**；本地 `face_feature` 表**只存了特征摘要/占位数据**，**没有真正存原始人脸图片**；
- **为什么这样设计**：**人脸是不可更改的生物特征**，一旦泄露无法"改密码"，所以**能不在自己这边存、就不存**——把比对交给有资质的第三方，本地只保存"这个人验证过了"的结果和必要的摘要；
- **合规问题（必须提）**：人脸属于**个人敏感信息**，采集需要**单独告知并取得同意**，存储要加密、要有删除机制。**这个项目是个人项目，没有做隐私合规设计（没有同意流程、没有数据删除接口、没有加密存储）**，如果真用于生产，这些都必须补上，而且要评估是否符合《个人信息保护法》对人脸信息的要求（**通常需要单独同意，且很多场景被要求"不得将人脸作为唯一验证方式"**）。

**（3）日志脱敏 —— ✅ 做了一处关键的，其他还有改进空间**
- **移除了明文打印完整 token 的日志**。原代码里有 `logger.info("Token: " + token)`——**JWT 一旦进了日志，就等于把登录凭证写到了磁盘和日志采集系统里**，这是很严重的问题；
- 同时把**逐请求的 info 日志降为 debug**（原来每个请求都打"Processing jwt authentication request"、"Skipping JWT filter for ..."，日志量很大而且会泄露路径信息）；
- **数据库连接串里的口令**：走环境变量，且**不打印配置**；
- **还没做的**：① **异常堆栈里可能带敏感参数**（比如注册请求的参数），没有做统一的脱敏；② 手机号、邮箱在日志和接口返回里**没有做掩码**（`138****0001` 这种）；③ 没有接入日志脱敏的框架。**这三条是明确可以改进的**。

### 79. 有没有做过越权扫描、SQL 注入、XSS、CSRF 的检查？用了什么工具或方法？

**答：** **⚠️ 没有用扫描工具，是人工审计 + 依据框架特性判断的**，我按四类如实说：

**（1）越权 —— ✅ 人工审计过，而且真找出问题了**
我发现并修复了**注册接口的账号接管 + 自助提权**（第 68 题），以及发现**遗留的无密码登录接口**（`/auth/loginByUserId`，等于任意用户可被冒用 token）。**方法就是"把所有能写敏感字段的入口逐个过一遍"**——把"哪些地方能写 `roles`"这件事当成一条线去梳理，而不是只看出问题的那个接口。**没做的是自动化扫描**。

**（2）SQL 注入 —— ✅ 结构上是安全的**
项目用 **MyBatis / MyBatis-Plus**，条件全部通过 `LambdaQueryWrapper` 的**参数化查询**构造，**没有用字符串拼 SQL**；即使少数手写 SQL 用的也是 `#{}` 占位符（MyBatis 会预编译成 `?`）而不是 `${}`（`${}` 是直接拼接、**才是注入风险点**）。**风险点在于 `last("limit " + EXPIRATION_BATCH_SIZE)` 这种写法**——虽然拼接的是**常量**不是用户输入，但**这是一个坏习惯**，因为一旦有人把它改成拼用户输入就变成注入了。**更严谨的写法是把 limit 也参数化，或至少加注释说明这里只能是常量**。

**（3）XSS —— ⚠️ 后端没有专门处理，依赖前端渲染方式**
这是一个前后端分离项目，后端返回 JSON、前端是 Vue（默认做 HTML 转义），所以**反射型 XSS 的风险主要在前端渲染**。**后端该做的**是：用户可控的内容（如 `userName`）**如果将来被拼进 HTML 或富文本就要转义**——项目里有个 `remark` 之类的文本字段就属于这类。**我没做的是**：没有加 CSP 响应头、没有在保存富文本时做服务端过滤。**如实说这是"没做"**。

**（4）CSRF —— ✅ 结构上不需要，但原因要讲清**
项目**主动关闭了 CSRF**（`csrf().disable()`）。这在**纯前后端分离 + JWT 放在请求头**的场景下是**正确的**——因为 CSRF 的攻击前提是"浏览器会自动携带凭证（Cookie）"，而**JWT 在 `Authorization` 头里，浏览器的跨站请求不会自动带上它**，所以不存在 CSRF 攻击面。**⚠️ 但这有个前提**：如果哪天把 token 改存 Cookie，**就必须重新开启 CSRF 防护**（或用 `SameSite=Strict/Lax`）——**"关掉 CSRF 是因为架构允许，不是因为懒得配"**，这个区别在面试里要讲清楚。

**如果要系统化，我会补的工具**：依赖漏洞扫描（`mvn dependency-check`）、静态代码扫描（**SAST**，如 SonarQube / CodeQL——能自动发现硬编码密钥、拼接 SQL、不安全的随机数等）、密钥泄露扫描（gitleaks，**加在 CI 的 pre-commit 上**）。**这些工具能覆盖"人容易漏"的部分，成本远低于人工逐行审。**

### 80. 你是如何系统性做"安全审计"的？有没有形成检查清单，或使用静态扫描（SAST）与依赖漏洞扫描？

**答：** **⚠️ 老实说，我没有做"系统性审计"——我做的是"按风险面逐个方向审"，而且是问题驱动（先发现异常再顺着查）。** 没有用 SAST、没有用依赖漏洞扫描、也没有形成书面的检查清单。**这是我的真实水平边界，我不夸大。**

**我实际做的（可以讲的部分）——四条线：**

| 线索 | 具体做法 | 产出 |
| --- | --- | --- |
| **凭据** | 全仓搜 `password`、`secret`、`key`、`token` 等关键词，逐条看哪些是**真实值**还是占位 | 清掉数据库口令、邮箱授权码、百度 key/secret、JWT 密钥、Swagger 账号 —— **并重建了 Git 历史** |
| **写入敏感字段的入口** | 把"哪些接口能把 `roles`/`state`/`password` 写进库"列成一条线逐个过一遍 | 发现**注册接口账号接管 + 自助提权**；收窄 `/auth/saveOrUpdateUser` 的角色变更权限 |
| **匿名可达的接口** | 把过滤器白名单逐个看过去，问"这个接口不登录就能调，会怎样" | 发现**无密码登录接口**（等于可冒用任意用户身份），加了开关 |
| **数据正确性** | 从"数据长什么样"反推（改角色时发现库里多了引号） | 发现 **Gson 适配器写坏 roles** 的缺陷 |

**没做但应该做的（我会明确说出来）：**
1. **SAST 静态扫描**（SonarQube / CodeQL / Semgrep）——能自动发现硬编码密钥、拼接 SQL、不安全的反序列化、弱随机数等**人工容易漏**的问题；
2. **依赖漏洞扫描**（`mvn dependency-check`、Snyk）——本项目依赖里有 Spring Boot 3.1.8 等**较旧版本**，**有没有已知 CVE 我完全没查过**，这是明确的空白；
3. **密钥泄露扫描**（gitleaks）+ **CI 前置卡口**——**成本最低收益最高**，能在提交那一刻拦住，而不是等审计；
4. **检查清单的沉淀**——审计的价值在于**可复用**，每发现一类问题就把它变成清单里的一条，下次照着过一遍，避免靠记忆。

**"我打算怎么建立体系"（如果被追问）**：我的顺序是——**① 先用工具兜住"机械性"的部分**（密钥扫描 + 依赖扫描 + SAST，全部接进 CI）；**② 再把本次审计的四条线索固化成清单**（凭据、敏感字段写入、匿名接口、数据闭合性）；**③ 最后做出口径**：所有涉及权限/金额/身份的操作，必须带上"谁在什么时间改了什么"的审计日志。**工具解决"漏"，清单解决"忘"，审计日志解决"查不了"。**

### 81. 这次审计中，除已修复的四个问题外，还有哪些风险你识别到了但并未修复？为什么没修？

**答：** 这个问题很好，**因为它逼我说出"我知道但没做"的部分**——这是最能体现诚实度的一题。我列出来：

| # | 风险 | 为什么没修 | 如果要修 |
| --- | --- | --- | --- |
| 1 | **无密码登录接口 `/auth/loginByUserId` 默认仍开启**（等于任意用户可被冒用身份） | 我**不敢直接删**——这是继承下来的兼容接口，前端可能在用它，删掉会破坏联调。所以改成**配置开关**，默认保持原行为 | **对外部署必须置为 `false`**；正解是确认前端不用后**直接删除**，或收窄为"仅超管可调用" |

| 3 | **邮件验证码没有失败次数限制** | 改动涉及验证码的服务端计数与失效逻辑，**要验证码流程做配套改造** | 加"同一邮箱连续失败 N 次即作废"，用 Redis 计数（基础设施已有） |

| 6 | **`WebSocket` 是单机内存广播** | 多实例需要 Redis pub/sub 转发，**当前是单实例部署**，没有实际影响 | 引入 Redis 订阅转发 |

| 8 | **`last("limit " + 常量)` 这类拼接**（当前不是注入，但是坏习惯） | 改造成本极低但我认为优先级低于其他项 | 参数化或明确注释"此处只能拼常量" |

### 82. 网关聚合接口文档的实现方式是什么？各服务的 OpenAPI 文档如何被拉取与分组展示？

**答：** 用 **springdoc 的网关聚合能力**，靠"路由 + 配置列表"两件事凑起来：

**第一步：把每个服务的 `/v3/api-docs` 暴露到网关上**——为 5 个业务服务各配一条路由，例如：
```yaml
- id: user-service-swagger
  uri: lb://user-service
  predicates:
    - Path=/user/v3/api-docs/**
  filters:
    - StripPrefix=1          # 去掉 /user 前缀再转发
```
这样访问 `网关:8080/user/v3/api-docs` 就等价于访问 user-service 自己的 `/v3/api-docs`。

**第二步：让 Swagger UI 知道有这几个分组**——
```yaml
springdoc:
  api-docs:
    enabled: true
  swagger-ui:
    path: /swagger-ui.html
    disable-swagger-default-url: true     # 关键：防止 UI 自己改写地址
    urls:
      - name: 用户服务
        url: /user/v3/api-docs
      - name: 房间服务
        url: /room/v3/api-docs
      # ... 预约 / 人脸 / 统计
```

**拉取与展示的机制**：Swagger UI 页面加载时**不会一次拉全部文档**——它只渲染一个"分组下拉框"，**用户选哪个分组，浏览器才去请求对应的 `/xxx/v3/api-docs`**，拿到 OpenAPI JSON 后在同一个页面渲染。**所以聚合是"按需拉取"，不是"启动时合并"**。

**由此带来两个特性**：
- **某个服务挂了，只有它那个分组打不开，其他分组不受影响**（这也是它不需要额外做"上下线刷新"的原因）；
- **没有"提前验证"**——配错路径时错误只在点开那个分组时才暴露。

**踩过的版本坑（值得记住）**：网关是 **WebFlux** 栈，业务服务是 **Servlet** 栈，所以**两边的 starter 不能混用**——网关必须用 `springdoc-openapi-starter-webflux-ui`，业务服务用 `springdoc-openapi-starter-webmvc-ui`；另外网关**不能引入 `spring-boot-starter-web`**（会和 Gateway 冲突），所以它依赖 `common-module` 时要把 `spring-boot-starter-web` 和 `security` **排除掉**。还有一个细节是 `disable-swagger-default-url: true`——不加它，UI 会尝试访问默认的 `/v3/api-docs` 并覆盖你配的地址。

### 83. 统计服务统计哪些指标？实时计算还是离线汇总？数据来源与更新频率是什么？

**答：** 统计服务提供 **11 个接口**，全部是**实时查库计算**，**没有离线汇总、没有缓存**。

**指标清单（按主题分三类）：**

| 主题 | 接口 |
| --- | --- |
| **总览与趋势** | `overview`（总览）、`reservation-trend`（预约趋势）、`violation-cancel-trend`（违约与取消趋势）、`advance-reservation-lead-time`（提前预约时长分布） |
| **房间与座位** | `room-usage-rank`（房间使用率排名）、`room-time-slot-heat`（房间×时段热力图）、`seat-usage`（座位使用情况） |
| **签到与人群** | `checkin-rate/time-slot`、`checkin-rate/room`（按时段/按房间的签到率）、`time-slot-distribution`（时段分布）、`dept-class-statistics`（按学院/班级统计） |

**数据来源**：**直接读同一个数据库**——统计服务自己带了一套 `ReservationMapper` / `UserMapper`，查的就是 `library_db` 里的 `reservation`、`user`、`seat`、`room` 这些表（第 14 题里说过，这是"共库"带来的方便，也是它的代价）。

**实时还是离线**：**全部实时**——每次请求都现查现算，没有任何预聚合表、没有离线任务。

**更新频率**：**等于请求频率**，用户刷新看板就重新算一次。

**⚠️ 我要指出的问题**：这个设计**只在数据量小时成立**。随着预约表增长，几个问题会依次暴露：
1. **聚合查询越来越慢**（尤其涉及 `DATE(create_time)` 这类**函数作用在列上**的写法，会让索引直接失效）；
2. **和核心业务争抢数据库资源**（统计是重查询，会和抢座这类写操作抢 CPU 和连接）；
3. **同一份数据被反复计算**（看板刷新 10 次，就算 10 遍完全一样的结果）。

### 84. 统计查询会不会拖垮主库？读写分离、缓存或预聚合你用了吗？

**答：** **⚠️ 会拖垮主库——这三样我一个都没用**，我如实说明，并给出改进方案。

**当前的真实情况：**
- 统计服务**直连同一个 MySQL 实例**（就是主库）；
- **没有读写分离**（单实例，没有从库）；
- **没有缓存**（每次请求都查库）；
- **没有预聚合**（没有汇总表、没有离线任务）；
- 更糟的是**部分统计 SQL 里有函数作用在列上的写法**（如按 `DATE(create_time)` 分组），**这会让 `create_time` 上的索引失效、退化成全表扫描**——这是我在审计时识别到但**没有修**的问题之一（第 81 题）。

**为什么现在"看起来没事"**：数据量小（几十条预约），全表扫描也就毫秒级。**但这是"数据量掩盖了设计问题"**——它不能证明设计是对的。

**改进方案（按代价从低到高，我会按这个顺序做）：**

1. **先修 SQL 层面能修的（成本最低、收益最直接）**：把 `DATE(create_time)` 改成**范围条件**（`create_time >= ? AND create_time < ?`）让索引能用；给统计用的字段补索引；**把能在 SQL 里做的聚合留在 SQL 里**，而不要捞回 Java 逐行算（本项目现在的实现里有不少 Java 侧的循环聚合，**这等于把数据库该干的活搬到应用里，还多了一次全量数据传输**）。
2. **加缓存（性价比最高）**：统计是**运营看板，允许分钟级延迟**——所以用**定时预聚合 + Redis 缓存**，而不是"请求时回源 + 缓存"。**这个区别很关键**：定时刷新（比如每 5 分钟算一次写进缓存）能**彻底避免缓存击穿**（因为不存在"缓存过期瞬间大量请求同时回源"），也不用处理复杂的缓存一致性。**代价是数据有最多 5 分钟延迟——对看板完全可以接受。**
3. **预聚合表**：如果数据量继续涨，建一张按天/按房间/按时段的汇总表，由定时任务或消息驱动更新——**查询从"扫明细"变成"查汇总"**。
4. **读写分离**：如果统计确实是重查询且无法预聚合，**加从库**——统计读从库，写走主库。**但要注意主从延迟**：刚预约完立刻看统计可能看不到（这对看板可接受）。**这一步是最后的手段**，因为它引入了"主从延迟"这个新的复杂度。

**优先级判断原则**：**能用"改 SQL + 加索引"解决的，不要上缓存；能用"预聚合"解决的，不要上从库。** 每往上一层，复杂度都显著增加，而收益是递减的。

### 85. 座位状态实时同步用的是什么机制（轮询/WebSocket/SSE）？延迟与服务器压力如何权衡？

**答：** 用的是 **WebSocket 长连接推送**，不是轮询也不是 SSE。

**实现方式**：`reservation-service` 里有 `SeatWebSocketHandler` + `WebSocketConfig`，网关配了 `/ws/**` 路由（**不剥前缀**，否则握手路径变了会断开）。预约状态变更时**服务端主动 push** 一条 `SeatStatusMessage`（房间 id、座位 id、行列、userId、日期、时段、状态）。

**一个我认为做对了的细节**：**推送发生在"事务提交之后"**——用 `TransactionSynchronizationManager.afterCommit` 注册。如果直接在事务里推送，**事务回滚时前端已经收到了一个不存在的状态变化**，用户会看到座位被占了但库里没有这条记录，状态永久不一致。

**为什么不用轮询**：座位图是"很多人同时在看的、变化不频繁"的数据，**轮询的代价是"变化率和请求量脱钩"**——一个 200 个座位的房间，1 秒轮询一次就是 200 req/s，而实际上可能几分钟才变化一次。**WebSocket 的代价是"连接数随在线用户线性增长"**，但每个连接空闲时几乎没有流量，**在"看的人多、变化少"这个特征下 WebSocket 明显更省**。

**为什么不用 SSE**：SSE 是**单向**（服务器→客户端）且基于 HTTP 长连接，做"只推不收"的场景其实够用、实现更简单（不用处理握手和帧协议）；**WebSocket 是双向的**。本项目选 WebSocket 是因为**实时性和双向性**；但如果只是"服务端单向通知"，**SSE 的运维成本更低**（走普通 HTTP 端口、更容易穿过代理、断线自动重连是浏览器内置的）。

**⚠️ 延迟与服务器压力的取舍，我要指出当前设计的两处短板：**
1. **广播是全房间广播，没有做增量/按需订阅**——一个房间的所有在线用户都会收到该房间的任何座位变化。房间大、变化频繁时**推送量会被放大**；改进方向是**按"前端当前可见的区域"做订阅过滤**，或对推送做**节流合并**。
2. **单机内存广播，多实例下会失效**——会话连接保存在**当前 JVM 的内存**里，如果起两个实例，**A 实例处理的预约变更无法推给连在 B 实例上的用户**。当前是单实例部署所以没暴露，**多实例必须用 Redis pub/sub 或 MQ 做广播转发**（第 81 题里列过这条）。

### 86. 人脸识别服务如何选型（SDK/自研/第三方）？识别失败与隐私合规问题怎么处理？

**答：** **选的是第三方（百度 AI 的人脸库）**，通过 OkHttp 调 HTTP 接口；`face-service` 单独拆出来一个服务。

**选型理由**：
- **自研不可能**——人脸检测 + 特征提取 + 比对模型需要训练数据和算法团队，不是这个项目的范围；
- **本地 SDK（离线模型）**可行但**依赖模型文件和算力**（要 ONNX Runtime 之类），部署复杂度高；
- **第三方 API** 的**接入成本最低、准确率有保障**，代价是**按调用量付费、依赖外网、且数据出了自己这边**。

**失败处理（业务侧的设计）：**
1. **签到的前置校验**：普通用户签到**必须"最近 2 分钟内有过一次成功的人脸识别"**（`hasRecentFaceRecognition`），否则报"请先通过人脸识别再进行签到入座"。这样**人脸识别是独立动作，签到靠一次时间窗校验解耦**——识别接口慢或超时不会把签到链路卡住。
2. **失败可降级**：`face-service` 用的是**环境变量注入的 key/secret**，**没配置时人脸相关接口不可用**，但**不影响其他服务启动**（第 77 题）。也就是说人脸能力是"可选增强"，不是硬依赖。
3. **识别日志**：`face_recognition_log` 表记录 `user_id`、`matched`、`score`、时间——**既是排障依据，也是"谁在什么时候验证过"的审计线索**。

**⚠️ 隐私合规问题（这部分我必须说清，因为人脸是敏感个人信息）：**

| 问题 | 现状 |
| --- | --- |
| 单独告知与同意 | ❌ 没有同意流程，采集合规缺失 |
| 数据最小化 | ✅ 本地只存特征摘要/占位，**没有存原始人脸图片** |
| 是否唯一验证方式 | ⚠️ **当前签到强依赖人脸**（2 分钟窗口内必须识别过），**人脸实际上成了唯一验证方式**——而监管通常要求提供替代方式 |
| 删除权 | ❌ 没有"删除我的人脸数据"的接口 |
| 传输与存储加密 | ⚠️ 未做加密存储 |

**正确的做法应该是**：**① 提供替代验证方式**（二维码本身就是——本项目扫码签到也支持，**所以人脸应当定位为"可选增强"而不是唯一通道**）；**② 采集前单独弹窗告知并留存同意记录**；**③ 支持删除**；**④ 本地不存原始图像**（现在这一点做到了）；**⑤ 评估是否必须走第三方**——如果只是"验证是不是本人"，本地离线模型能避免把生物特征传给第三方，合规压力更小。

### 87. 系统的实际并发与部署规模是多少（几个容器、多少内存、是否上 K8s）？“高并发抢座”的压测数据是什么？

**答：** **这一题我必须非常诚实地回答，因为它最容易被我夸大。**

**实际部署规模：**
- **单机部署，6 个 Java 进程**（gateway 8080、user 8081、room 8082、reservation 8083、statistics 8085、face 8000）+ Nacos + MySQL + Redis；
- **没有容器化部署**：`docker-compose.yml` **只用于拉起依赖**（MySQL/Redis/Nacos），**服务本身还是 `mvn spring-boot:run` 起的**；项目**没有 Dockerfile**，**没有上 K8s**；
- **内存没有做过规划**，就是本地开发机的默认配置。

**"高并发"的实测数据：**

| 项目 | 数据 |
| --- | --- |
| **并发抢座用例** | **8 个线程**并发抢同一座位 → **1 个成功、7 个失败**；数据库里有效预约 **1 条**。这是**实测**（`SeatBookingConcurrencyTest`，跑在真实 MySQL 8.3 + Redis 7.2.5 上） |
| **单用户并发** | 同一用户并发提交两个不同座位 → 成功 **1 个**，有效预约 **1 条** |
| **QPS / 压测** | **没有做过压测，没有任何 QPS 数据** |
| **用户量 / 数据量** | **没有真实用户**，演示数据是 4 个账号、2 个房间、39 个座位 |

**⚠️ 所以"高并发"这个词我要说准**：**这个是"并发正确性"的验证，不是"高并发性能"的验证**。8 个线程证明的是"**在并发下不会超卖**"（正确性），**它完全不能说明系统能承载多少 QPS**（性能）。**这两件事在简历和面试里必须分开讲**：
- 可以说："**我验证了并发下的正确性——8 线程抢同一座位只有 1 个成功**"；
- **不能说**："系统支撑高并发"——因为**没有压测数据支撑**。

**如果要做压测，我会这样设计**：
1. **工具**：JMeter / wrk / Gatling 打**抢座接口**；
2. **场景**：① **稳态**（固定并发持续压，看 P99 和错误率）；② **尖峰**（瞬间并发，模拟开抢）；③ **长时间**（跑 30 分钟以上，看有没有连接泄漏、内存增长——**这类问题只在长时间压测里暴露**）；
3. **关注指标**：**QPS、P95/P99 延迟、错误率、数据库连接池使用率、CPU/内存、Redis 命中率、以及"唯一索引冲突的次数"**（冲突次数直接反映锁的粒度和竞争程度）；
4. **明确瓶颈在哪**：单机部署下**瓶颈几乎一定先出现在数据库**（并发写入 + 唯一索引冲突等待），所以压测的意义是**找到拐点并知道该往哪个方向扩**。

**这题怎么答才加分**：**主动说明"没有压测数据"**，然后讲清"压测该怎么设计、我会关注哪些指标"——**这比编一个 QPS 数字安全得多，而且显得懂工程方法**。

### 88. 微服务间接口版本变化与字段兼容如何管理？

**答：** **⚠️ 项目没有做接口版本管理**——没有 `/v1` `/v2` 这样的路径版本、没有 Header 版本协商、也没有走"向后兼容 + 灰度"的流程。我如实说明现状和已知的处理痕迹。

**项目里实际存在的"兼容处理"（都是补丁式的）：**
1. **`normalizeReservationPayload`**：兼容前端**只传 `roomId + row + column`**（不传 `seatId`）的老形式，服务端自己反查出 `seatId`；
2. **`normalizeTimeSlot`**：兼容前端传**中文时段**（"上午/下午/晚上/夜间"）并映射到枚举；
3. **`Reservation` 实体同时保留两套字段**：`time`（旧）与 `timeSlot`（新）、`room_id + row + column`（旧定位）与 `seat_id`（新定位）；
4. **网关的 `StripPrefix` 混用 1 和 2**，也是因为各服务的路径前缀风格不统一。

**这些痕迹说明的问题**：**字段演进靠"服务端写兼容代码"硬扛**，而不是靠版本管理。**代价是**：新老字段长期并存、实体上挂着一堆"只为兼容存在"的字段、代码里到处是 `normalize*` 方法——**新读代码的人分不清哪个字段是"现在用的"**。

**如果要规范管理，我会这样做：**
1. **对外接口用路径版本**（`/api/v1/...`）：**只在出现不兼容变更时升版本**，老版本保留一段时间；
2. **对内（服务间）坚持"只增不改不删"**：新增字段必须有默认值、**删除字段分两步**（先标记废弃、等所有调用方都不再用再删）、**类型变更等同于新增字段**；
3. **契约先行**：把接口定义（OpenAPI）纳入版本控制，**变更走 review**，用**契约测试**卡住"改了契约但调用方没同步"的情况；
4. **废弃要有信号**：老字段/老接口在日志里埋"被调用"计数，**确认没有调用方之后再删**——而不是靠猜"应该没人用了"；
5. **兼容期要有截止日期**：否则兼容代码会永久留着（**本项目正是缺这一条**）。

**说白了**：**版本管理的目标不是"支持多版本"，而是"让每次变更的影响可评估、可回滚"**。本项目现在是"没有版本概念 + 靠服务端兼容兜住"，**能用，但不可持续**。

### 89. 这个项目最难的三个技术点是什么？如果重做，你还会用微服务架构吗？

**答：**

**最难的三个点（按我认为的难度排序）：**

**第一，"锁和事务的边界"**——难在它的错误形态很隐蔽。直觉上"在方法上加 `@Transactional`、方法里加锁"看起来天经地义，但实际上**锁会在提交前释放**，造成"一人一约"规则被击穿。而**这个故障在低并发下完全测不出来**（因为窗口很窄），只有在真并发时才偶发。更难的是要理解**为什么不能靠"多查一次"解决**——因为第二个请求读到的是一个**已经过时但当时确实成立的一致性快照**（第 45 题），这需要真正理解 MVCC 才能讲清。

**第二，"用生成列模拟部分唯一索引"**——难在**MySQL 没有部分索引**（不能"只对满足条件的行建唯一索引"），必须绕。用"无效状态返回 NULL + 唯一索引允许多个 NULL"这个特性来模拟，**是一个需要把数据库特性吃透才能想到的技巧**；而且选 `STORED` 还是 `VIRTUAL`、表达式必须确定性、状态列不能简单塞进唯一键（否则历史记录撞键）——**每一处都有坑**。

**第三，"失败方向的设计"**——难在它是**理念层面**的：整个系统里**每一个失败路径都要想清楚"失败时是偏安全还是偏危险"**。`parseRoles` 解析失败该返回空集合（fail-closed，安全但用户静默失权）；锁拿不到该拒绝还是等待；Redis 挂了座位维度能不能继续（能，唯一索引兜底）而用户维度不能。**这些判断没有标准答案，但每一个都会决定系统出故障时的表现。**

**如果重做，还会用微服务吗？——不会，我会用单体。**

理由很清楚，而且我认为这是**这个项目最有价值的反思**：
1. **业务规模根本不需要**：单校区的座位预约，**单体 + 模块化**完全够用，一套进程、一次部署、一个数据库，**运维成本低一个数量级**；
2. **微服务带来的复杂度远大于收益**：6 个进程、注册中心、网关、13 条路由、服务间共享一个库——**而服务之间根本没有调用**。也就是说，我承担了微服务的**全部成本**（部署、排查、配置、版本），却**没有拿到它的收益**（独立伸缩、独立迭代、故障隔离）；
3. **共库让"服务边界"形同虚设**：统计服务直接读别的服务的表（第 2、14 题），**表结构一改就一起坏**——**真正的微服务应该是每服务独立库**，那才需要处理跨服务一致性，而那是另一个量级的复杂度；
4. **错误被放大**：**单进程里的问题暴露得更早更明显**；拆成多进程后，日志分散、没有链路追踪，**排查一个跨服务的请求要人工拼时间戳**（第 13 题）——这些都在消耗本该用在业务上的精力。

**什么情况下我会选微服务**：**团队规模超过单体的协作上限**（多团队独立交付）、**不同模块的伸缩特性差异巨大**、**需要按模块独立发布和故障隔离**。**这三条在这个项目里一条都不成立。**

**所以我的答案是**：**先用单体把业务做对、把边界划清（模块划分清楚、依赖单向、不互相读表），等真的撞到伸缩或协作瓶颈再拆**——而且**拆的时候应该按业务能力拆，不是按现在的"一个实体一个服务"拆**。这也回应了第 1 题里"粒度偏细"的反思。

### 90. 用 5 分钟向面试官介绍这个项目，你会怎么组织（背景—问题—方案—结果）？

**答：** 我会**不按功能模块讲，而按"问题—解决"讲**，因为功能罗列没有信息量。下面是我准备好的结构（约 5 分钟）：

---

**① 一句话定位（20 秒）**
> "这是一个面向高校图书馆自习室的座位预约系统，Java 17 + Spring Boot 3 + Spring Cloud Alibaba，6 个服务，核心链路是**预约 → 签到 → 超时释放 → 统计**。我做的主要不是加功能，而是**解决并发正确性和一次安全审计**。"

**② 抛出最核心的问题（40 秒）**
> "座位预约的本质矛盾是：**同一座位同一时段只能被一个人预约**。这里有个天然的**检查-执行竞态**——'先查有没有被占、再插入'这两步之间，另一个请求也在查、也查到没被占，于是两个都插入成功——**超卖**。而且'一个账号只能有一条有效预约'这条规则也一样会被绕。"

**③ 方案——分两层讲，重点讲取舍（2 分钟）**
> "我用了两层，**而且它们保护的是不同的规则**：
> - **座位维度**用**数据库层的约束**：在预约表上建了一个**生成列**，有效状态（PENDING/CHECKED_IN）取值 `座位:日期:时段`，其他状态取 `NULL`，在它上面建**唯一索引**。这样历史记录可以随便留（多个 NULL 不冲突），但有效预约只能有一条。**选数据库而不是只用 Redis，是因为这是所有并发路径上最强的保证——不依赖任何外部组件。**
> - **用户维度**（一人一约）**没法用索引表达**，所以用 **Redis 分布式锁**把同一用户的请求串行化。锁用 `SET NX PX` 原子加锁、value 存随机 token、释放用 **Lua 脚本比对 token 再删**（防止误删他人锁）。
>
> **最关键的一点是锁必须包住事务**：如果在提交前释放锁，下一个请求会读到**尚未提交的数据**，同样通过校验——所以锁要在**事务外拿、提交后放**。为了表达这个顺序，我用的是 **`TransactionTemplate` 而不是方法上的 `@Transactional`**（注解的提交发生在方法返回之后，顺序天然是反的）。
>
> **还有一点**：我并没有把正确性寄托在锁上。因为**锁会失效**（TTL 到期、主从切换），所以真正的保证是数据库约束——**锁只是减少竞争、保护那条没法用约束表达的规则**。"

**④ 结果与验证（1 分钟）**
> - **并发用例实测**：**8 个线程抢同一座位，只有 1 个成功**，数据库里有效预约只有 1 条；同一用户并发抢两个座位，只产生 1 条有效预约；
> - **可复现**：补了建表 SQL + 演示数据，`docker-compose` 一键拉起 MySQL/Redis/Nacos，**38 个测试全绿**（含并发用例和注册安全用例）；
> - **另外做了一次安全审计**，修了四个真实缺陷：**注册接口可覆盖他人账号并自助提权**（根因是"学号由客户端传 + `saveOrUpdate` 语义 = 存在就 UPDATE"）、**JWT 过期时间被 `static final` 固定**（服务跑满 24 小时后新签发的 token 立即失效）、**用户角色的权限映射始终返回空集合**（导致方法级授权形同虚设）、以及**自定义序列化适配器把角色数据写坏**（`toString()` 用成了 `getAsString()`，用户会静默失权）。

**⑤ 收尾给一个"我知道不足"的信号（40 秒）**
> "这个项目我知道不足的地方也很明确：**共用一个数据库**（统计服务直接读业务表，边界是假的）、**服务之间零调用却拆了 6 个服务**（微服务的成本承担了、收益没拿到）、**没有压测数据**（8 线程验证的是并发正确性，不是高并发性能）、**统计接口没有缓存和预聚合**。**如果重做，我会先用单体把业务做对、边界划清，撞到瓶颈再拆。**"

---

**为什么这样组织（面试官视角）**：
1. **先讲问题再讲方案**——面试官关心的是"你怎么想"，不是"你用了什么"；
2. **取舍必讲**——"为什么用数据库约束而不是只用 Redis""为什么用 `TransactionTemplate`"，这些**决策点才是加分项**；
3. **数字只讲实测的**——8 线程、38 个测试是**真的**；**不编 QPS、不编用户量**；
4. **主动暴露不足**——这会让前面所有内容都更可信，而且**面试官一定会问到这些**，自己先说比被问出来强得多。

**最后一句话我会留一个钩子**（引导他往我最想讲的方向问）：
> "**如果只能挑一个最有价值的点，我会说是'锁和唯一索引各管一条规则'这个划分**——因为它让我第一次意识到：分布式锁不应该被当成正确性的唯一保证。"
