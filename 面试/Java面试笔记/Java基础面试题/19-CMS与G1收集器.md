# CMS 与 G1 收集器

> [!question] 疑问
> CMS 和 G1 的区别？什么场景用 CMS、什么场景用 G1？

## 一图看懂两者结构

![[CMS与G1对比.svg]]

## CMS：以最短停顿为目标的"并发"收集器

四阶段，**只有两端是 STW**：

| 阶段 | 是否 STW | 干什么 |
| --- | --- | --- |
| ① 初始标记 | ✅ STW（短） | 只标记 GC Roots 直接关联的对象 |
| ② 并发标记 | ❌ | 与用户线程并发，遍历引用链 |
| ③ 重新标记 | ✅ STW（短） | 修正并发期间的变动 |
| ④ 并发清除 | ❌ | 与用户线程并发清除 |

配套细节：

- **浮动垃圾**：④ 期间用户线程产生的新垃圾只能下次回收，CMS 必须**预留空间**
- **退化**：预留不足 → `Concurrent Mode Failure` → 退化 **Serial Old** 单线程整堆回收（最惨情况）
- **碎片**：用标记-清除，久用碎片化 → 大对象放不下 → 提前 Full GC（靠 `-XX:CMSInitiatingOccupancyFraction` 提前触发缓解）
- **版本**：JDK 9 弃用，**JDK 14 移除** —— 新项目不需要选它

## G1：面向服务端的"分区"收集器（JDK 9+ 默认）

核心思想：把堆切成约 **2048 个等大 Region**（1~32MB），每个 Region 动态扮演 Eden / Survivor / Old / **Humongous（大对象）**。

- **Garbage First 得名**：按 `-XX:MaxGCPauseMillis`（默认 200ms）建立停顿预测模型，每次优先回收"垃圾占比最高"的一批 Region —— 用最小代价腾出最多空间
- **Region 间复制（Evacuation）** → 天然无碎片（说"标记-整理"是简化说法，较真会扣分）
- **筛选回收是 STW 并行复制**：不是并发清除，所以没有 CMS 那种并发碎片问题；但**并发标记期间同样产生浮动垃圾** —— "G1 没有浮动垃圾"是错误说法
- **失败路径**：预留空间耗尽（Evacuation Failure / to-space exhausted）→ Full GC（JDK 10 起并行）

## 区别速查

| 对比项 | CMS | G1 |
| --- | --- | --- |
| 范围 | 老年代收集器，需配 ParNew 等新生代收集器 | 整堆独立工作 |
| 算法 | 标记-清除（有碎片） | Region 间标记-复制（无碎片） |
| 停顿 | 目标是最短停顿，但不可预测 | 可预测停顿模型（MaxGCPauseMillis） |
| 浮动垃圾 | 有，且预留不足会退化 Serial Old | 也有（并发标记期），但失败后 Full GC 是并行的（JDK 10+） |
| 大堆适应 | 一般 | 数 GB~数十 GB 更有优势 |

## 选型

- **CMS 适用**：JDK 8 及以下 + 对停顿敏感 + 堆不大（≤4~6G）—— 但它已死，只在维护老系统时遇到
- **G1 适用**：大堆（6G+）、要求停顿可控、不想手工调优 —— 现代默认选择
- **再往上**：超大堆 + 亚毫秒级停顿 → ZGC / Shenandoah

> [!tip] 一句话速记
> **CMS 两端 STW 中间并发，浮动垃圾 + 碎片是两大死穴；G1 切 Region、挑最脏的收、复制无碎片，停顿可预测。**
