# 循环依赖与三级缓存

> [!question] 疑问
> 什么是循环依赖？Spring 怎么解决的？三级缓存是什么？

## 三种情况，只有一种能救

![[循环依赖三级缓存.svg]]

| 情况 | 能否解决 | 原因 |
| --- | --- | --- |
| ① 构造器注入 | ✗ | 实例化**前**就要依赖，对象还没出生，没有引用可暴露 |
| ② 原型 + Setter | ✗ | 每次 getBean 都新建实例，缓存只对单例生效 |
| ③ 单例 + Setter/字段 | ✓ | 实例化后、属性填充前，引用已存在 → 可以**提前暴露** |

## 三级缓存

- **一级 `singletonObjects`**：完全初始化好的成品 Bean，`getBean()` 最终返回这里的
- **二级 `earlySingletonObjects`**：提前暴露的早期引用（原始对象**或**提前生成的代理），防止代理重复创建
- **三级 `singletonFactories`**：`ObjectFactory` 工厂，发生循环依赖时才调用 —— 由它决定返回原始对象还是提前生成代理

## 五步流程（A ⇄ B）

![[循环依赖五步流程.svg]]

1. 实例化 A（构造函数跑完，属性为空）
2. 把 A 的 `ObjectFactory` 存入三级缓存 —— 提前暴露
3. A 填充属性发现依赖 B → 转去创建 B（B 同样实例化 + 暴露工厂）
4. B 填充属性发现依赖 A → 三级缓存命中 → 工厂产出**早期引用**（需要 AOP 就此时生成代理）放入二级缓存，工厂条目删除 → 注入给 B
5. B 完成初始化升入一级缓存 → 回溯：B 注入 A → A 完成初始化升入一级 → 闭环

**关键认知**：第 4 步塞给 B 的是 A 的半成品引用 —— Java 引用指向对象本体，引用一个"属性还没填的对象"完全合法，等 A 后续初始化完成，B 手里那个引用自动就是完整的。

## 追问必考：为什么是三级，两级不够吗？

- **两级方案的问题**：要在**每个** Bean 实例化后立刻生成代理放入二级缓存 → 破坏 Spring 的生命周期设计（代理应由初始化后的 BeanPostProcessor 生成），且绝大多数 Bean 根本没有循环依赖，白白提前代理
- **三级方案的精髓**：工厂把"要不要提前代理"的决策**延迟**到真正发生循环依赖的那一刻 —— 没有循环依赖就一切按正常生命周期走
- **二级缓存的职责**：保证同一 Bean 的早期引用只创建一次（第 5 步回溯时直接复用，不重复生成代理）

## 构造器循环依赖：无解，但有绕法

- `@Lazy` 注入：塞进去的是一个"延迟代理"，第一次真正使用时才创建目标 —— 打破"实例化前就要依赖"的死结
- 根本解：重构设计，别让两个类在构造器里互相咬

> [!warning] 版本演进：Boot 2.6+ 默认禁止循环依赖
> `spring.main.allow-circular-references` 默认改为 **false** —— 再遇到循环依赖直接启动报错。官方态度明确：三级缓存是兜底机制，不是让你依赖的设计。老项目升级 Boot 2.6+ 时一堆启动失败就是这么来的。

> [!tip] 一句话速记
> **构造器和原型无解；单例 Setter 靠"实例化后提前暴露"续命 —— 三级工厂能造、二级暂存早期引用、一级交付成品。**

> [!note] 关联
> [[01-IOC与AOP实现原理]]：三级缓存里"提前生成代理"正是 AOP 与循环依赖的交汇点 —— 也是三级缓存必须存**工厂**而不是直接存对象的原因（不发生循环依赖就永远不提前代理）。
