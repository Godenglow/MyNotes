## 🔴 Notion `<columns>` 不能用来做卡片网格（用户截图实锤）

- **现象**：母版里用 `<columns ratio="20">` 五等分 + 彩色 `<callout>` 复刻 HTML 的 `.cards`，**渲染后每个 callout 被压成一条约 130px 宽的竖柱**，中文全部竖排单字（"活跃总时长〔待填〕h" 变成一个字一行），完全不可读。侧栏一展开更窄。
- **根因**：Notion 的 `columns` 是**流体布局**，在桌面宽度下会按内容自动收缩；五列 + 中文 + `〔待填：…〕` 长占位符 → 每列被压到最小。`ratio` 只是偏好比例，不是硬性最小宽度。
- **结论**：**Notion 里没有可靠的"卡片网格"**。想并排展示就用 `table`（`<table fit-page-width="true">`），列宽自适应、不会竖排；想要颜色就退回单个 `callout`（整行宽度，安全）。emoji 当行首标识可以保留视觉分组。
- 已把母版「核心指标」从 columns 改成三列表格（指标 / 数值 / 说明），用户看后未再报错。

## 🔴🔴 三个致命问题的根因与修法（用户截图实锤，务必记住）

用户截图指出「1 格式没生效 2 HTML 没有 3 模板颜色标记一个没有」。查了几小时，**三个问题同一个根因：混用了两个 Notion 通道**。

### 根因

- **MCP 通道与直连 API 是两个不同的 integration，上传的文件互相不可见。**
  实测：MCP 报 `Could not find file_upload with ID: xxx, integration_id: 1f8d872b-...`，
  而同一个 ID 用直连 `GET /file_uploads/{id}` 查回 `status: uploaded`。
  → 我用直连传 HTML、页面却由 MCP 渲染，**页面根本不认识那些文件 →「无法加载此嵌入文件」**。
- **直连 API 的 `text.content` 是纯文本，不解析 markdown** → `**加粗**` 和反引号全变字面量。
- **表格单元格禁止 `annotations`** → 颜色/加粗注解在表格里全部失效。

### 三条正确修法（已全部实测通过）

1. **embed 必须用 `file_upload` 字段，不是 `url: "file-upload://..."`**：
   `{"object":"block","type":"embed","embed":{"file_upload":{"id":fid},"caption":[...]}}`
   Notion 服务端会**自动转成 `prod-files-secure.s3...` 真实链接**。直连 API 上传 + 这样 append → 200 且 URL 已转换。
   （对比：`url: "file-upload://xxx"` 直连不会被转换，页面报「无法加载」。）
2. **markdown 自己解析成 rich_text**（API 不认 markdown）：`rich()` 用正则拆 `**bold**` / `` `code` ``，输出 `{"annotations":{"bold":true}}`；再写 `parse_md()` 认表格 `|---|`、引用 `>`、有序/无序列表。
3. **颜色一律用 block 级 color**（`callout`/`quote` 的 `color` 字段）或 emoji 色标，**绝不用 table cell 的 color**。

### 验收脚本的坑（差点又被骗）

- 第一版查 `b['embed'].get('external',{}).get('url')` → 全报 `NO_S3_EMBED`，但 08-30 明明手工验证过是好的。**实际 URL 在 `b['embed']['url']` 顶层**。
- 第二版把 `has_literal` 初值写成 `False` 又当"存在"用 → 30 篇全报 `LITERAL_MD` 假阳性。**布尔判断别写反。**
- 修正后 31 页里 30 页全合格。剩 3 篇报 `LITERAL_MD` 是**源文本真含 `****91e9`**（API key 尾号），属误报；`10-03` 无 embed 正常（手建空模板，等今晚 22:30 出 HTML）。
- **教训：验收脚本本身要先拿一篇已知正确的页做对照**，否则信它的结论就是自欺欺人。

### 最终结果

31 页 = 30 篇日报（2026-08-30~ 10-02）+ 1 条手建 10-03。每篇：核心指标表 / 问题与阻塞（🟡🔵 色标）/ 今日完成（时间轴 + **加粗生效**）/ 进行中表 / 明日计划 + 原始 HTML 暗色卡片版 embed（S3 链接可渲染）。测试副本 `9月12 (1)` 已 trash。

## 🗑️ 「待删除」垃圾箱套路（workaround 推一个能多删的场景）

- **场景**：MCP 没有 `delete-page` / `archive` / `in_trash` 工具，22 个空重复 / 模板条目 / 首页都需要回收，手动逐个点太烦。
- **套路**：建一个草稿页（`creation_mode: draft` = workspace 顶层私页）→ 用 `move-pages` 把所有要删的页面 `new_parent: {page_id: <草稿页>}` 批量收进去 → 草稿页里会嵌套全部子页 → 用户只 trash 这一个草稿父页，Notion 递归删除所有子页（20 个一次性进回收站）。
- **已实测**：批量 move 20 个 page 一次性成功，草稿页作为父页后所有 page 的 `<ancestor-path>` 都指向它。但**草稿页对用户默认不可见**——用户需要通过 URL 直达（`https://app.notion.com/p/<id>`）或搜索才能找到它。创建后最好把 URL 明确告诉用户。
- **draft + move to workspace 是 noop**：草稿页本身已经在 workspace 顶层，再 `new_parent: {type: workspace}` 移动会返回 "1 item was already in the target location"。草稿位置就是 workspace 顶层。
